## Chrome 打开讲义页内存占用诊断（215 MB 从何而来）

**起因**：用户发现 Chrome 打开 `docs/` 下的 HTML 后，标签页内存 215068K（约 210 MB），问原因与优化方案。

**方法**：写了 CDP 探针 `.refs/mem-probe.mjs`（无头/带界面 Chrome + `Performance.getMetrics` + `Memory.getDOMCounters` + tasklist 私有工作集 + `SystemInfo.getProcessInfo` 按 PID 关联进程类型），另有 `.refs/storage-probe.mjs` 验证存储共享与进程复用。两个脚本都在 `.refs/`（gitignore、不提交）。

**核心结论**：
- 全新无扩展 Chrome 打开**空白页**就 **562.7 MB / 10 进程**；最大讲义页（01 课）**668.9 MB**。
- 承载页面的渲染进程：空白页 84.1 MB → 01 课 114.9 MB，**页面内容只贡献约 30 MB**（约 15%）。
- 索引页 456 节点时最大渲染进程 81.3 MB，**比空白页的 84.1 MB 还小** → 80 MB 上下是渲染进程的固定底子，与内容无关。DOM 从 456 → 10,971 节点（24 倍）只让渲染进程涨 34 MB。
- 01 课结构：DOM 10,971 节点 / 3,984 元素 / 41 表 1,004 单元格 / 992 个 `<strong>` / 页高 73,113 px（81 屏）/ **JS 堆仅 0.57 MB** / 66 监听器 / 加载 Layout 1.43 s、Task 1.84 s。
- `tools/app.js` 无内存问题：无常驻定时器、无大对象缓存、滚动 rAF 节流 + passive。

**两条被实测否定的设想（以后不要再提）**：
- ❌「`file://` 下 localStorage 跨页不共享、学习状态功能是坏的」→ **实际共享**（Chrome 视所有 `file://` 页为同一源 `file://`），从 index 写入、导航到 01 课能读到。
- ❌「改用本地 HTTP 服务可让同源标签复用渲染进程从而省内存」→ **不成立**，`file://` 与 `http://` 都一样，每新开一个标签 = 多一个独立渲染进程（实测两次新开、渲染进程 +2）。

**唯一真正的性能缺陷**：`tools/style.css` 第 129–130 行顶栏 `backdrop-filter: blur(12px) saturate(1.3)`。实测（软件合成）滚动时样式重算 190 → 68 次（−64%）、滚动 CPU 501 → 352 ms（−30%）。核显机器受益更明显。**尚未修改**。

2. 字重归并：`style.css` 第 413 行 `750`、893 行 `780`、978 行 `650` → `700` / `600`；

### 三、顺带查出并修掉两类"只有渲染才暴露"的 Markdown 缺陷

1. **`**` 紧跟在标点之后 → 不能当闭合标记**（CommonMark 右翼规则）：`**` 前是标点、后是汉字时该对粗体失效，页面**字面露出 `**`**。全仓库 **16 处**（02/03/04/05/06/08/12/99 与 01 各 1~3 处）。典型：「逻辑独立性屏蔽的是**逻辑结构（表定义）**的变化」——把括号移到加粗外即可。
2. **单个 `~` 被当成删除线分隔符**：同段落内 2 个以上 ASCII `~`（哪怕隔几十字）会把中间整段文字包进 `<del>` 打删除线。全仓库 **83 处 `~`**（其中 **13 处**已真的产生删除线，06 课有一整句被划掉）。范围一律改全角 `～`，代码块与行内代码内不动。
3. **行内代码里写 `**52**`** → 代码内不解析标记，页面露出字面星号（01 快排演算原表就有），已清。

**审计/修复脚本**：`.refs/audit-bold.mjs`（逐段解析、剥掉代码后找残留 `**`；**注意要排除 `____` 填空下划线**）、`.refs/patch-markdown-defects.mjs`（波浪号按行内代码分段替换 + 16 处粗体精确替换，断言命中数）、`.refs/patch01-lists.mjs`。**踩坑：Write 工具会把 `\`` 转义吃掉**——脚本里要写反引号时用哨兵字符（如 `§`）或 `String.fromCharCode(96)`，别用 `\``。
