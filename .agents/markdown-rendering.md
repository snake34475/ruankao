# Markdown 与渲染规范

这些规则用于避免“源码看起来正常、浏览器显示错误”。修改课程 Markdown 时必须执行。

## 链接与标记

- 不写页内 `#标题` 锚点链接。构建后的标题 ID 是顺序号，增删小节会使其漂移。引用本页内容时写“见第 X 节”，跨文件则使用相对文件链接。
- UML 构造型如 `<<include>>`、`<<extend>>`、`<<component>>`、`<<Database>>` 必须放在反引号内，否则浏览器可能把它当 HTML 标签吞掉。
- 避免生僻 Unicode 图形。字体兼容性不确定时用文字描述或常见 ASCII 字符。
- 粗体标记不要把右括号、引号或句号包在末尾。写成“这是**逻辑结构**（表定义）的变化”，避免标点导致闭合 `**` 失效。
- 普通文本中的范围使用全角 `～`，例如 `0～255`。同一段落中的多个 ASCII `~` 可能触发删除线；代码块和行内代码不受此限制。
- **一个符号只承担一种含义**。图论、状态机、流程图类小节里 `→` 已经表示“图的边／状态转移”时，同一行（尤其同一表格单元格）不得再用 `→` 表示“于是、得出”。改用“于是”“从而”“即”等文字。例如“删 A→B、A→C → B 变 0”会被读成存在一条 A→C→B 的边，必须写成“删掉 A→B、A→C 两条边，于是 B、C 的入度变 0”。

## 表格与长内容

- 横向对齐本身有意义的信息继续使用表格，例如算法稳定性、步骤状态和判断结果。
- 不用全角 `｜` 拼接伪表格；比例字体无法保证列对齐。
- 长角色链、参数串或说明使单元格被压成逐字竖排时，先缩短措辞；仍不适合时改为分组列表，每条一段。
- 判断表格是否拥挤必须看真实渲染结果，不能只凭首列字数或 DOM 数量判断。
- 新格式先在一页、一个小节中实渲染验证，再推广到其他课程。
- **算法过程表的列头必须写清筛选口径**。只写“所有入度为 0 的点”会被读成**累计集合**（把已处理过的元素也算进去），而表格通常想表达的是“当前可用的元素”。应写成“本轮可输出的点（未输出、入度为 0）”这类明确表述，并在表下说明“不累计”。凡列头含“所有”“当前”而实际语义是“筛选后的子集”时，都要改成限定写法。

## ASCII 图

- 图中的树、图、流程和数据关系必须合法并经过计算验证。
- 同一小节统一高度、深度、路径长度等口径。
- 中文和全角符号通常占两个等宽字符位置；斜线、节点和边的对齐要在等宽字体中检查。
- 图改动后同时核对正文、公式和答案，避免多个表示使用不同数据。

## 源码检查

- 检查正文残留的字面 `**`、意外生成的 `<del>`、裸写 UML 构造型以及失效相对链接。
- 如果 `.refs/audit-bold.mjs`、`.refs/table-sweep.mjs` 等本地工具存在，可以复用；`.refs/` 内容不提交。
- 静态扫描只能发现候选问题，最终以浏览器渲染检查为准。
