## 第一节 三级模式与两级映像 ★

### 为什么需要"三级模式"

数据库是被很多应用程序**共享**的：财务程序、人事程序、报表工具都要读同一批数据，但它们各只关心自己那一块，而且谁都不希望"存储结构一改、我的程序就得重写"。为此数据库把数据组织分成三个视角、配上两层"翻译层"，把**变化隔离**在各自层内——这就是考"独立性"的全部动机。

| 层次 | 别名 | 看到什么 | 例子 |
|---|---|---|---|
| 外模式 | 用户模式/子模式 | 某类用户看到的部分数据 | 一个视图、一张报表用的字段 |
| 概念模式 | 模式/逻辑模式 | 全体数据的逻辑结构 | 一张张表的定义 |
| 内模式 | 存储模式 | 数据在磁盘上怎么存 | 索引、压缩、存储顺序 |

**两级映像**（考试考"哪个映像对应哪种独立性"，必背）：

| 映像 | 连接的两层 | 保证的独立性 | 白话 |
|---|---|---|---|
| **外模式/模式映像** | 外模式 ↔ 模式 | **逻辑独立性** | 表的逻辑结构变了（加字段），应用程序不用改 |
| **模式/内模式映像** | 模式 ↔ 内模式 | **物理独立性** | 换了存储方式（加了索引、换了磁盘），应用程序和表定义都不用改 |

**反例演示（易错）**：题目说"数据存储结构改变，模式不变"——变化发生在内模式层，靠**模式/内模式映像**挡住 → **物理独立性**；说"表新增了字段，应用程序不变"——变化发生在模式层，靠**外模式/模式映像**挡住 → **逻辑独立性**。判断口诀：**变化发生在哪一层，挡住它的映像就连着哪一层；看应用程序"感知不到什么"来选词**。别把"逻辑独立性 = 跟逻辑有关所以是内模式"想反了——逻辑独立性恰恰是指**逻辑结构变化也影响不到应用**。

**应试动作**：背"外模式/模式映像 ↔ 逻辑独立性，模式/内模式映像 ↔ 物理独立性"这一组对应，考试只考配对，认出题干描述的变化发生在哪层即可。

## 第二节 E-R 模型 ★★★（案例题必考）

### 实体、属性、联系

- **实体**：客观存在可区分的事物（一个学生、一门课），矩形框。
- **属性**：实体或联系的性质（学号、姓名），椭圆；能唯一标识实体的属性叫**码**。
- **联系**：实体之间的关系，菱形（如学生"选修"课程）。

### 联系类型：1:1、1:n、m:n（必须会判）

拿具体业务判断"一个 A 对应几个 B"：

- **1:1**：一个部门只有一个经理，一个经理只管一个部门。
- **1:n**：一个部门有多个员工，一个员工只属于一个部门 → 部门:员工 = 1:n。
- **m:n**：一个学生选多门课，一门课被多个学生选 → 学生:课程 = m:n。

**判断反例（易错）**：别看到"多个"就判 m:n——**只有两边都能是"多个"才是 m:n**。"一个班有多名学生"但"一名学生只属一个班"是 1:n，不是 m:n。

### E-R 图转关系模式（案例题必考步骤）

| 联系类型 | 转换规则 |
|---|---|
| 1:1 | 联系并入任一端实体（加对方的主键作外键） |
| 1:n | 联系并入 **n 端**实体（加 1 端的主键作外键） |
| **m:n** | **联系必须单独建一张关系模式**，主键 = 两端主键的组合 |

**反例演示（易错）**：学生-课程是 m:n，若把"选课"并入学生表（学生表加课程号、成绩列），一个学生选多门课就要占多行，学号、姓名重复存储，而且学号不再能作主键——错。**口诀：多对多，单独坐一桌**。

### E-R 集成时的三类冲突（选择题考过）

多个分 E-R 图合并时会撞车：**属性冲突**（同一属性类型/单位不一致）、**命名冲突**（同名异义、异名同义）、**结构冲突**（同一对象在此图是实体、在彼图是属性）。**没有"实体冲突"这种说法**——选项里出现即排除。

## 第三节 关系代数 ★★

关系代数就是"对表做运算"。考三种：

### 选择 σ：挑行

σ(系别='计算机')(学生) = 从学生表里**抽出满足条件的行**（水平方向切）。

### 投影 π：挑列

π(姓名,系别)(学生) = 只保留指定**列**（垂直方向切）。**注意：投影会自动去掉重复行**（只剩两列后原本不同的行可能变得相同）。

### 连接 ⋈：两张表拼起来

- **θ 连接**：按"某列 vs 某列"的比较条件拼接。
- **自然连接**：按**所有同名属性**相等来拼接，**结果去掉重复列**。

**公式三件套（考数字计算）**：
- 笛卡尔积 R×S：若 R 有 r 行 s 列、S 有 t 行 u 列，结果 **r×t 行、s+u 列**。
- 自然连接结果的**列数 = s + u − 公共属性个数**（重复列只留一份）。
- 例：R(A,B,C) 有 3 行，S(C,D,E) 有 4 行，公共列 1 个（C）→ 自然连接列数 = 3+3−1 = **5**。

**反例演示（易错）**：自然连接 ≠ 笛卡尔积再挑同名相等的行之后还保留两份 C 列——重复列必须**去掉一份**；选项里列数算成 s+u 的是陷阱。另外投影和选择的别记反：**选择管行（横向内容）、投影管列（纵向结构）**，σ 的 σ 像"筛子"筛行，π 的两条竖线像切列的刀。

**应试动作**：背"σ 行、π 列、⋈ 拼表去重列"；行数列数计算用上面公式代数字。

## 第四节 关系规范化 ★★★（选择题 + 案例题双考）

### 为什么要规范化

一张大表什么都往里塞，会出现三种病：**数据冗余**（系主任跟着每个学生重复存）、**修改麻烦**（换主任要改几百行）、**插入/删除异常**（还没招生的系插不进来、最后一个学生毕业系主任信息也跟着没了）。规范化的目的就是**拆表**，把这些病一步步消掉。

### 函数依赖（判断范式的唯一工具）

X→Y 读作"X 决定 Y"：知道 X 就能唯一确定 Y。三种关键形态（设 K 是候选键）：

- **完全依赖**：Y 依赖整个 K，去掉 K 中任何一个属性都不行。例：(学号, 课程号)→成绩。
- **部分依赖**：Y 依赖 K 的**一部分**就够了。例：(学号, 课程号)→姓名，其实学号→姓名——**部分依赖是病**。
- **传递依赖**：X→Y、Y→Z 且 Y 不决定 X，则 Z 传递依赖 X。例：学号→系名→系主任——**传递依赖是病**。

### 范式判定：一级一级"消病"

| 范式 | 要求 | 一句话判定 |
|---|---|---|
| 1NF | 属性不可再分（数据库默认满足） | 所有属性都是原子值 |
| 2NF | 消除**部分依赖** | 每个非主属性都依赖**整个**候选键 |
| 3NF | 再消除**传递依赖** | 非主属性不间接依赖候选键 |
| BCNF | 每个决定因素都必须是候选键 | 比 3NF 更严：主属性也不能有依赖毛病 |

**判定四步法（背流程，别背定义）**：
1. 找候选键（见下）；
2. 列出所有"决定→被决定"；
3. 看有没有**非主属性只依赖候选键一部分** → 有则最高 1NF；
4. 再看有没有**非主属性靠别的非主属性中转** → 有则最高 2NF；都没有 → 3NF；若还有主属性被非主属性决定 → 不到 BCNF。

**反例演示（易错）**：R(学号, 姓名, 系, 系主任)，学号→姓名、学号→系、系→系主任。候选键是学号（单属性），**不可能有部分依赖**（键只有一个属性，"一部分"还是它自己），所以它**直接就是 2NF**；但学号→系→系主任是传递依赖，所以**最高 2NF，不是 3NF**。最常见的错误就是把"有冗余"当成"不是 2NF"——单属性键的表不存在部分依赖，第一步就能跳过。

### 候选键怎么求（案例题必考）

**口诀：只在依赖集右部出现过的属性，必在候选键里**（它不被任何人决定，只能靠自己去决定别人）。从这些属性出发，看能否推出全部属性，不够就再拼上别的属性。

例：R(A,B,C,D)，F = {A→B, B→C, D→B}。右部出现过的：B、C。从未出现在右部的：**A、D**。验证 AD：A→B，B→C，D→B → 可推出 A、B、C、D 全部 → **候选键 = AD**（ABD 虽也能决定全部，但含多余属性，是超键不是候选键）。

**分解保持性**：拆表后要求"无损连接"（能自然连接回原表，不丢信息也不多出假行）；3NF 分解还能保持函数依赖。案例题小问爱考"分解后最高达到几范式"。

**应试动作**：背四步判定法 + "右部不出现的属性进候选键"；考"最高属于第几范式"时**从低往高验**，卡在哪级就答前一级。

## 第五节 SQL ★★★（案例题必考）

SQL 分四类语句，案例题主要考前两类：

| 类别 | 关键词 | 用途 |
|---|---|---|
| DDL 数据定义 | CREATE / ALTER / DROP | 建表、建视图、改结构 |
| DML 数据操纵 | SELECT / INSERT / UPDATE / DELETE | 查和改数据 |
| DCL 数据控制 | GRANT / REVOKE | 授权、收权（选择题常考） |

### SELECT 完整骨架（背顺序）

```sql
SELECT   列名或函数            -- ⑤ 挑列
FROM     表                    -- ① 数据从哪来（可 JOIN ... ON）
WHERE    行条件                -- ② 先筛行
GROUP BY 分组列                -- ③ 按列分组
HAVING   组条件                -- ④ 筛组（条件里通常带聚合函数）
ORDER BY 排序列 [ASC|DESC];    -- ⑥ 最后排序
```

**为什么 HAVING 和 WHERE 要分家**：WHERE 在分组**前**筛原始行，此时还没有算出平均分这类聚合值；HAVING 在分组**后**筛"每组"。所以"查询平均分大于 80 的课程"必须写 `HAVING AVG(成绩)>80`，写进 WHERE 直接报错——这是最常见的案例扣分点。

### 建表与完整性（案例题第 1 小问模板）

```sql
CREATE TABLE SC (
    Sno   CHAR(8),
    Cno   CHAR(6),
    Grade SMALLINT,
    PRIMARY KEY (Sno, Cno),                -- 实体完整性：主键
    FOREIGN KEY (Sno) REFERENCES Student(Sno),  -- 参照完整性：外键
    FOREIGN KEY (Cno) REFERENCES Course(Cno),
    CHECK (Grade BETWEEN 0 AND 100)        -- 用户定义完整性
);
```

三种完整性对应关系：主键 → 实体完整性；外键 → 参照完整性；CHECK/取值范围 → 用户定义完整性。**选择题爱考对应关系，案例题爱考写外键子句**。

### 视图与授权

```sql
CREATE VIEW 计算机系学生 AS
    SELECT Sno, Sname FROM Student WHERE Dept = '计算机';

GRANT SELECT, INSERT ON SC TO 用户1 WITH GRANT OPTION;  -- 授权（可转授）
REVOKE SELECT ON SC FROM 用户1;                          -- 收回权限
```

**视图的动机**：视图是一张**虚表**（只存定义不存数据），作用有二——① 简化常用查询；② **提供逻辑独立性/安全隔离**（用户只见视图字段，表结构改了只需改视图定义）。考题问"视图的作用/提高了什么独立性"→ 答**逻辑独立性**（视图是外模式级的东西，正好呼应第一节）。

### 嵌套查询（选择题常考）

```sql
SELECT Sname FROM Student
WHERE Sno IN (SELECT Sno FROM SC WHERE Cno = 'C02');
```

IN 后面跟子查询结果集合；EXISTS 写法是"存在即保留"，选择题考"IN 与 EXISTS 等价改写"。

**应试动作**：SELECT 骨架六个子句的**执行顺序**（FROM→WHERE→GROUP→HAVING→SELECT→ORDER）必须背熟，它是所有 SQL 题的做题导航。

## 第六节 事务、并发控制与故障恢复 ★★

### 事务与 ACID

事务是"要么全做、要么全不做"的一组操作。经典例子：转账 = A 扣 100 + B 加 100，两个 UPDATE 必须同生共死。

| 性质 | 含义 | 靠什么保证 |
|---|---|---|
| 原子性 Atomicity | 全做或全不做 | 故障恢复（UNDO） |
| 一致性 Consistency | 事务前后数据都处于正确状态 | 原子性 + 隔离性共同效果 |
| 隔离性 Isolation | 并发事务互不干扰 | 并发控制（锁） |
| 持久性 Durability | 提交后永久生效 | 故障恢复（REDO/日志） |

考法："转账中途断电，钱不能凭空消失"体现**原子性**；"提交后断电重启数据仍在"体现**持久性**。

### 并发带来的三类错误（反例各背一个）

两个事务 T1、T2 同时操作 A=100：

1. **丢失修改**：T1 和 T2 都读 A=100，T1 加 10 写回 110，T2 减 5 写回 95——T1 的修改被**覆盖丢了**（应是 105）。
2. **不可重复读**：T1 读 A=100，T2 把 A 改成 200 并提交，T1 再读 A 变 200——**同一事务内两次读结果不同**。
3. **读脏数据**：T1 把 A 改成 200（还没提交），T2 读到 200；T1 随后**回滚**，A 恢复 100——T2 读到的 200 是"脏"的，根本没生效过。

区分口诀：**丢改是"写丢了"，不可重复读是"读两次不一样"，脏读是"读到了没提交的"**。

### 封锁与两段锁协议

- **S 锁（共享锁/读锁）**：加锁后别人只能读不能写。S 与 S **相容**（都能读）。
- **X 锁（排他锁/写锁）**：加锁后别人读写都不行。X 与任何锁都**不相容**。
- **两段锁协议**：事务分两阶段——先**扩展阶段**（只加锁不放锁），后**收缩阶段**（只放锁不加锁）。遵守两段锁协议 → 调度**可串行化**（并发结果等价于某个串行执行），但**不能避免死锁**（反例：T1 锁了 A 等 B，T2 锁了 B 等 A）。这是经典选择题："两段锁协议保证可串行化、不保证不死锁"。

### 故障恢复：REDO 与 UNDO

依靠**日志**（先写日志、后写数据库）+ **检查点**。系统重启后扫描日志：

- 事务**已提交**（BEGIN 后有 COMMIT）→ **REDO 重做**（结果已该生效，重放保证落盘）；
- 事务**未提交**（只有 BEGIN 没有 COMMIT）→ **UNDO 撤销**（做了一半的必须抹掉）。

口诀：**提交了就重做（REDO），没提交就撤销（UNDO）**。检查点的作用：缩小扫描范围，检查点之前已落盘的不用管。

### 分布式数据库的透明性（选择题 0–1 题，背四个名词）

- **分片透明**（最高层）：用户不必知道数据怎么**分块**；
- **复制透明**：不必知道数据在各节点**复制**了几份；
- **位置透明**：不必知道数据存在**哪个站点**；
- **逻辑透明**（最低层）：不必知道局部场地用什么数据模型。

**应试动作**：ACID 四个词背全称；三类并发错误能看描述对号入座；"两段锁 → 可串行化但可能死锁"背成一句；REDO/UNDO 口诀背死。

## 第七节 案例题专攻：数据库设计大题（约 15 分）

案例第 2 题一般是"业务说明 + 不完整 E-R 图 + 关系模式 + SQL 填空"，三小问固定套路：

### 套路一：E-R 图补全——读句子找联系

题干每个动词都暗示一条联系："学生**选修**课程""教师**讲授**课程""部门**聘用**员工"。补空时：
1. 先数图中已有几实几联系，句子里的名词 = 实体、动词 = 联系；
2. 联系类型用业务常识判："一个 X 对应几个 Y"，两边都可多个才是 m:n；
3. m:n 联系上若有自己的属性（如"成绩"属于选课联系而非学生或课程），标在菱形上。

### 套路二：关系模式填空——主键外键往哪放

1. 每个实体一张表，主键 = 实体的码；
2. 1:n 联系：把 1 端主键放进 **n 端表**作外键；
3. m:n 联系：单独建表，主键 = **两端主键组合**，联系的属性（成绩）也放这张表；
4. 小问问"XX 表的主键是什么"：先想清它是实体表还是联系表，联系表的主键几乎总是组合键。

### 套路三：SQL 填空——按 SELECT 骨架对号入座

1. 空 FROM：看 SELECT 和 WHERE 里用了哪些列，缺哪张表补哪张，多表加 `JOIN ... ON 连接条件`；
2. 空 WHERE：对应题干"查询**满足某条件**的行"，日期/字符串加引号；
3. 空在聚合旁："每门课/每个部门的平均/最高/数量"→ `GROUP BY` 分组列，条件带 AVG/MAX/COUNT 写 `HAVING`；
4. 空在 CREATE TABLE：主键 `PRIMARY KEY(...)`、外键 `FOREIGN KEY(...) REFERENCES 表(列)`；
5. 填完代入一条具体数据心里跑一遍（同第一课算法填空的自检法）。

## 答案与解析

### 课后考题答案

**1. B**
外模式就是某类用户看到的局部数据逻辑（典型实现即视图）。概念模式是全体逻辑，内模式/存储模式是物理层。★ 对应关系直接背。

**2. B**
存储结构变化发生在内模式，靠模式/内模式映像屏蔽 → 物理独立性。易错点：把"逻辑独立性"跟"存储"联想到一起——恰好相反，逻辑独立性屏蔽的是**逻辑结构（表定义）**的变化。

**3. B**
一门课只属一个教师、一个教师可授多门课 → 教师:课程 = 1:n。易错点：见到"多门"就选 m:n——必须**两边都可多**才是 m:n，这里课程一侧只能一个教师。

**4. C**
m:n 联系必须单独建关系模式，主键 = 学生主键 + 课程主键组合，联系自身的属性（成绩）也放这里。并入任一端都会造成学号重复存储、学号失去主键资格。

**5. D**
行数：自然连接行数取决于同名属性上相等的元组如何配对，**不能确定**（最少可能 0 行）；列数 = 4+6−1 = **9**。所以选"行数不确定、9 列"。易错点：列数算成 10（忘了去掉一份重复列）或行数答 15（那是笛卡尔积的行数）。

**6. B**
选择 σ 挑行，投影 π 挑列。口诀：σ 像筛子筛行，π 两条竖线切列。

**7. A**
能唯一标识元组且**无多余属性**正是候选键的定义。超键只要求"能唯一标识"（可含多余属性）；主属性是包含在任一候选键中的属性，不是属性集；外键是引用他表主键的属性。

**8. A**
右部出现过的属性：B（A→B）、C（B→C）、B（D→B）——即 B、C。从未出现在右部的：**A、D** → 先试 AD：A→B，B→C，D→B，闭包 = A、B、C、D 全部 → 候选键 = AD。再看其余三个为何只是超键：ABD 闭包虽也是 ABCD，但 B 可由 A 推出（A→B），去掉 B 剩 AD 仍能推全 → B 是多余属性；ACD 同理，C 可由 A→B→C 推出，去掉 C 剩 AD 仍推全 → C 多余；ABCD 显然更冗余。**候选键 = 无多余属性的"最小"超键，四个选项里只有 AD 满足**。

**9. B**
候选键 = 学号（单属性）→ 不存在部分依赖，直接满足 2NF；但学号→系→系主任是传递依赖 → 达不到 3NF。**最高 2NF**。易错点：因"有冗余"误判 1NF——单属性键的表第一步就不可能有部分依赖。

**10. D**
范式是逐级加严的包含链：1NF ⊃ 2NF ⊃ 3NF ⊃ BCNF。BCNF ⇒ 3NF 成立（C 对），反过来 3NF 不一定到 BCNF（D 错，反例：存在主属性被非主属性决定的情况）。A、B 是标准定义。

**11. B**
聚合条件只能写 HAVING：`GROUP BY 课程号 HAVING AVG(成绩)>=80`。WHERE 在分组前执行，彼时 AVG 还没算出来，A 语法错误。D 把成绩当分组列，会把每个分数各成一组，不符合"按课程"。

**12. B**
GRANT 授予、REVOKE 收回。DROP 是删除对象（DDL），DENY 不是软考教材标准关键词。

**13. C**
读到"未提交、随后被回滚"的数据 = 脏数据（读脏数据）。区分：不可重复读是"本事务两次读之间被**别人提交**的修改弄得不一致"；丢失修改是两个都提交导致一个写被覆盖。

**14. B**
两段锁协议：先统一加锁、后统一放锁 → 保证可串行化；但两个事务可能互相持有对方要的锁（T1 锁 A 等 B，T2 锁 B 等 A）→ **不能避免死锁**。A、C、D 均为典型错误表述。

**15. B**
故障恢复口诀：**已提交 REDO（重做），未提交 UNDO（撤销）**。未完成的事务做了一半，必须撤销抹掉。ROLLBACK 是事务运行期间的主动回滚操作，不是恢复策略本身。

### 案例题答案

**问题 1（E-R 图描述）**：
实体三个：代表团、运动员、比赛项目。
- 代表团—运动员：**1:n** 的"组成"联系；
- 运动员—比赛项目：**m:n** 的"参赛"联系，联系属性：成绩。
（画图时：三个矩形 + 两个菱形；"参赛"菱形上挂"成绩"椭圆。）

**问题 2（关系模式）**：
- 代表团(**团编号**, 团名, 团所在地)
- 运动员(**运动员编号**, 姓名, **团编号**) ← 1:n 联系，把 1 端主键"团编号"并入 n 端作外键
- 比赛项目(**项目编号**, 项目名称)
- 参赛(**运动员编号, 项目编号**, 成绩) ← m:n 联系单独建表

**"参赛"表的主键 =（运动员编号，项目编号）组合键**——单靠任何一端都无法唯一标识一行（同一运动员参加多个项目、同一项目多名运动员）。

**问题 3（SQL）**：

```sql
-- (1) 建参赛表
CREATE TABLE 参赛 (
    运动员编号  CHAR(8),
    项目编号    CHAR(6),
    成绩        SMALLINT,
    PRIMARY KEY (运动员编号, 项目编号),
    FOREIGN KEY (运动员编号) REFERENCES 运动员(运动员编号),
    FOREIGN KEY (项目编号)   REFERENCES 比赛项目(项目编号)
);
```

```sql
-- (2) 各代表团总分，保留 300 分以上
SELECT 代表团.团编号, 代表团.团名, SUM(参赛.成绩) AS 总分
FROM 代表团
JOIN 运动员 ON 代表团.团编号 = 运动员.团编号
JOIN 参赛   ON 运动员.运动员编号 = 参赛.运动员编号
GROUP BY 代表团.团编号, 代表团.团名
HAVING SUM(参赛.成绩) >= 300;
```
（要点：三表连接取全路径代表团→运动员→参赛；GROUP BY 带上团编号防止两个代表团重名被并成一组；聚合条件进 HAVING。）

```sql
-- (3) 建视图
CREATE VIEW vHighScore AS
SELECT 运动员.运动员编号, 运动员.姓名, 比赛项目.项目名称
FROM 运动员
JOIN 参赛 ON 运动员.运动员编号 = 参赛.运动员编号
JOIN 比赛项目 ON 参赛.项目编号 = 比赛项目.项目编号
WHERE 参赛.成绩 >= 95;
```

### 精华题答案

**1. 视图属于外模式；索引属于内模式**
视图是用户局部视图（外模式级，典型实现）；索引是物理存储组织（内模式级）。这题考"具体事物 → 归哪一层"：用户看到的逻辑 = 外模式，磁盘组织细节 = 内模式。

**2. 列数 = 3 + 2 − 1 = 4 列**（R 的 A、B、C 三列加 S 的 D 列，公共属性 B 只留一份）。
行数最多 = **2×3 = 6 行**（R 的每行 B 值恰好都能在 S 中配上时，最多达到笛卡尔积水平；若 B 值全对不上则 0 行）。

**3. R 最高属于 2NF**
候选键 = 仓库号（单属性）→ 无部分依赖 → 满足 2NF；仓库号→城市→地区编号是传递依赖 → 不到 3NF。
分解到 3NF：仓库(**仓库号**, 仓库面积, 城市) 和 城市(**城市**, 地区编号)。

**4. 候选键 = E**
右部出现过的属性：B、D、A、C；从未出现在右部的只有 **E**。试 E：E→A，A→B，B→C，C→D → 闭包 = ABCDE，全部推出 → **E 单属性即候选键**。（验证：E→A→B→C→D，链式全推。）

**易错点：答案不是 "AE"**。AE 也能推出全部属性（A→B→C→D，再加 E），但它**含冗余属性**——E 一个人就够了，A 是多余的。候选键的定义是**不含冗余属性的最小超键**，能少一个就少一个，多出来的那个只能叫超键。反向也要查一遍：A 行不行？A→B→C→D 只能推出 A、B、C、D，**推不出 E**，所以 A 不是候选键。本题**唯一候选键 = E**。

**5. 发生丢失修改时，A 的错误终值可能是 100 或 70；正确终值应为 120 或 140（取决于串行顺序）**
错误终值举例：T1 读 A=50 → T2 读 A=50 → T1 写回 70 → T2 写回 50×2=100，T1 的 +20 被覆盖丢失；另一交错 T2 先写 100、T1 再写 70，则 T2 的结果丢失。正确终值：先 T1 后 T2 串行 = (50+20)×2 = **140**；先 T2 后 T1 = 50×2+20 = **120**——两种都符合事务语义，但丢失修改哪种都得不到。此题演示"丢失修改 = 一个事务的写被另一个事务的写覆盖"。

**6. SQL 答案**：

```sql
-- (1) 嵌套查询
SELECT Sname FROM Student
WHERE Sno IN (SELECT Sno FROM SC WHERE Cno = 'C02');

-- (2) 选课超过 3 门
SELECT Sno FROM SC
GROUP BY Sno HAVING COUNT(Cno) > 3;

-- (3) 授权（可转授）
GRANT SELECT ON SC TO U1 WITH GRANT OPTION;
```
要点：(2) 聚合条件进 HAVING；(3) WITH GRANT OPTION 是"允许转授"的固定写法。

**7. 前者是不可重复读，后者是读脏数据**
"两次读结果不同"：两次读之间**别的已提交事务**改了数据；"读到未提交"：读到的事务随后可能回滚。判断窍门：看干扰事务**提交没有**——提交了 → 不可重复读；没提交（后回滚）→ 脏读。
