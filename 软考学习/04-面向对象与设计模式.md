# 04 面向对象与设计模式

> **分值地位**：本课是"选择题 + 案例题"双料大头 —— 选择题稳定 5–7 题，案例题第三题（UML 建模）是**必答题**、约 15 分；案例题第五题（Java/C++）也常结合设计模式填空。设计模式属"背了就得分"的典型，是全库性价比最高的记忆型考点之一。
>
> **学习目标**：读完讲义后，你能——① 分清封装/继承/多态、重载/重写，说出多态的四种形态与动态绑定的三个条件；② 说清 OOA/OOD 各做哪几步、OOD 七大原则各自反对什么写法；③ 认出 UML 各图及其要素（重点：用例图三关系、类图六关系、状态图五要素、构件图供/需接口、部署图节点）；④ 背下 23 种模式的分类、"意图一句话"与主要模式的**角色名**；⑤ 按套路补全 UML 建模案例题。

## 第一节 面向对象基本概念 ★

### 1.1 四大基石与"为什么"

- **封装**：把数据和对数据的操作捆在一起（类），对外只暴露接口、隐藏实现细节。**动机**：使用者不必知道内部怎么实现，内部改动不波及外部——和数据库三级模式的"隔离变化"是同一个思想。
- **继承**：子类自动拥有父类的属性和方法，并可扩展。**动机**：共同点写一遍（放父类），差异点写在子类——消除重复。
- **多态**：同一消息发给不同对象，各自做出不同响应。**动机**：调用方写一段代码（面向父类/接口），加新子类时调用方**一行都不用改**——否则就得写满 `if 类型==... else if ...`，每加一种类型都要回头改调用方。
- **消息**：对象之间通过发送消息（调用操作）通信。

**类的正式定义**（选择题原话出处）：类是对象的**模板**，描述一类对象共有的特征（属性）和行为（方法）；对象是类的**实例**。一个对象 = **属性（数据）+ 方法（操作）+ 对象标识（ID）**——三样都要有，缺 ID 就不是对象。对象占用内存空间，类不占（类是描述，不是数据本身）。

**应试动作**：认"三件套"——问"对象由什么组成"答「属性 + 方法 + 对象 ID」。

### 1.2 类的三种类型（识别题高频）★

建模时会画一堆类，出题人爱问"某某类属于哪一类"。三类各有**外形特征**，抓住"属性多还是方法多、管不管流程"就能秒判：

| 类型 | 别名 | 干什么 | 外形特征 | 例子 |
|---|---|---|---|---|
| **实体类** | 数据类 | 表示现实世界真实存在的实体 | **属性多、方法少** | 读者、图书、借阅记录、订单 |
| **边界类** | 接口类 | 为用户提供与系统交互的方式（窗口、接口、外部系统接口） | **方法多、属性少**；常带 interface、UI、Adapter | 借书窗口、登录界面、支付接口 |
| **控制类** | 控制/协调类 | 描述业务逻辑、控制活动流，协调实体类与边界类 | 名字常带 **Controller、Manager、Session** | 借书控制器、订单处理器 |

**反例演示（易错）**："图书"和"图书管理界面"都是名词，但一个是**实体类**（有书名/作者/定价等一堆属性），一个是**边界类**（它自己不存数据，只提供"输入书号""显示结果"这些操作）。做题时别只看名字像不像名词，要看**它是"存数据的"还是"干活的/给人用的"**。

**应试动作**：背一句口诀「**实体存数据、边界接用户、控制管流程**」；看到 Controller / Manager / Session / Handler 结尾的名字，优先判控制类。

### 1.3 重载 vs 重写（必考对比）

| | 重载 overload | 重写 override |
|---|---|---|
| 位置 | **同一个类**里 | **子类**覆盖父类方法 |
| 签名 | 方法名相同，**参数列表必须不同** | 方法名、参数列表**完全相同** |
| 绑定时机 | **编译期**根据参数选方法 | **运行期**根据实际对象类型（多态的基础） |
| 关系 | 体现同一个类中的不同表现 | 体现父类与子类的不同表现 |

**反例演示（易错）**：只改返回值类型、参数完全相同——既不是重载也不是重写，是编译错误（重载要求参数不同）；子类方法参数列表与父类不同，那就成了重载（新方法），**父类版本没有被覆盖**，用父类引用调用时执行的还是父类版本——这是"以为重写了、其实重载了"的经典陷阱。

**应试动作**：抓两个判别词——"同类不同参 = 重载；子类同签名 = 重写"。考题常给一段代码问"输出什么"：父类引用指向子类对象，调用被重写的方法 → 执行**子类**版本。

### 1.4 多态的四种形态（选择题送分点）★

"多态"不是只有一种，按**形成机制**分四类。考题常问"哪种多态应用最广泛/最纯"或"下面的例子属于哪种多态"：

| 形态 | 机制 | 一句话认法 | 例子 |
|---|---|---|---|
| **过载多态**（ad hoc） | 同一个名字在不同上下文中含义不同 | **就是重载** | `add(int,int)` 与 `add(String,String)` |
| **参数多态** | 类型作为参数，一套代码适配多种类型 | **泛型**（"最纯、应用最广泛"） | `List<T>`、`swap<T>(a,b)` |
| **包含多态** | 同样操作可用于一个类型**及其子类型** | **子类替换父类**，需运行期类型检查 | 父类引用调子类重写的方法 |
| **强制多态** | 编译程序通过语义操作把类型**强行变换** | **隐式类型转换** | `int` 参与浮点运算时自动转 `double` |

**记忆抓手**：**过载**名字一样、**参数**类型当参、**包含**子类包进来、**强制**编译器硬转。

**反例演示（易错）**：别把"参数多态"和"包含多态"混了 —— 判断标准是**"靠类型参数化"还是"靠继承层次"**。`List<int>` 和 `List<String>` 用同一个 `List` 是**参数多态**（没有继承关系）；父类引用指向子类对象是**包含多态**（有继承关系）。

### 1.5 动态绑定：多态落地要同时满足三个条件 ★

讲义前面说"父类引用指向子类对象、调用被重写的方法就执行子类版本"——这不是无条件成立的，**三个条件缺一不可**：

1. 要有**继承关系**（子类继承父类）；
2. 要发生了**重写**（子类覆盖了父类的方法）；
3. 要有**父类引用指向子类对象**（`父类类型 变量 = new 子类类型();`）。

**绑定时机对照**：**静态绑定**发生在**编译时**（如重载按参数类型选定方法）；**动态绑定**发生在**运行时**（按对象的实际类型选定方法）。

**反例演示（易错）**：三个条件少一个，多态就不发生 —— 若父类方法**没被子类重写**，父类引用调它就是父类版本；若用**子类引用**调，即使重写了也谈不上"多态"（本来就是子类对象，直接调即可）；若方法被声明为不可覆盖（Java 的 `static`、`final`、`private` 方法），走的就是静态绑定。

**应试动作**：看到代码题里出现 `父类 p = new 子类();`，先在心里核对这三条，再判定"调的是哪个版本"；问"为什么输出父类版本"时，答案往往就是**"该方法没有被重写"**或**"它不是通过父类引用调用的"**。

## 第二节 面向对象分析与设计过程 ★★

### 2.1 为什么先要有"过程"

很多人以为"面向对象"就是"写类"。但类从哪来？属性怎么定？关系怎么画？——**不解决这些问题，画出来的类图就是凭感觉摆的**。OOA（面向对象分析）解决"**要什么**"，OOD（面向对象设计）解决"**怎么搭**"，两步各有一套固定动作。考试既考选择题（问"下面哪一步属于 OOA"），更是 UML 案例题的**解题骨架**——案例题让你补类名、补方法名，靠的就是 OOD 的"定义属性/定义服务"这两步。

### 2.2 OOA 四步（背顺序，选择题按顺序出干扰项）★★

| 步骤 | 做什么 | 落在案例题里的动作 |
|---|---|---|
| ① **认定对象** | 从需求描述里挑出**名词**候选 | 说明文字里的名词就是类名候选（读者、图书、借阅记录） |
| ② **组织对象** | 把同类对象**抽象成类**，抽出公共属性 | 学生读者/教师读者 → 抽父类"读者" |
| ③ **描述对象间的相互作用** | 谁和谁有往来、什么关系、多重性 | 读者 1 — 1..\* 借阅记录 |
| ④ **基于对象的操作** | 每个对象要提供哪些操作（服务） | 补**方法名**（checkOut、getForCheckOut） |

**记忆口诀**：**认对象 → 组类 → 拉关系 → 定操作**（"认组拉定"）。

### 2.3 OOD 五步 ★★

| 步骤 | 做什么 |
|---|---|
| ① **识别类及对象** | 在分析结果上补足实现层面的类（控制类、边界类、工具类） |
| ② **定义属性** | 每个类需要存哪些数据（书号、书名、定价） |
| ③ **定义服务** | 每个类要对外提供什么方法（借出、归还、计算应还日期） |
| ④ **识别关系** | 泛化/关联/聚合/组合/依赖，以及多重性 |
| ⑤ **识别包** | 把类按职责分组打包，定义包间依赖 |

**反例演示（易错）**：考题问"下列哪一项属于**面向对象设计**而非分析"——判别标准是"**有没有落到实现细节**"。**"认定对象"是分析**（还在业务层挑名词），**"定义属性/服务"是设计**（已经在写类的成员了）。别把"识别类及对象"错认成分析的"认定对象"：前者是实现视角的补全，后者是需求视角的提取。

### 2.4 OOD 七大原则（送分题，也决定"为什么这么设计"）★★

这七条是判断题与案例题"为什么要用设计模式"的**答题依据**——注意它们的共同指向：**都反对"改一处牵动全身"的紧耦合写法**。

| 原则 | 一句话 | 反对什么写法（反例） |
|---|---|---|
| **单一职责**（SRP） | 一个类只负责一件事 | 一个 `BookManager` 既管借还、又管打印报表、又管发短信 |
| **开放-封闭**（OCP） | **对扩展开放、对修改封闭** | 每加一种支付方式就去改 `PaymentService` 里的 `switch` |
| **里氏替换**（LSP） | 子类**可以替换**父类（不破坏父类的约定） | 子类重写后抛异常/收紧前置条件，父类能用的地方用不了 |
| **依赖倒置**（DIP） | 依赖**抽象**，不依赖具体实现；**针对接口编程** | 高层业务类里直接 `new MySQLDao()` |
| **接口隔离**（ISP） | 多个专门接口优于一个总接口 | 一个 20 个方法的 `IAllService`，实现类被迫空实现一堆方法 |
| **组合重用**（CRP） | 尽量用**组合**而不是继承来重用 | 为了复用几个方法就继承一个不相干的类（继承层级爆炸） |
| **迪米特**（LoD，最少知识） | 一个对象对别的对象**知道得越少越好** | `a.getB().getC().getD().doX()` 层层穿透调用 |

**依赖倒置的经典原话**（真题原句）："**抽象不应该依赖于细节，细节应该依赖于抽象**；高层模块不应该依赖低层模块，两者都应该依赖于抽象。"——这句话只要出现，答案就是**依赖倒置原则**。

**里氏替换与多态的关系**：多态能成立，前提正是里氏替换——"父类的地方放子类不出错"。所以 LSP 是**多态的原则性表述**。

### 2.5 包设计原则（低频，认识就够）

另有六条更细的包（package）级原则，考试偶见，**不要与七大原则混记**：

| 原则 | 一句话 |
|---|---|
| 重用发布等价 | 重用的粒度就是发布的粒度 |
| 共同封闭 | 一个变化应只影响一个包内的类，不波及其他包 |
| 共同重用 | 重用了包中一个类，就得重用包中所有类 |
| 无环依赖 | 包的依赖图中**不允许有环** |
| 稳定依赖 | 朝着**稳定**的方向依赖（不稳定的包依赖稳定的包） |
| 稳定抽象 | 包的**抽象程度应与其稳定程度一致**（越稳定越抽象） |

**真题原题形式**："若重用了一个包中的某个类，就要重用该包中的所有类，这属于（ ）原则" → **共同重用原则**。这句题干里的"某个 → 所有"就是它的唯一识别特征。

**应试动作**：七大原则**必须背名字 + 一句话**（选择题直接考原话）；包原则只背"共同重用""共同封闭"两条题眼，其余见过即可。案例题里问"采用什么设计模式更好、为什么"，答题时**顺手引用原则名**（如"符合开放-封闭原则，新增算法无需修改原有代码"）能显著提分。

## 第三节 UML 图 ★★★（案例题必考）

### 3.0 先建全景：UML 2.x 共 13 种图，按"静态/动态"一刀切开

UML 2.x 共定义 **13 种图**，按"静态/动态"一刀切开（其中最常见的 10 种必须全认，末尾三种低频，**认名字即可**）：

| 类别 | 图 | 一句话用途 | 认图特征 |
|---|---|---|---|
| **静态（结构图）** | 类图 | 一组对象、接口、协作及其关系 | 矩形分三格：类名/属性/操作 |
| | 对象图 | 某一时刻的对象快照 | 名字带**下划线** |
| | 构件图（组件图） | 一组构件之间的组织和依赖（静态**实现**视图） | 构件符号（带两个小凸起）+ 供/需接口 |
| | 部署图 | 运行处理**节点**及构件的配置（静态**实施**视图） | **立体长方体**（节点） |
| | 包图 | 类/图如何组织成包及包间依赖 | 文件夹形状 |
| | 组合结构图 | 分解类、构件或用例的**内部结构** | 大框套小框、内部部件 |
| **动态（行为图）** | 用例图 | 用例、参与者及其关系 | 小人（参与者）+ 椭圆（用例） |
| | 顺序图（序列图） | 以**时间顺序**组织的对象间交互 | 竖直生命线 + 水平消息箭头 |
| | 通信图（协作图） | 强调收发消息的对象的**组织结构** | 对象间连线标消息序号 |
| | 状态图 | 一个**状态机**：状态、转换、事件、活动 | 圆角矩形（状态）+ 箭头（转换） |
| | 活动图 | 一个活动到另一个活动的**流程** | 泳道、分叉/汇合粗横线 |
| | 交互概览图 | 组合顺序图与活动图的特征，显示对象如何交互 | 像活动图但节点是交互引用 |
| | 定时图 | 关注对象改变状态时的**时间约束** | 时间刻度、状态阶梯 |

**记忆抓手**：结构图 6 种 = **类、对象、构件、部署、包、组合结构**；行为图 7 种 = **用例、顺序、通信、状态、活动、交互概览、定时**。其中真正高频的是 **10 种（静态五 + 动态五）**——类图、对象图、构件图、部署图、包图、用例图、顺序图、通信图、状态图、活动图。多出的三种（组合结构图、交互概览图、定时图）只会在"UML 图不包括下列哪种"这类题里当干扰项出现。

**反例演示（易错）**：状态图和活动图长得像，区别在——状态图描述**一个对象**因事件引起的状态变迁，必须以"事件"为转换条件；活动图描述**业务流程**步骤，支持并发分支（分叉/汇合），不关心某个对象。另外顺序图 vs 通信图：**内容等价、侧重不同**——顺序图突出时间顺序，通信图突出对象间链接结构，两者可以互相转换（案例题常要求"画出通信图"）。

### 3.1 类图与对象图：三格 + 可见性 + 多重性

**类图的矩形三格**（从上到下）：

```
┌──────────────────────┐
│      类名 Book       │  ← 第 1 格：类名（抽象类用斜体）
├──────────────────────┤
│ - 书号  : String     │  ← 第 2 格：属性    - 私有  + 公有  # 保护
│ - 定价  : double     │
├──────────────────────┤
│ + 借出() : boolean   │  ← 第 3 格：操作（方法）  括号不能省
│ + 计算应还日() : Date│
└──────────────────────┘
```

**可见性符号**（选择题直接问 `-` 是什么意思）：`+` 公有 public、`-` 私有 private、`#` 保护 protected。考场上看到属性前全是一串减号，说明是**私有属性**（这正是封装）。

**多重性（读书数字）vs 基数**：题目常给你一句业务的自然语言，要你翻成符号。**翻法**是"**在每一端，问自己：一个对面对象能对应几个我**"：

| 符号 | 读作 | 业务原话的样子 |
|---|---|---|
| `1` | 恰好一个 | "每本书只属于一个书架" |
| `0..1` | 零个或一个 | "读者可能有一条"欠款记录"，也可能没有" |
| `1..*` | 一个或多个（**至少一个**） | "一名读者至少有一条借阅记录" |
| `0..*` 或 `*` | 零个或多个（**可以没有**） | "一个书架可以没有任何图书" |

**反例演示（易错）**：`1..*` 与 `0..*` 只差一个数字，含义却相反。判断口诀——**看"至少"这个词**：题干出现"至少有/必须有"→ 端点写 `1..*`；出现"可以没有/可能没有/不一定有"→ 写 `0..*`。这里最容易把手写答案画反，因为**同一句话的两端各有一个多重性**：如"读者可借多本书"，在**图书端**要写的不是"多"而是"1"（一本书只被一条借阅记录指向一个读者），在**读者端**才写 `0..*`。**逐端问、别照抄句子**。

**对象图**：类图是"模板"，对象图是"**某一时刻的快照**"。识别特征就是**名字带下划线、冒号前是对象名、冒号后是类名**，写成 `:图书` 或 `b1 : 图书`。

### 3.2 用例图：三个要素 + 三种关系 + 建模流程四步 ★★

**要素**：**参与者**（小人，缩写可以是人、外部系统）、**用例**（椭圆，一件完整的、有业务价值的事）、**关系**（连线）。

**三种关系**（选择题 + 案例题双考）：

| 关系 | 符号 | 判据 | 例 |
|---|---|---|---|
| **包含** `<<include>>` | 虚线箭头 + 构造型，**基用例 → 被包含用例** | **必经**、可被多个用例共用的公共行为 | 借书**必须先**登录；借书/还书/查询**都要**检查权限 |
| **扩展** `<<extend>>` | 虚线箭头 + 构造型，**扩展用例 → 基用例** | **可选**、条件触发、是基用例的分支场景 | 超额时**才**弹逾期提示；勾选定时发布**才**执行 |
| **泛化** | 空心三角实线，**子用例 → 父用例** | 多个用例有**共同的类似结构和行为**，抽出父用例 | 网上注册/电话注册 → 泛化到"课程注册" |

**方向易错**：include 是**基用例指出去**（借书 → 登录）；extend 是**扩展用例指回来**（拒绝提示 → 借书）。口诀：**include 从主干指出，extend 从分支指回**；判断只用一句话——**"没有它这事就干不成"是 include，"有它也行没它也行"是 extend**。

**用例建模流程（四步，其中前三步必须、第四步可选）**：

1. **识别参与者**（必须）—— 谁使用系统、系统服务谁；
2. **合并需求获得用例**（必须）—— 把每个参与者要做的事收成用例；
3. **细化用例描述**（必须）—— 写"典型事件流 + 备选事件流"；
4. **调整用例模型**（可选）—— 抽 include/extend/泛化，简化模型。

**案例题怎么用这四步**：真题给的"用例详细描述"就是第 3 步的产物，**结构固定为——参与者 / 典型事件流（正常步骤 1、2、3…）/ 备选事件流（2a、4a 这类"异常分支"）**。读题时把**典型事件流的步骤**当主线索（对应顺序图的消息顺序），把**编号带字母的备选事件流**当 **extend 的来源**（如"4a 读者要借的书无法外借"→ 扩展用例）。

**反例演示（易错）**："参与者"里可以有**外部系统**（如"支付网关""短信平台"），不一定是人；反过来，"系统内部的某个模块"**不能**当参与者——参与者必须**在系统边界之外**。这是选择题的常见陷阱：给你"数据库""登录模块"当选项，它们都是系统内部的东西，不是参与者。

### 3.3 顺序图与通信图：同一件事的两种画法

**顺序图要素**（从图上一眼能指出来）：**对象**（顶部方框）、**生命线**（对象下方的竖直虚线）、**激活/控制焦点**（生命线上叠的窄长条，表示对象正在执行）、**消息**（水平箭头）、**返回消息**（**虚线**箭头，表示把结果交回）。

**消息方向与种类**：

| 消息 | 画法 | 含义 |
|---|---|---|
| 同步消息 | **实线 + 实心箭头** | 发送者**等**对方处理完（普通方法调用） |
| 异步消息 | 实线 + 空心箭头 | 发送者**不等**（发完就走） |
| 返回消息 | **虚线 + 箭头** | 把结果回传给调用者 |

**一条最重要的判图规律**：**从左边第一个对象开始，箭头指向谁，就是谁在干活**；消息自左向右排序，**上下位置 = 时间先后**——所以案例题让你"按说明填消息"，就是**照典型事件流的步骤顺序往右下方排**。

**通信图（协作图）**：同样的交互内容，但**画法完全不同**——对象是**网络式**散布的，消息写在**对象之间的连线上**并用**序号**标注调用层次：

```
        :Patron
           │  2: isFaculty()
           │
 1: checkOut(bookID)      :CheckoutSessionController
           │  3: find(bookID)
           ▼
        :Book  ──── 4: recordBookLoan() ───▶ :Catalog
```

序号里的点表示**嵌套层级**（`1.1` 是 `1` 内部调用的第一句，`1.1.2` 再深一层）。**顺序图 vs 通信图对照**：两者**语义等价、可以互相转换**；顺序图突出**时间顺序**，通信图突出**对象间的链接结构与调用层次**。

**反例演示（易错）**：判断"哪张是顺序图"不要只看有没有箭头——**定音锤是"有没有生命线（竖直虚线）"**：有竖直生命线、消息横着排的是顺序图；对象用连线连成网状、序号写在线上的是通信图。

### 3.4 活动图：流程 + 并发 + 泳道

**要素**：初始节点（**实心圆**）、结束节点（**带圈的实心圆**）、**动作/活动**（圆角矩形）、**分支与监护表达式**（菱形 + `[条件]`）、**分叉与汇合**（**粗横线**，表示并发）、**泳道**（按责任人划分的纵向区域）。

```
        ●                ← 初始节点
        │
   ┌────▼────┐
   │ 接收订单 │            ← 动作
   └────┬────┘
   ═════╪═════             ← 分叉（粗横线）：下面两条并发
   │         │
┌──▼──┐  ┌──▼──┐
│填订单│  │开发票│          两条同时进行
└──┬──┘  └──┬──┘
   ═════╪═════             ← 汇合（粗横线）：都做完才往下
        │
   ┌────▼────┐
   │  ◇ [未完成] │           ← 分支（菱形）+ 监护表达式
   └────┬────┘
        ▼
        ◉                ← 结束节点
```

**与流程图的区别**（选择题常问）：活动图**支持并发**（分叉/汇合），流程图只有顺序和分支；活动图还能用**泳道**表达"谁负责哪一段"。

**反例演示（易错）**：**分叉（fork）和分支（decision）都画两条出路，但含义相反**——**分支**是"**二选一**，只走一条"（菱形，路上标条件）；**分叉**是"**两条都要走，并发执行**"（粗横线）。看符号不看箭头数量：**菱形 = 选一条，粗横线 = 全走并同时走**。

### 3.5 状态图：五要素 + 四类事件 + 组合状态 ★★

状态图是"**单个对象的生命史**"：它在这辈子经历过哪些状态、因为什么事件而切换。**五要素必须背齐**：

| 要素 | 是什么 | 画法/写法 |
|---|---|---|
| **状态** | 对象所处的情形 | 圆角矩形，写状态名（空闲/占线/已锁定） |
| **事件** | 触发状态迁移的事情 | 转换线**上方**写事件名 |
| **监护条件** | 事件发生还不够，还要满足的条件 | 方括号写在事件后：`turnOn[有水]` |
| **动作** | 迁移时执行的一句话 | 斜线后写：`turnOn[有水]/烧水` |
| **转换（转移）** | 状态之间的那条箭头 | 箭头从源状态指向目标状态 |

**一条完整转换的读法**（把上面四样串起来）：

```
  空闲 ──── turnOn[有水]/烧水 ────▶ 加热中
  ↑源状态      ↑事件 ↑监护条件 ↑动作        ↑目标状态
```

**结构规律（选择题原话）**：一个状态图**只能有一个初态**（实心圆），但**可以有一个或多个终态**（带圈实心圆），**也可以没有终态**（比如一个永远循环的系统）。

**四类事件（问"下面属于哪种事件"）**：

| 事件类型 | 含义 | 例子 |
|---|---|---|
| **信号事件** | 对象之间**发送/接收信号**实现通信 | 鼠标点击、外部中断 |
| **调用事件** | 一个对象**请求调用**另一个对象的操作 | 方法调用 |
| **变换事件** | **when + 布尔表达式**，条件由假变真即触发 | `when(温度>100)` |
| **时间事件** | 到达某时刻或经过某段时间，用 **when / after** | `after(5秒)`、`when(日期=10月24日)` |

**状态内部的五个组成部分**（了解即可）：状态名、**entry/exit 动作**（进入/退出该状态要做的事）、**内部转移**（`event/action`，不跳出本状态）、**子状态**、**延迟事件**（`defer`，事件先记下、等以后处理）。

```
   ┌──────────── Flashlight ────────────┐
   │ entry/开灯      do/闪烁五次         │   ← 进入即开灯、在状态内持续闪烁
   │ exit/关灯       selfTest/defer      │   ← 退出即关灯；selfTest 事件先延迟
   └────────────────────────────────────┘
```

**组合状态**：一个状态内部还装着子状态，分两种，**这是易混点**：

- **顺序子状态**：子状态之间**互斥**（同一时刻只能在一个），要**全部完成**整体才算完成（像是"一串流程分几步"）；
- **并发子状态**：某时刻**可以同时达到多个**子状态，内部**并发进行**。

**反例演示（易错）**：题干说"进入该状态后，可以同时进行 A、B 两件事"→ **并发子状态**；说"先做 A、做完再做 B，两步都完成状态才结束"→ **顺序子状态**。判别只看一个字：**"同时"还是"先后"**。

### 3.6 构件图：一眼认出供接口和需接口 ★

构件图（组件图）专注于**静态实现视图**——把系统拆成可替换的软件构件，画清它们之间谁依赖谁。

**构件符号**：矩形 + 左上角画两个小矩形凸起（像插头），框内写 `<<component>>`。

**接口的画法（高频识别题，必须记住）**：

| 接口 | 符号 | 记忆法 |
|---|---|---|
| **供接口**（provided，我对外提供的服务） | **整圆**（画成一个完整的圆圈） | 我**给出去**的是完整的；圆是**满**的 |
| **需接口**（required，我需要别人提供的服务） | **半圆**（缺了一块的半圆弧） | 我**要往里接**的是缺口；半圆是**缺**的 |

**口诀**：**整圆供、半圆需**（或"**满的给别人、缺的找别人要**"）。

**反例演示（易错）**：依赖箭头从**需接口**指向**供接口**（谁需要谁 → 指向被依赖方），别画反——画反了会变成"提供方依赖使用方"，逻辑颠倒。构件之间的虚线箭头表示**依赖关系**（一个构件的实现离不开另一个）。

### 3.7 部署图：节点是立体长方体

部署图给的是**体系结构的静态实施视图**——软件构件**跑在哪些物理节点上**。

**要素**：

| 要素 | 画法 |
|---|---|
| **节点**（node） | **立体长方体**（3D 立方体），表示硬件设备/运行环境，如应用服务器、数据库服务器、PC、手机 |
| **构件** | 节点框内放构件符号（表示这台机器上部署了什么） |
| **连接** | 节点之间的实线，可标协议（`TCP/IP`）或构造型（`<<Database>>`、`<<Storage>>`） |

**识别特征**：图上一旦出现**立体长方体（有厚度、有顶面和侧面）**，就是部署图——这是它和构件图最容易区分的地方（构件图是平的、带两个小凸起；部署图是立体的）。

### 3.8 UML 全图小结与应试动作

**"给场景选图"速判表**（案例题和选择题都用得上）：

| 题目在说什么 | 该用哪张图 |
|---|---|
| 系统有哪些功能、谁能用 | **用例图** |
| 类的属性、操作、类间关系 | **类图** |
| 某一时刻的对象快照 | **对象图** |
| 按时间顺序的对象交互 | **顺序图** |
| 强调对象链接结构与调用层次的交互 | **通信图** |
| **单个对象**因事件而状态变迁 | **状态图** |
| 业务流程步骤、有并发/责任人划分 | **活动图** |
| 软件拆成哪些可替换构件、接口供需 | **构件图** |
| 软件跑在哪些硬件节点上 | **部署图** |
| 类如何分组打包、包间依赖 | **包图** |

**应试动作**：
1. **背分类**：结构图 6 种、行为图 7 种（至少记住高频 10 种的归属）；
2. **认符号**：三角 = 泛化/实现（虚线是接口实现）、菱形 = 整体部分（空心聚合 / 实心组合）、虚线 = 弱关系（依赖最弱）、**整圆供/半圆需**、**立体长方体 = 部署节点**、**下划线 = 对象**；
3. **判用例关系**：必经 include（主干指出）、可选 extend（分支指回）；
4. **状态图五要素**与**四类事件**要能默写（简答题和填空都可能要）。

## 第四节 设计模式 ★★★（每年 2–4 题）

### 4.1 23 种模式的分类框架（先背骨架）

模式按**目的**分三类——这本身就回答了"为什么有 23 种"：**创建型**管"对象怎么造出来"（5 种）、**结构型**管"对象怎么组装起来"（7 种）、**行为型**管"对象怎么交互分工"（11 种）。

口诀（自编，按序号背）：
- 创建型 5：**单原工抽建**（单例、原型、工厂方法、抽象工厂、构建器）
- 结构型 7：**适桥组外装享代**（适配器、桥接、组合、外观、装饰器、享元、代理）
- 行为型 11：**责命解迭中，备观状策模访**（职责链、命令、解释器、迭代器、中介者、备忘录、观察者、状态、策略、模板方法、访问者）

**数量口诀**：**5 / 7 / 11**（连着念"五七十一"）。考题问"下列属于创建型的有几个"，先数出 5 个就够了，不必逐个回忆意图。

**另一种分类维度（算考点，别忽略）**：按**作用范围**分**类模式**与**对象模式**——**类模式只有 4 个**：**工厂方法、适配器（类）、模板方法、解释器**；其余 19 个都是**对象模式**（适配器两种都算：既可用类继承实现，也可用对象组合实现，所以两边都列它）。**记住"类模式 = 4 个"这个数**比记名字更实用：看到"下列属于类模式的是"，先在心里数出这 4 个。

### 4.2 23 种意图速查表（背"意图一句话 + 速记词"）

**创建型（管出生）**：

| 模式 | 意图一句话 | 速记词 |
|---|---|---|
| Singleton 单例 | 保证一个类**只有一个实例**，提供全局访问点 | 唯一实例 |
| Prototype 原型 | 通过**拷贝**原型来创建新对象 | 克隆 |
| Factory Method 工厂方法 | 定义创建对象的接口，**由子类决定**实例化哪个类 | 动态生产对象 |
| Abstract Factory 抽象工厂 | 创建**一系列相关对象**，无需指定具体类 | 成系列生产 |
| Builder 构建器 | 复杂对象的**构建过程与表示分离**，分步构造 | 分步组装 |

**结构型（管组装）**：

| 模式 | 意图一句话 | 速记词 |
|---|---|---|
| Adapter 适配器 | **转换接口**，使原本不兼容的类协同工作 | 转换接口 |
| Bridge 桥接 | 把**抽象与实现分离**（两个维度），使它们独立变化 | 继承树拆两维 |
| Composite 组合 | 把对象组成**树形结构**表示"整体—部分"，单个和组合对象使用一致 | 树形目录 |
| Facade 外观 | 给复杂子系统提供一个**统一的高层接口** | 统一窗口 |
| Decorator 装饰器 | **动态地给对象附加职责**，比继承灵活 | 附加职责 |
| Flyweight 享元 | **共享**大量细粒度对象，节省内存 | 共享细粒度 |
| Proxy 代理 | 为对象提供一个**替身**以控制对它的访问 | 间接访问 |

**行为型（管交互）**：

| 模式 | 意图一句话 | 速记词 |
|---|---|---|
| Chain of Responsibility 职责链 | 请求沿处理者**链条传递**，直到被处理 | 传递职责 |
| Command 命令 | 把请求封装成对象，支持**撤销、日志、排队** | 请求变对象 |
| Interpreter 解释器 | 给定语言文法，用解释器**解释句子** | 解释语言 |
| Iterator 迭代器 | 顺序访问聚合元素而**不暴露内部表示** | 逐个访问 |
| Mediator 中介者 | 封装对象间交互，各对象**不必显式互相引用** | 中介转达 |
| Memento 备忘录 | 保存对象状态，需要时**恢复** | 存档恢复 |
| Observer 观察者 | 一对多依赖，状态变化时**通知所有依赖者** | 订阅—通知 |
| State 状态 | 对象在**状态改变时改变行为** | 状态变行为变 |
| Strategy 策略 | 封装一系列**算法**，使它们可**互相替换** | 算法可换 |
| Template Method 模板方法 | 父类定**算法骨架**，某些步骤延迟到子类 | 骨架在父类 |
| Visitor 访问者 | 不改动类的前提下给类**添加新操作** | 外加操作 |

### 4.3 高频 8 种：用生活场景锁死（单例、工厂方法、观察者、策略、适配器、装饰器、代理、桥接）

| 模式 | 场景联想 | 认题特征词 |
|---|---|---|
| 单例 | 系统配置管理器、连接池、打印管理器 | "全局唯一""只能有一个" |
| 工厂方法 | 日志工厂按配置决定生成文件日志还是数据库日志 | "子类决定创建哪种对象" |
| 观察者 | 微信公众号更新，所有粉丝收到推送；事件监听器 | "一对多""通知""订阅" |
| 策略 | 排序算法可换（快排/归并）、支付方式可换（微信/支付宝） | "算法可互换""封装算法族" |
| 适配器 | 国标插头转美标插座；老系统接口包装成新接口 | "接口不兼容""转换" |
| 装饰器 | 给咖啡动态加奶、加糖（不加子类爆炸）；Java IO 流包装 | "动态添加职责" |
| 代理 | 房产中介带看房（控制访问）、图片懒加载、远程调用桩 | "控制访问""延迟/远程/安全" |
| 桥接 | 形状（圆/方）× 颜色（红/蓝）两个维度独立扩展，不用 2×2 个子类 | "两个变化维度""抽象与实现分离" |

**代理的三种细分（选择题出现过）**：**远程代理**（为不同地址空间的对象提供本地代表，负责编码请求）、**虚拟代理**（缓存信息，**延迟**创建开销大的对象，如图片懒加载）、**保护代理**（检查调用者**权限**）。看到"权限/延迟/远程"三个字眼，就归到代理的对应细分里。

### 4.4 模式的角色名（案例题第五题 Java/C++ 填空的命门）★★

案例题第五题常给一段 Java/C++ 代码 + 一张类图让你填空，**填的就是角色名**（如 `interface Observer`、`class Subject`）。所以高频模式的**角色名必须能中英对照写出来**。下面按三分类分组列出，箭头 `→` 表示"抽象到具体"，斜杠 `/` 表示并列角色：

**创建型（5）**

- **抽象工厂**：`AbstractFactory`（抽象工厂，声明创建产品的抽象方法）→ `ConcreteFactory`（具体工厂，实现方法并生成具体产品）；`AbstractProduct`（抽象产品，为一种产品声明接口）→ `Product`（具体产品）；`Client`（客户，用抽象产品与抽象工厂生成对象）。
- **工厂方法**：`Product`（产品接口）→ `ConcreteProduct`（真实产品）；`Creator`（工厂角色，声明工厂方法）→ `ConcreteCreator`（真实工厂，返回产品实例）。
- **原型**：`Prototype`（抽象原型，定义克隆自己的接口）→ `ConcretePrototype`（实现 clone、返回自身拷贝）；`Client` 调 `p = prototype.clone()`。
- **单例**：`Singleton` 自己——**私有的静态唯一实例变量** + **公有的静态获取方法**（`getInstance()`），构造方法私有化。
- **构建器**：`Builder`（抽象建造者，为各部件指定抽象接口）→ `ConcreteBuilder`（具体建造者）；`Director`（指挥者，按步骤指挥建造）；`Product`（被构建的复杂对象）。

**结构型（7）**

- **适配器**：`Target`（目标抽象类，客户要用的标准接口）；`Adapter`（适配器，调另一个接口做转换）；`Adaptee`（被适配者，需要接入的实际接口）；`Client`。
- **桥接**：`Abstraction`（抽象类，维护一个 Implementor 引用）→ `RefinedAbstraction`（扩充的抽象类）；`Implementor`（实现类接口，只给基本操作）→ `ConcreteImplementor`（具体实现类）。
- **组合**：`Component`（成员父类，统一接口含 Add/Remove/GetChild）→ `Leaf`（叶子，无子节点）／ `Composite`（组合类，持子部件列表并**递归调用**）。
- **装饰器**：`Component`（部件接口）→ `ConcreteComponent`（被装饰者）；`Decorator`（装饰抽象类，**持有一个 Component**，接口与之一致）→ `ConcreteDecorator`（加具体职责，内部调 `super.operation()`）。
- **外观**：`Facade`（外形类，知道哪些子系统负责哪些请求，把客户请求转给相应子系统）；`Subsystem`（子系统类，实现功能，**不知道也不引用 Facade**）。
- **享元**：`Flyweight`（抽象享元，接受**外部状态**）→ `ConcreteFlyweight`（含**内部状态**）／ `UnsharedConcreteFlyweight`（不共享的具体享元）；`FlyweightFactory`（轻量级工厂，按 key 从池中取或新建）。
- **代理**：`Subject`（抽象实体接口，为 RealSubject 与 Proxy 定义相同的接口）→ `RealSubject`（真实对象）／ `Proxy`（代理，**持有 RealSubject 引用**，控制访问）。

**行为型（11）**

- **职责链**：`Handler`（传递者接口，**持有后继者引用**）→ `ConcreteHandler`（能处理就处理，否则**转发给后继**）；`Client`。
- **命令**：`Command`（抽象命令，声明执行接口）→ `ConcreteCommand`（**把接收者与动作绑定**）；`Invoker`（调用者，触发 `execute`）；`Receiver`（接收者，知道如何执行关联请求）；`Client`。
- **解释器**：`AbstractExpression`（抽象表达式，定义 `Interpret(Context)`）→ `TerminalExpression`（终结符表达式，每个终结符一个实例）／ `NonTerminalExpression`（非终结符表达式）；`Context`（场景，含解释器的全局信息）。
- **迭代器**：`Iterator`（First/Next/CurrentItem/IsDone）→ `ConcreteIterator`（遍历时跟踪聚合中的当前位置）；`Aggregate`（定义创建迭代器的接口）→ `ConcreteAggregate`。
- **中介者**：`Mediator`（抽象中介者，定义同事间通信的统一接口）→ `ConcreteMediator`（**掌握并维护各同事对象的引用**）；`Colleague`（同事类，与别的同事通信**必经中介者**）。
- **备忘录**：`Memento`（备忘录，保存原发器在某一时刻的状态）；`Originator`（原发器，创建备忘录并可**用它恢复自己**）；`Caretaker`（管理者，负责保存备忘录）。
- **观察者**：`Subject`（被观察对象，提供绑定/分离观察者的接口）→ `ConcreteSubject`（具体被观察对象，状态改变时通知）；`Observer`（定义更新接口）→ `ConcreteObserver`（持 ConcreteSubject 引用）。
- **状态**：`Context`（情景类，持有具体状态实例，把请求**委托给状态**）；`State`（抽象状态，封装与某状态相关的行为）→ `ConcreteState`（具体状态类）。
- **策略**：`Strategy`（抽象策略，定义所有策略的公共接口）→ `ConcreteStrategy`（封装具体算法）；`Context`（上下文，持有 Strategy 引用）；`Client`。
- **模板方法**：`AbstractClass`（抽象类，定义**算法骨架**并声明若干基本方法）／ `ConcreteClass`（子类实现某些步骤）。
- **访问者**：`Visitor`（为每个 ConcreteElement 声明一个 Visit 操作）→ `ConcreteVisitor`；`Element`（定义 `Accept(Visitor)`）→ `ConcreteElement`；`ObjectStructure`（对象结构类，遍历元素）。

**背法建议**：不要死背这一长串，而是**抓三个"通用套路"**——① **抽象 + 具体**成对出现（抽象工厂/具体工厂、抽象产品/具体产品）；② **谁持有谁**决定控制权（代理持 RealSubject、装饰器持 Component、状态持 State、职责链持 successor、上下文持 State、组合持子部件列表）；③ **客户只认抽象**（Client 永远通过抽象接口打交道，这就是依赖倒置原则在模式里的落地）。考场上即使记不住确切名字，**按"抽象 X / 具体 X / 客户"的命名规律写，往往也能得分**。

### 4.5 易混组对照（案例题给理由时用得上）

1. **装饰器 vs 代理**：都包一层对象，区别在**意图**——装饰器给对象**加功能**（层层包出不同组合），代理是**控制访问**（功能不变，管你能不能/何时访问）。
2. **适配器 vs 外观**：适配器是"一个接口转成另一个接口"（一对一改造）；外观是"一堆子系统接口收敛成一个入口"（多合一简化）。
3. **桥接 vs 装饰器**：桥接拆的是**两个独立变化的结构维度**（形状×绘制方式）；装饰器是**同一维度上叠加功能**。
4. **策略 vs 状态**：结构几乎一样（都委托给一个接口），但**客户能不能选**是分水岭——策略是**客户主动选算法**（想换就换）；状态是**对象自己随条件转换**，客户通常不指定（且状态之间常互相触发迁移）。
5. **命令 vs 备忘录**（撤销题的正主）**：支持"撤销"的机制是**命令**（把操作封装成对象，命令里存了执行所需的信息，提供 `undo()`）；备忘录是**保存/恢复对象状态快照**。若题目问"把请求封装成对象从而支持撤销/排队/日志"→ **命令**；问"保存对象某一时刻的状态以便以后恢复"→ **备忘录**。真题里两者常同框出现，**看题干强调的是"操作"还是"状态"**。
6. **工厂方法 vs 抽象工厂**：都造对象，区别在**单一还是系列**——工厂方法造**一个产品**（由子类决定），抽象工厂造**一整个产品族**（一族相关对象，如"Windows 风格的按钮+滚动条"）。

**应试动作**：① 背三分类数字"5/7/11" + 口诀；② 速查表每个模式的"速记词"必须条件反射——考试 80% 是"场景/意图 → 模式名"的配对；③ 易混对按"意图"区分；④ **高频模式的角色名要能默写英文**（服务案例题填空）。

## 第五节 案例题专攻：UML 建模（约 15 分）

案例题的形态固定为「**文字说明 + 挖空的图（用例图/类图/顺序图/通信图/活动图/状态图之一）**」，常配 3 个小问。三个固定套路如下。

### 套路一：补用例图——参与者、用例、include/extend

1. **参与者**：名词且"谁在使用系统/系统服务谁"（读者、管理员、外部系统如支付网关）；
2. **用例**：系统为参与者完成的一件完整的事（动词短语：借书、还书、缴费）；
3. **挖空补关系**：句子里"必须先/一定要"→ include；"如果…就/可选"→ extend；两种"某类参与者…"→ 用例泛化。

**从"用例详细描述"里挖答案**（近真题的新形态）：题目给的往往是一段标准格式的描述——**参与者 / 典型事件流（1、2、3…）/ 备选事件流（2a、4a…）**。读法三条：
- **参与者**直接抄（原文写了"参与者：读者"）；
- **典型事件流的每一步**对应顺序图/通信图里的一条消息，**步骤序号 = 消息顺序**；
- **备选事件流 → extend 的来源**（如"4a 读者要借的书无法外借 → 告知本书无法借阅"就是"告知无法借阅"这个扩展用例）。

### 套路二：补类图——名词变类、关系按语义套，方法按事件流找

1. **类名**：说明中的**核心名词**（读者、图书、借阅记录）——注意填空题要求"**用图中给出的英文词汇**"，所以要把中文名词与英文类名对应上（读者 = Patron、图书 = Book、目录 = Catalog）；
2. **属性**：说明里"要记录的信息"（书号、书名、定价）；
3. **方法（补 M1、M2…）**：**从事件流的动词里找**，且**要匹配调用者与接收者**——如"根据图书目录中的图书ID确认该书可以借阅"这一步，主语是目录对象 → 方法就是目录提供的 `find(bookID)`／`getForCheckOut(id)`；"判断读者身份"→ 读者对象的 `isFaculty()`；
4. **多重性**：按 3.1 的"**逐端问**"法填写；
5. **关联类**：多对多时中间挂**关联类**（学生—课程之间挂"选课记录"——与第 2 课 m:n 转关系模式同构）。

**判"哪个方法属于哪个类"的通用办法**：看**动作的宾语归谁管**——"查书"问的是图书/目录 → 方法落在这两个类上；"生成借阅记录"要落到借阅记录或会话控制类上；"通知读者应还日期"落到读者或通知类上。

### 套路三：补顺序图/通信图/状态图/活动图——按说明的顺序与事件照搬

1. **顺序图挖消息**：按说明句子的**先后顺序**填消息名（从上到下 = 时间先后），注意返回消息（虚线箭头）也要填；
2. **通信图挖序号**：序号体现调用层次（`1`、`1.1`、`1.1.2`），**先定第一个调用，再补嵌套**；
3. **状态图挖状态/事件**：状态 = 名词（空闲/占线），转换线上标**事件**（题干会说"当…时进入…"）；起点实心圆、终点带圈圆；
4. **活动图挖动作/条件**：动作 = 动词短语，菱形出口标**监护表达式**（题干会说"如果…则…否则…"）。

### 套路四：设计模式小问（"可以采用何种设计模式？简要说明原因"）

这是 **3 分题**，答题**必须两段：模式名 + 原因**（只写名字通常拿不满）。原因要**用题目原话 + 原则名**，模板如下：

> 可以采用**策略（Strategy）模式**。理由：题库中的规则（制度）会不断扩充和调整，属于**一族可互相替换的算法**；采用策略模式把每种规则封装成独立的策略类，由上下文按需注入，**新增规则时只需增加新的策略类，不必修改原有代码**，符合**开放-封闭原则**。

**识别抓手（题干 → 模式）**：

| 题干出现 | 答案模式 |
|---|---|
| "可灵活扩充/调整的一系列规则、算法，可互相替换" | **策略** |
| "状态改变时通知所有相关对象/订阅者" | **观察者** |
| "创建过程复杂、分步骤，且表示可不同" | **构建器** |
| "系统只能有一个××（如全局配置、唯一编号生成器）" | **单例** |
| "要接入已有接口不兼容的第三方/旧系统" | **适配器** |
| "需要在不修改类的前提下增加新操作" | **访问者** |
| "对象行为随自身状态变化而变化" | **状态** |
| "需要支持撤销/重做、操作排队" | **命令** |
| "多步骤处理，每个处理者只处理自己管的部分，其余往下传" | **职责链** |

**应试动作**：这一问**先写模式名再写理由**，理由必含「**新增/变化时只需加新类、不必改原有代码**」这类功能点，并**点名原则**（开放-封闭 / 依赖倒置 / 单一职责）。给分点是**关键词**，不是文采。

8. 【模式角色】某 Java 程序中有如下骨架：

```java
abstract class Subject {
    private List<Observer> obs = new ArrayList<>();
    void attach(Observer o) { obs.add(o); }
    void detach(Observer o) { obs.remove(o); }
    void notifyObservers() { for (Observer o : obs) o.update(); }
}
class Clock extends Subject { /* 时间变化时调用 notifyObservers() */ }
interface Observer { void update(); }
class DigitalClock implements Observer { public void update() { /* 刷新显示 */ } }
```

指出这是哪种设计模式，并说明 `Subject`、`Clock`、`Observer`、`DigitalClock` 各对应模式中的哪个角色。

## 答案与解析

### 课后考题答案

**1. C**
封装 = 数据 + 操作捆绑、隐藏实现。继承是获得父类特征；多态是同一消息不同响应；重载是同名不同参的方法。

**2. B**
重载 = 同类中方法名同、**参数列表不同**、编译期绑定；重写 = 子类同签名覆盖父类方法、运行期绑定。A 把两者的特征说反了；D 错——参数不同就不叫重写了。

**3. B**
运行期按**实际对象类型**绑定 → 执行子类版本，这正是多态。C 错在那是重载的绑定方式（编译期看参数）。

**4. C**
静态（结构）图：类图、对象图、构件图、部署图、包图（+组合结构图）；状态图、活动图、顺序图、用例图都是动态（行为）图。部署图虽然画的是物理节点，但描述的是**结构**归属 → 静态。

**5. B**
鸟与翅膀**同生共死**（翅膀不能离开鸟独立存在）→ 组合 = 实心菱形。雁群与雁这种"散了还能活"才是空心菱形（聚合）。

**6. B**
"必须先执行"→ include（包含）。extend 是可选/条件触发；泛化是同类用例的一般化。

**7. A**
同步消息实线实心箭头（发送者停下等返回）；返回用虚线箭头。粗横线是活动图的分叉/汇合，小人是参与者（用例图）。

**8. C**
结构型 7 种：适配器、桥接、组合、外观、装饰器、享元、代理 → 装饰器在其中。策略、命令属行为型，单例属创建型。

**9. B**
"请求封装成对象 + 撤销/日志/排队" = 命令模式速记词。备忘录是"存档恢复状态"，职责链是"沿链传递直到处理"。

**10. A**
"树形 + 整体部分 + 使用一致" = 组合模式。桥接是抽象与实现两维分离；享元是共享细粒度对象。

**11. C**
"一对多依赖 + 状态变化通知" = 观察者速记词。中介者是"通过中介交互、不显式引用"；状态是"状态变行为变"。

**12. A**
"转换接口、使不兼容类协同" = 适配器。代理是控制访问不加接口转换；装饰器加职责不转接口。

**13. B**
"动态附加职责" = 装饰器速记词。代理意图是控制访问。

**14. C**
"算法可运行时切换" = 策略模式。模板方法是骨架在父类步骤留子类（结构固定）；状态是状态驱动的行为变化（不由客户随意切换算法）。

**15. A**
"仅一个实例 + 全局访问点" = 单例速记词。

**16. B**
参数多态即**泛型**（类型参数化），是应用最广泛、最"纯"的多态——同一份代码通过类型参数适配多种类型。过载多态就是重载；包含多态靠继承（子类替换父类）；强制多态靠编译器隐式类型转换（`int` 自动转 `double`）。

**17. C**
控制类描述业务逻辑、控制活动流、充当实体类与边界类之间的协调者，命名上常见 Controller / Manager / Session。实体类属性多、边界类方法多。

**18. B**
**整圆 = 供接口**（对外提供的服务），**半圆 = 需接口**（需要别人提供的服务）。口诀"满的给别人、缺的找别人要"。C、D 是类图里的泛化与聚合符号，与接口无关。

**19. B**
状态图**只有一个初态**（实心圆），终态可以有多个、也可以没有（A 错、B 对）；监护条件是可选的——只写事件不写条件也合法（C 错）；描述**多个对象之间的交互**是顺序图/通信图的事（D 错）。

**20. C**
这句话是**依赖倒置原则**的经典表述，核心是"针对接口编程，不要针对实现编程"。里氏替换讲的是"子类能替换父类"；单一职责讲"一个类只干一件事"；接口隔离讲"多个专门接口优于一个总接口"。

**21. C**
Observer（抽象观察者）的职责就是**定义一个更新接口**，在被观察对象改变时被通知；ConcreteObserver 是它的具体实现。Subject/ConcreteSubject 属于"被观察"的一方（通知者），不是"接受通知"的一方。

**22. D**
动态绑定的三个必要条件是：① 有继承关系；② 发生了重写；③ 父类引用指向子类对象。**静态方法（以及 final、private 方法）不参与动态绑定**——它在编译期就确定了，属于"破坏条件"的因素，不是必要条件之一。

### 案例题答案（第一道：类分类 + 模式 + 图选型）

**问题 1**：
- **实体类**：Reader、Book、Catalog、LoanRecord。识别特征：表示现实世界真实存在的实体，需要保存大量数据，**属性多、方法少**（Catalog 虽然只看到 `find` 一个方法，但它是"图书目录"这一实体数据的集合，仍按"存数据"归实体类）；
- **边界类**：BorrowUI。识别特征：为用户提供与系统交互的方式（界面、外部接口），**方法多、属性少**；
- **控制类**：BorrowController。识别特征：描述业务逻辑、控制活动流，充当实体类与边界类之间的协调者（命名常带 Controller / Manager / Session）。

**问题 2**：**策略（Strategy）模式**。
理由：借阅规则会不断扩充、并且需要按实际运行情况调整启用哪些规则，说明这是一族**可互相替换的算法**。用策略模式把每条规则封装成独立的策略类，由上下文（BorrowController）按配置注入其一；**新增或调整规则时只需增加/更换策略类，不必修改原有代码**，符合**开放-封闭原则**（也体现了依赖倒置——业务代码依赖"规则"抽象而非具体规则）。

**问题 3**：应采用**顺序图（序列图）**。
关系：顺序图与通信图**语义等价、可以互相转换**，描述的是同一份交互内容，区别在侧重——顺序图突出**时间顺序**（每个对象一条生命线，消息自上而下排列），通信图突出**对象之间的链接结构与调用层次**（对象连成网状，消息标序号如 `1.1`、`1.1.2`）。

### 案例题答案（第二道：用例关系 + 类图 + 模式）

**问题 1**：
- "借书" → "登录"：**`<<include>>`（包含）**——说明中"使用系统前必须先完成身份登录"，登录是借书的必经步骤，基用例（借书）指向被包含用例（登录）。
- "拒绝提示" → "借书"：**`<<extend>>`（扩展）**——说明中"若读者存在逾期未还记录，系统给出拒绝提示（没有逾期则不会有）"，是条件触发的可选行为，扩展用例（拒绝提示）指向基用例（借书）。

**问题 2**：
```
读者 1 ── 1..* 借阅记录          图书 1 ── 1..* 借阅记录
```
- 读者—借阅记录：1 : 1..* 的关联（一名读者可有多条记录，每条记录只属于一名读者）；
- 图书—借阅记录：1 : 1..* 的关联（一本书可对应多条借阅记录，每条记录只涉及一本书）；
- 借阅记录是关联类：它把"读者"和"图书"的多对多借还关系落到具体记录上（与第 2 课 m:n 转关系模式同构）。
- 若增加"读者分为学生读者和教师读者"：增加"读者"的**两个子类**（学生读者、教师读者），与"读者"之间画**泛化**（空心三角指向读者），公共属性上移到父类。

**问题 3**：**策略（Strategy）模式**。
理由：短信提醒、邮件提醒是**一族可互换的算法**，系统按配置动态选择其一——正是"封装一系列算法、使它们可以互相替换"的意图。实现上定义统一的提醒接口，短信/邮件各做一个具体策略，配置决定注入哪个策略；将来新增"钉钉提醒"只需加一个策略类，调用方不改（呼应第一节多态的动机）。

### 精华题答案

**1. 分类**：创建型——Singleton、Factory Method、Prototype；结构型——Adapter、Bridge、Composite；行为型——Observer、Strategy、Command、Memento。按口诀核对：创建 5 / 结构 7 / 行为 11。

**2. ① 享元（Flyweight）**——"共享细粒度对象省内存"，棋子共享、位置外提（作为外部状态）；② **代理（Proxy）**——图片对象作为替身控制对真实图片的访问，"延迟加载"是**虚拟代理**的典型应用；③ **职责链（Chain of Responsibility）**——请求沿处理者链传递直到被处理，任一环节可截住；④ **命令（Command）**——"把请求封装成对象"从而支持撤销，撤销机制由命令对象提供（若题干强调"保存/恢复某一时刻的状态快照"，那才是备忘录）。

**3. ① 聚合**（雁离了雁群还能活，空心菱形）；**② 组合**（翅膀同生共死，实心菱形）；**③ 依赖**（方法内临时使用，虚线箭头）；**④ 实现**（类—接口，空心三角虚线）。

**4. `f(int)` 与 `f(String)` 是重载**（同类、同名、参数不同、编译期按参数绑定）；**子类的 `f(int)` 是重写**（同签名覆盖父类版本）。多态体现：`父类引用 p = new 子类(); p.f(5);` 执行的是**子类**的 `f(int)`（运行期按实际对象类型绑定）；而 `p.f("x")` 编译期就绑定到 `f(String)`。若子类写的是 `f(double)`，那既没重写也没参与多态——它是子类的新重载方法，父类引用 p 无法直接调到它。

**5. 看转换线上标的是什么**：状态图的箭头上标**事件**（事件驱动一个对象的状态迁移，有明确的起点/终点伪状态），活动图的箭头上是**动作/活动**且出现**泳道、分叉汇合（并发）**；再问"这图描述的是单个对象还是一段业务流程"——单对象用状态图，流程用活动图。

**6. "发布文章"与"保存草稿"是 `<<include>>`**（必经步骤，箭头从发布文章指向保存草稿）；**"定时发布"是 `<<extend>>`**（勾选才发生，箭头从定时发布指向发布文章）。口诀：必经 include、可选 extend；include 从基用例指出去，extend 从扩展用例指回来。

**7. 依赖倒置原则（Dependence Inversion Principle）**。经典表述："**抽象不应该依赖于细节，细节应该依赖于抽象**；高层模块不应该依赖低层模块，两者都应该依赖于抽象。"本题中"面向 `IDao` 接口编程、由配置决定注入哪个实现类"正是"针对接口编程，不要针对实现编程"，也让新增数据库实现无需改动业务类（呼应开放-封闭原则）。注意别答成"里氏替换"——里氏替换说的是**子类能替换父类**，本题场景里并不涉及父类/子类的替换。

**8. 观察者模式**。角色对应：`Subject` = **抽象被观察对象（主题）**，提供 `attach/detach/notifyObservers` 接口用于绑定与分离观察者；`Clock` = **ConcreteSubject（具体被观察对象）**，维护观察者列表，自身状态改变时发送通知；`Observer` = **抽象观察者**，定义 `update()` 更新接口；`DigitalClock` = **ConcreteObserver（具体观察者）**，实现 `update()`，并在需要时向具体主题取状态。答题易错点：别把 `Subject` 和 `Clock` 的角色写反——**抽象角色是接口/抽象类，具体角色是真正 new 出来干活的那个**。

**9. ① 强制多态**（编译程序通过语义操作把 `int` 强行变换为 `double`）；**② 过载多态**（同一个名字在不同上下文中含义不同，即重载）；**③ 参数多态**（类型作为参数，泛型）；**④ 包含多态**（同样的操作可用于一个类型及其子类型，一般需要运行时的类型检查）。判别顺序：**看有没有"类型当参数"（参数多态）、有没有隐式类型转换（强制多态）、有没有同名不同参（过载多态）、有没有继承与子类替换（包含多态）**。

**10. ① 部署图**——立体长方体（有厚度的立方体）是**节点**符号，`<<Database>>`、`<<Storage>>` 是节点的构造型，节点之间的实线可标协议（如 TCP/IP）；**② 构件图**——构件符号（带两个小凸起）+ **整圆表示供接口、半圆表示需接口**，这是构件图的独有特征。
