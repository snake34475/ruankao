# 03 软件工程基础

> **分值地位**：选择题约 6–8 题（第一梯队）+ 案例题「数据流图」一道大题（约 15 分，常是案例第一题）。内聚耦合排序、逻辑覆盖强弱、McCabe 环路复杂度、模块设计原则几乎每年必考其一。
>
> **学习目标**：读完讲义后，你能——① 给一段项目描述选出合适的开发模型与方法；② 背出内聚/耦合七级排序并判断具体场景；③ 说出模块设计六条原则并能识别违反项；④ 排逻辑覆盖强弱、由流程图数出最少测试用例数与 McCabe 环路复杂度；⑤ 区分四种维护、质量特性分组与软件文档三类；⑥ 认出 CMM 等级描述、算沟通路径与风险暴露；⑦ 按套路补全数据流图（补数据流、补实体、补存储、补加工名——案例题）。

## 第一节 软件开发模型与方法 ★★

### 1.1 为什么有多种模型

不同项目的**需求清晰度**和**风险高低**差别巨大：需求写得一清二楚的项目不需要反复确认，需求说不清的项目硬按部就班走完设计才发现做错了。开发模型的区别就是"**怎么安排'想清楚'和'动手做'的顺序**"。认模型题的关键是抓题干特征词。

### 1.2 先分清「方法」和「模型」

这两个词真题里都出现，且常被混问。**开发方法回答"用什么思想去理解系统"，开发模型回答"阶段按什么顺序排"**。同一个方法可以用不同模型落地（面向对象方法既能用喷泉模型也能用 UP）。

| 开发方法 | 核心思想 | 一句话识别 |
|---|---|---|
| **结构化方法** | 用户至上、自顶向下逐步求精；严格区分工作阶段（每阶段有任务和结果）；强调开发的整体性、全局性；开发过程工程化、文档资料标准化 | "自顶向下、逐步求精、阶段严格" |
| **原型法** | 先给用户一个能跑的原型，边用边改 | "先做出来给用户看" |
| **面向对象方法** | 把系统看成一组互相作用的对象；**关键是建立一个全面、合理、统一的模型**；**分析、设计、实现三阶段界限不明确** | "三阶段界限模糊、复用性好" |
| **面向服务方法** | 把功能包装成松耦合的服务；抽象级别分三层：**操作 → 服务 → 业务流程** | "三层抽象、服务组合" |

**考试特征**："三阶段界限不明确"只能选**面向对象方法**（这句话反过来也考："面向对象方法与结构化方法的最大区别"）；"抽象级别为操作、服务、业务流程"只能选**面向服务方法**。

### 1.3 开发模型全景（不只有四种）

按"想清楚"和"动手做"的排法分两大族：**顺序型**（一次走完，不回头）与**迭代演化型**（反复小圈走）。

| 模型 | 核心特征 | 适用场景 | 题干特征词 |
|---|---|---|---|
| **瀑布模型** | 线性顺序，每阶段结束有评审，**文档驱动** | 需求**明确且稳定**的项目 | "需求明确""一次通过、阶段评审" |
| **V 模型** | 瀑布的升级：把测试与开发阶段**一一对应**挂起来（下面的 4.1 节给对应表） | 强调测试贯穿始终的项目 | "测试与开发阶段对应""测试贯穿始终" |
| **增量模型** | 需求切成一片片**分批交付**，第一个增量常是**核心产品** | 可以分期上线、想让核心先稳定的项目 | "分批交付""先核心后扩展" |
| **原型模型**（属演化模型） | 先快速做一个可运行的**原型**给用户确认，再正式开发 | 需求**不明确**、用户说不清，且**规模不太大不太复杂** | "快速构建演示""用户确认后再开发" |
| **螺旋模型**（属演化模型） | 瀑布 + 原型 + **每圈都做风险分析**，多圈迭代 | **大型、复杂、高风险**项目 | "风险分析""多轮迭代" |
| **喷泉模型** | 各阶段**迭代无间隙**（不像瀑布那样阶段分明）；**以用户需求为动力、以对象为驱动** | **面向对象**的开发 | "迭代无间隙""对象驱动" |
| **统一过程 UP** | 三大特点：**用例驱动、以架构为中心、迭代和增量**；四阶段：**初始 → 细化 → 构建 → 交付** | 中大型面向对象项目 | "用例驱动""以架构为中心""四个阶段" |
| **敏捷族**（Scrum / XP …） | 短迭代、拥抱变化、可工作软件优先 | 需求多变、小团队、快速上线 | "每日站会""冲刺""结对编程""测试驱动" |

**记忆抓手**：
- **演化模型是一族**，包含原型模型与螺旋模型——题干说"属于演化模型的是"要能选原型/螺旋；
- **喷泉模型的"无间隙"对应面向对象**，与瀑布"严格分阶段"正好是一对反义；结构化方法的"严格区分工作阶段"就配瀑布/结构化，别配喷泉；
- **UP 的"用例驱动 + 以架构为中心"**这句连读，是选择题的原话级考点。

### 1.4 敏捷族六个成员（认名字 + 抓一句特征）

| 敏捷方法 | 一句话特征 |
|---|---|
| **极限编程 XP** | 4 大价值观、5 大原则、**12 个最佳实践**（结对编程、测试驱动开发、持续集成、重构、小型发布…）——**工程实践最多** |
| **水晶法 Crystal** | **以人为本**：每个项目都需要一套不同的策略、约定与方法论；项目质量和开发人员素质提高，过程质量也随之提高 |
| **开放式源码** | 开发人员**在地域上分布很广** |
| **Scrum（并列争球法）** | 把每 **30 天**一次的迭代称为一个"**冲刺周期**"，按需求**优先级**实现；多个**自组织和自治**的小组并行递增实现产品 |
| **功能驱动开发 FDD** | **首席程序员**与"类"程序员，人尽其用 |
| **自适应软件开发 ASD** | 核心是三个非线性、重叠的阶段：**猜测、合作、学习** |
| **敏捷统一过程 AUP** | 采用"大型连续"和"小型迭代"原理构建系统 |

**Scrum 与 XP 要能区分**（最高频的一对）：Scrum 是**管理框架**（产品负责人、Sprint 冲刺、每日站会、回顾会）；XP 是**工程实践**（结对编程、测试驱动开发 TDD、持续集成、重构、小型发布）。题干问"结对编程属于"→ XP；问"每日站会属于"→ Scrum。

### 1.5 反例演示（易错三处）

1. **原型不是最终产品**——抛弃型原型确认完需求就扔掉；考题说"原型可作为最终系统交付"即错。
2. **螺旋模型不是"更花哨的瀑布"**——它区别于一切传统模型的核心就是**每圈迭代都加入风险分析**；选项里没有风险分析的螺旋描述都是干扰项。
3. **瀑布模型的"缺点"考法**——**直到后期才能看到可运行软件**、需求变更代价大；不是"没有文档"（瀑布恰恰**文档最全**，它是文档驱动的）。
4. **甘特与 PERT 的优缺点不能互串**（详见第七节）——"不能反映依赖关系"是甘特的缺点、"不能反映并行关系"是 PERT 的缺点，这两个形容词一换就是错项。

**应试动作**：背四个特征词对应（明确→瀑布 / 不明确→原型 / 高风险→螺旋 / 多变→敏捷），考试就是配对题；再单独背两条"原话级"结论——**面向对象 = 三阶段界限不明确**、**UP = 用例驱动 + 以架构为中心 + 迭代和增量**。

## 第二节 需求分析与软件设计 ★

### 2.1 需求工程的四个过程

**需求获取 → 需求分析 → 需求规格说明（定义）→ 需求验证（确认）**（背顺序）。

**需求分析的任务是"找出系统要实现什么功能"**——只回答**做什么**，不回答**怎么做**。所以"确定模块内部算法""设计数据库表结构"都**不属于**需求分析（属于设计阶段），这是真题的一种问法。

**需求验证**指检查需求规格说明书是否**正确、一致、完整**（三个词连读记）。

### 2.2 需求的分类（两个层次，别混）

**按抽象层次分三层**：

| 层次 | 视角 | 例子 |
|---|---|---|
| **业务需求** | 整体（组织为什么做这个系统） | "提升线上订单占比到 60%" |
| **用户需求** | 用户视角（用户想干什么） | "我要能在线查订单进度" |
| **系统需求** | 计算机化视角（机器怎么界定） | 见下面三类 |

**系统需求内部再分三类**（这一层才是选择题的主战场）：

| 类别 | 含义 | 识别特征 | 例子 |
|---|---|---|---|
| **功能需求** | 系统**做什么** | 动词 + 对象（查询、统计、导出） | "系统应能按日期导出销售报表" |
| **性能需求**（非功能需求） | 做得**怎么样** | 含**数字指标**：响应时间、吞吐量、并发数、可靠性 | "响应时间不超过 2 秒" |
| **设计约束** | **必须遵守**的外部条件 | "必须用…""必须符合…标准" | "必须部署在国产操作系统上""须符合等保三级" |

**应试动作**：判断口诀——**有数字的"多快好省"归性能，有"必须/须符合"的归设计约束，其余动词句归功能需求**。

### 2.3 结构化分析的产出：四件套（必背清单）

结构化分析（SA）做完之后，交出来的东西是**四件**，考题常问"下列不属于结构化分析结果的是"：

| 产出 | 作用 | 一句话 |
|---|---|---|
| **一套分层的数据流图（DFD）** | **功能建模**——描述数据怎么流动、被怎么加工 | "系统的功能地图" |
| **一本数据词典（DD）** | 给 DFD 中每个数据流、数据存储、数据项下**精确定义** | "把图上的名字翻译成人能懂的定义" |
| **一组小说明**（加工逻辑说明） | 描述 DFD 里每个**加工内部**的处理逻辑 | "加工肚子里的算法" |
| **补充材料：E-R 图** | 描述数据之间的关系 | "数据的静态结构" |

**动机**：为什么光有 DFD 不够？因为 DFD 里的"订单""客户信息"只是**名字**，谁也不知道里面究竟有哪几个字段——**没有数据词典，图中的名字就没有精确含义**；同理 DFD 里的"审核"这个加工是个黑盒子，**没有小说明就不知道它按什么规则审核**。图 + 词典 + 说明，才是完整的一份分析结果。

### 2.4 软件设计的四项活动（顺序不能乱）

需求想清楚了，进入设计。设计的四项活动是一条有先后依赖的链：

| 活动 | 做什么 | 依据 |
|---|---|---|
| **① 体系结构设计** | 定义软件系统**各主要部件之间的关系**（先搭骨架） | 需求 + 经验 |
| **② 数据设计** | 基于 **E-R 图**确定**文件系统结构与数据库表结构** | E-R 图 |
| **③ 接口设计**（人机界面设计） | 软件**内部**、软件与**操作系统**间、软件与**人**之间如何通信 | 体系结构 |
| **④ 过程设计** | 把结构部件转换成**过程描述**——确定各部件**内部的算法与内部数据结构** | 前两项结果 |

**考试问法**："确定模块内部算法与数据结构属于哪个活动"→ **过程设计**（不是体系结构设计，体系结构只管部件之间的关系）。"基于 E-R 图确定表结构"→ **数据设计**。

### 2.5 加工逻辑的三种描述工具（判定表是重点）

光有 DFD，加工内部是个黑盒；**小说明**就是用来"打开黑盒"的。描述工具**三种**：**结构化语言、判定表、判定树**。

**为什么需要判定表**：当某个加工的一组动作**依赖多个逻辑条件的取值组合**时，用自然语言写必然又长又漏（"如果是会员且金额够…如果是会员但金额不够…如果不是会员但金额够…"），**判定表能把条件组合与应做的动作一一对平，不漏一种组合**。

**判定表的四个部分**（用双线分割成四个区域）：

| 区域 | 内容 |
|---|---|
| 左上 | **条件定义** |
| 右上 | **条件取值的组合**（每一列 = 一条规则） |
| 左下 | **动作定义** |
| 右下 | **在各种取值组合下应执行的动作** |

**完整例子**（打折规则：会员且金额≥200 打 9 折；金额≥200 或会员打 95 折；其余不打折）：

| 条件 / 动作 | 规则 1 | 规则 2 | 规则 3 | 规则 4 |
|---|---|---|---|---|
| 是会员？ | Y | N | Y | N |
| 金额 ≥ 200？ | Y | Y | N | N |
| **动作** 打 9 折 | ✓ | | | |
| 打 95 折 | | ✓ | ✓ | |
| 不打折 | | | | ✓ |

**验算这张表对不对**：4 列 = 2 个条件各取真假共 **2² = 4 种组合**，无遗漏无双算 ✓。逐列核对规则——(Y,Y)=会员且够钱 → 9 折 ✓；(N,Y)=非会员但够钱 → 命中"金额≥200"→95 折 ✓；(Y,N)=会员但钱不够 → 命中"是会员"→95 折 ✓；(N,N) 两条都不命中 → 不打折 ✓。

**判定树**是判定表的变形，把条件按层级展开：

```
用户是否会员？
├─ 是 ── 订单金额 ≥ 200 元？
│        ├─ 是 → 打 9 折
│        └─ 否 → 打 95 折
└─ 否 ── 订单金额 ≥ 200 元？
         ├─ 是 → 打 95 折
         └─ 否 → 不打折
```

**两者对照**：**判定树更直观、易理解易用**；**判定表在条件组合多时更严密、不易漏**。口诀"**树好看、表不漏**"。

**结构化语言**则是用 `IF…THEN…ELSE`、`WHILE…DO` 这类受限的伪代码写，规则同上例：

```
WHILE (收到出库申请)
DO
    查询会员信息 AND 查询订单金额;
    IF (是会员 AND 金额 ≥ 200)
    THEN 打 9 折;
    ELSE
        IF (金额 ≥ 200 OR 是会员)
        THEN 打 95 折;
        ELSE 不打折;
        ENDIF
    ENDIF
    生成结算单;
ENDDO
```

**应试动作**：① 背"分层 DFD + 数据词典 + 小说明 + E-R 图"四件套；② 记设计四活动的**依据**（数据设计靠 E-R 图、过程设计管算法）；③ 判定表只需记住"**四区域 + 每列一条规则 + 列数 = 2ⁿ**"，考题问列数就直接算 2 的条件数次方。

## 第三节 模块化设计：内聚、耦合与模块原则 ★★★

### 3.0 为什么要"高内聚、低耦合"

软件要拆成模块，拆法有好坏：一个模块内部干的事**越相关**（内聚越高），越容易看懂、改起来越不容易牵连别处；模块之间**越独立**（耦合越低），一个模块改动对别的影响越小。"高内聚、低耦合"就是这两条经验的一句话版。**内聚看模块内部，耦合看模块之间**——先分清这个方向再背排序。

### 3.1 模块设计的六条原则（真题的"下列错误的是"常客）

内聚与耦合只回答了"模块怎么拆才算好"里的一个维度。完整的模块设计原则是**六条**，其中三条专考：

**① 保持模块的大小适中**
- 过大：内部可能揉进不同类型的功能，需要进一步划分，尽量让各模块功能单一；
- 过小：系统复杂度反而增加，**模块之间的调用过于频繁，降低了模块的独立性**。
- **结论：模块规模不是越小越好**——"模块规模越小越好"是真题的固定错项。

**② 深度、宽度适中**
- **深度** = 软件结构中模块的**层数**。层数过多 → 说明有些模块设计得过于简单，应考虑**合并**。
- **宽度** = 软件结构中**同一层次上模块总数的最大值**。影响宽度最大的因素是**模块的扇出**。宽度越大系统越复杂。

**③ 扇入、扇出系数要合理**
- **扇入** = 该模块的**直接上级模块的个数**（有多少个模块调用它）；
- **扇出** = 该模块的**直属下级模块的个数**（它调用了多少个模块）；
- 原则是"**多扇入、少扇出**"：扇入大 = 复用性好（很多模块都用它，改好一处全都受益）；扇出小 = 该模块自身比较独立、不牵动一大片。经典的错项写法是反过来写"多扇出、少扇入"。

**④ 模块的作用域应该在控制域之内**（最绕、最爱考）
- **控制域** = 这个模块**本身**以及所有**直接或间接从属于它**的模块的集合；
- **作用域** = 受该模块**内一个判定所影响**的所有模块的集合；
- 要求：**判定的影响范围必须落在该模块能控制的范围内**。

**违反时的样子与改法**（一眼看懂）：

```
        M（主控）
       /  \
      A    B        判定 P 写在 A 里面，
     (P)             但 P 的结果要影响兄弟模块 B

A 的控制域 = {A}   ← A 没有下级，管不到 B
A 的作用域 = {B}   ← P 影响的是 B
{B} ⊄ {A}  → 违反！A 只能在算完之后把结果当参数往外传，耦合被迫升高
```

改法二选一：**把判定 P 上移到 M**（此时 M 的控制域 = {M, A, B} ⊇ {B} ✓）；或者**把被影响的模块 B 下移到 A 之下**。

**⑤ 功能应该是可预测的**
模块的功能要单一、结果要可预期。反例：一个模块的输出取决于某个全局变量的当前值，同样的入参可能返回不同结果，调用者无法预知——这就是"功能不可预测"，属设计缺陷。**"模块的功能应该是不可预测的"是真题的固定错项。**

**⑥ 高内聚、低耦合**：见 3.2、3.3。

### 3.2 内聚七级（从低到高，必须背顺序）

| 级别 | 名称 | 含义 | 一句话识别 |
|---|---|---|---|
| 1 | **偶然内聚**（巧合内聚） | 动作之间毫无关系，凑在一起（如"为了省事把几个无关函数塞一个模块"） | "没什么关系，硬凑" |
| 2 | **逻辑内聚** | 逻辑上**相似**但功能用途无关（如一个模块按参数分别执行打印输入/打印输出） | "相似但无关" |
| 3 | **时间内聚**（瞬时内聚） | 动作无关，但必须在**同一时间**（同一时间间隔内）执行（如初始化模块） | "同一时间" |
| 4 | **过程内聚** | 动作关系不大，但必须**按特定次序**执行 | "按次序但无实质关系" |
| 5 | **通信内聚** | 各动作对**同一数据**进行操作（如对同一份数据先读后存再打印） | "围绕同一数据" |
| 6 | **顺序内聚** | 前一个动作的**输出**正好是后一个动作的**输入**（必须顺序执行） | "接力棒" |
| 7 | **功能内聚** | 所有部分合起来完成**单一功能**（如计算利息），协同工作缺一不可 | "就是一个功能" |

### 3.3 耦合七级（从高到低，必须背顺序）

| 级别 | 名称 | 含义 | 一句话识别 |
|---|---|---|---|
| 1 | **内容耦合** | 一个模块直接访问另一个模块的**内部**数据或代码；或不经正常入口转入内部；或两块代码重叠；或一个模块有多个入口 | "掀开别人内脏" |
| 2 | **公共耦合** | 多个模块通过**同一公共数据环境**（全局数据结构，如一个大数组、一个公共文件）传递信息 | "共用一个大仓库" |
| 3 | **外部耦合** | 多个模块访问**同一全局简单变量**（不是数据结构），且不是通过参数表传递 | "共用一个全局变量" |
| 4 | **控制耦合** | 传递的信息中含**控制信号**（如开关标志决定对方走哪个分支） | "传的是命令不是数据" |
| 5 | **标记耦合** | 通过参数表传递**记录信息/数据结构**（而非简单变量） | "传一整条记录" |
| 6 | **数据耦合** | 通过参数表传递**简单数据** | "传一个数" |
| 7 | **非直接耦合** | 两模块之间**没有直接关系**，联系完全通过**主模块的控制和调用**实现 | "各干各的，上级牵线" |

### 3.4 反例演示（最易混四组）

1. **逻辑内聚 vs 偶然内聚**：动作之间"有点相似"（都跟打印/输入输出沾边）→ 逻辑内聚；"完全没关系"→ 偶然内聚。判别标准是**相似性**是否存在。
2. **时间内聚 vs 过程内聚**：都是"关系不大硬放一起"，区别在**约束是"同时"还是"先后"**——初始化必须一起做 = 时间；必须按某次序执行 = 过程。
3. **公共耦合 vs 外部耦合**：共用的是**数据结构**（一整个数组/记录/文件）→ 公共耦合；只是**简单变量**（一个全局计数器）→ 外部耦合。
4. **标记耦合 vs 数据耦合**：参数传的是**一条记录/结构**（整个学生信息）→ 标记耦合；只是**一个简单变量**（学号这一个数）→ 数据耦合。

**再强调一处易错**：耦合的**数据类**三项（控制 > 标记 > 数据）排序时，**"传记录"比"传简单变量"耦合高**——因为在传递的内容里，前者包含了后者的全部信息，改记录结构会牵连更多模块。

**应试动作**：① 两个排序必须能默写——内聚从"凑（偶然）"到"专（功能）"，耦合从"掀内脏（内容）"到"不认识（非直接）"；② 做题先抓题干关键词（同一时间/同一数据/接力/命令/记录/变量/全局）对号入座；③ 模块原则题抓三个"反向错项"——"越小越好""多扇出少扇入""功能不可预测"，见到就选它错。

## 第四节 软件测试 ★★★

### 4.1 测试的两大分类：静态 vs 动态

测试不等于"把程序跑一遍看对不对"——有一大类测试**根本不运行程序**。这张分类树是很多题的答案来源：

```
软件测试
├── 静态测试（纯人工，不运行程序）
│    ├── 桌前检查（desk checking）
│    ├── 代码走查（walkthrough）
│    └── 代码审查（inspection）
└── 动态测试（实际把程序跑起来）
     ├── 黑盒测试（测功能，不看代码）
     ├── 白盒测试（测结构，看代码）
     └── 灰盒测试（黑白结合）
```

**考试特征**：题干出现"**不运行程序**""**人工评审**""**代码评审会**"→ 静态测试；出现"输入数据看输出"→ 动态测试。

### 4.2 静态测试三手段（三者的差别就是考点）

| 手段 | 谁主持 | 怎么做 | 正式程度 |
|---|---|---|---|
| **桌前检查** | 代码作者自己（或拉个同行在桌边） | 自己把代码**逐行过一遍**，对可疑处做标记 | 最轻、非正式 |
| **代码走查** | **开发人员（作者）主持** | 作者**逐段讲解**自己的代码，评审者**边听边跟着走代码**、随时提问 | 中等 |
| **代码审查** | **评审组长**（不是作者） | 评审小组**对照一份"常见错误检查表"逐项核对**，最后产出缺陷清单与处理结论 | **最正式** |

**记忆抓手**：**桌前看自己、走查听讲解、审查对清单**。（三者的共同点是都**不运行程序**，所以都属于静态测试——这是最容易混的地方。）

### 4.3 测试阶段：顺序、目标、依据文档

**顺序（必须背）**：**单元测试 → 集成测试 → 确认测试 → 系统测试**（教材四步）；**若题目另外单列出"验收测试"，则排在最后**（下详）。

| 阶段 | 测什么 | **依据的文档** | 主要任务 |
|---|---|---|---|
| **单元测试** | 单个**模块内部** | **详细设计** | 模块接口、局部数据结构、**边界条件**、独立路径、错误处理 |
| **集成测试** | 模块**之间的接口与通信** | **概要设计** | 数据传递错误、模块间调用关系异常 |
| **确认测试** | 软件**与需求的一致性** | **需求规格说明书** | 有效性测试、软件配置审查 |
| **系统测试** | **真实环境**下与硬件/网络/其他系统的整体联调 | 需求 + 环境约束 | 恢复、安全性、**强度**、性能、可靠性、**安装**测试 |
| （验收测试） | 用户确认是否满足**业务需求** | 合同 / 需求 | 由**用户**主导 |

**关于"确认测试"与"验收测试"的口径**：确认测试本身有**四种形式**——**内部确认测试、Alpha 测试（在开发方场所、开发者在场）、Beta 测试（在用户实际使用环境）、验收测试（用户主导）**。所以题目给四个空就填"单元→集成→确认→系统"，给五个空才把"验收测试"单列在最后。**两者不是矛盾的两套体系，只是一个合并算、一个拆开算**。

**为什么"集成测试发现接口问题"、而单元测试发现不了**（真题原话考法）：单元测试时每个模块是**孤立**跑的，调用关系是假的，接口错配根本暴露不出来；只有把模块**组装**起来，参数个数、类型、顺序、数据传递的错误才会显形。

### 4.4 V 模型：测试与开发阶段的对应关系

V 模型是瀑布模型的升级，它把"测试"从最后一坨拆开、提到与开发阶段**一一对应**的位置上：

```
需求分析 ────────────────▶ 验收测试
     \                   /
      \                 /
概要设计 ───────────▶ 系统测试
        \           /
详细设计 ─────▶ 集成测试
          \   /
     编码 ──▶ 单元测试
```

**四对对应关系（背下来，真题原话考过"系统测试阶段的测试目标来自于哪个阶段"→ 需求分析）**：

| 开发阶段 | 对应测试 | 逻辑 |
|---|---|---|
| 需求分析 | **验收测试** | 需求对不对，最终只能由用户验收时回答 |
| 概要设计 | **系统测试** | 概要设计定部件与系统边界，系统测试在真实环境验证整体 |
| 详细设计 | **集成测试** | 详细设计定模块接口，接口错配在集成时暴露 |
| 编码 | **单元测试** | 代码片段对不对，只在该单元内检查 |

**记忆抓手**：**越晚的测试，对应的文档越"上游"**——验收问的是"需求对不对"，单元只问"这段代码对不对"。

### 4.5 集成测试的两种策略（桩模块 / 驱动模块，高频易错）

模块一个个写，总有"还没做好"的邻居。集成测试要按方向借"假模块"顶替：

| 策略 | 从哪开始 | 需要什么辅助模块 | 辅助模块的作用 |
|---|---|---|---|
| **自顶向下** | 从**主控模块**往下逐层组装 | **桩模块（stub）** | 模拟**被调用**的**下级**模块（下面的还没做好，先拿假的顶住） |
| **自底向上** | 从**最底层**模块往上组装 | **驱动模块（driver）** | 模拟**调用者**（**上级**还没做好，先造个假的来调我） |
| **三明治集成** | 上下并行（混合） | 桩 + 驱动都要 | — |

**方向别记反**：**"桩"打在地里 → 在最下面被顶住的是桩**；**"驱动"来自上层 → 主动去调别人的是驱动**。所以"自顶向下需要桩模块、自底向上需要驱动模块"——这句话可以直接填两个空。

### 4.6 其他专项测试（一句话区分）

| 类型 | 一句话 |
|---|---|
| **回归测试** | 软件**修改之后**再测：既测变更部分是否正确，也测变更有没有碰坏别处（防止引入新错误） |
| **负载测试** | 测软件在**规定负载**（如 500 并发）下的表现能力 |
| **压力测试** | 测软件在**超负荷**条件下的运行情况（如 5000 并发，看它是降级还是崩溃） |

**回归 vs 压力别混**：**改完就回归**、**压趴才叫压力**。

### 4.7 白盒测试与逻辑覆盖（必考排序）

白盒测试把程序看成**透明**的，按**程序内部逻辑**设计用例。逻辑覆盖从弱到强：

**语句覆盖 < 判定覆盖 < 条件覆盖 < 判定/条件覆盖 < 条件组合覆盖 < 路径覆盖**

| 覆盖 | 要求 |
|---|---|
| **语句覆盖** | 每条**语句**至少执行一次（最弱） |
| **判定覆盖**（分支覆盖） | 每个判定的**真、假分支**各至少经历一次（判定可以是 1 个条件，也可以是多个条件的组合） |
| **条件覆盖** | 每个判定中每个**条件的真、假取值**各至少一次 |
| **判定/条件覆盖** | 判定的真假分支 + 条件的真假取值**都**满足（= 判定覆盖 ∧ 条件覆盖） |
| **条件组合覆盖** | 每个判定中条件的**所有取值组合**都出现 |
| **路径覆盖** | 覆盖程序**所有可能的路径**（最强） |

**必须知道的一个"例外"**：上表的先后只是**习惯排列**，严格讲 **条件覆盖与判定覆盖互不包含**——既不是"条件覆盖 ⊃ 判定覆盖"，也不是反过来。所以考题若直接问"条件覆盖和判定覆盖谁更强"，正确说法是"**两者没有包含关系**"；要同时保证两者，必须上"**判定/条件覆盖**"。真正的包含链是：

```
路径覆盖 ⊃ 条件组合覆盖 ⊃ 判定/条件覆盖 ⊃ 判定覆盖 ⊃ 语句覆盖
                                  （条件覆盖不在这条链上，它与判定覆盖互不包含）
```

**反例演示（经典陷阱）**：判定 `A>0 AND B>0`，两个用例取 (A=1,B=0) 和 (A=0,B=1)——两个条件的真假都取遍了（**条件覆盖满足**），但判定结果**都是假**，真分支一次没走过（**判定覆盖不满足**）。这就是为什么排序里条件覆盖只保证条件、不保证分支。

### 4.8 从流程图数出「最少用例数」（真题形态）

真题常这么问：给一张程序流程图，问"进行**语句覆盖**测试和**路径覆盖**测试**至少**需要几个测试用例"。它考的不是覆盖定义，而是**你数不数得清路径**。看下面这张流程图（一个"双分支 + 双分支"的程序）：

```
        开始 (1)
          |
          v
      读入 A,B (2)
          |
          v
     < A > 0 ? > (3)
       |        |
      Y|        |N
       v        v
   x = 1 (4)  x = 2 (5)
       |        |
       +---+----+
           |
           v
        汇合 (6)
           |
           v
     < B > 0 ? > (7)
       |        |
      Y|        |N
       v        v
   y = 1 (8)  y = 2 (9)
       |        |
       +---+----+
           |
           v
        汇合 (10)
           |
           v
        结束 (11)
```

**① 语句覆盖最少用例数**：要四条赋值语句 ④⑤⑧⑨ 各执行一次。一个用例走"每个判定的一侧"，所以一个用例只能覆盖 2 条赋值语句；两个用例（如 A=1,B=1 走 ④⑧、A=−1,B=−1 走 ⑤⑨）刚好覆盖 ④⑤⑧⑨ → **2 个**。

**② 路径覆盖最少用例数**：无循环时，**路径条数 = 各判定分支数的乘积** = 2 × 2 = **4 条**，所以需要 **4 个**用例。四条路径是：④⑧ / ④⑨ / ⑤⑧ / ⑤⑨。

**③ 判定覆盖最少用例数**：判定 ③ 要取真假、判定 ⑦ 要取真假 → 同样 2 个用例（A=1,B=1 给"真真"，A=−1,B=−1 给"假假"）。

**记法**：**语句覆盖、判定覆盖通常 2 个就够（一个走一侧）；路径覆盖数"分支数的乘积"**。判定层数一多，路径数就指数级膨胀——这正是路径覆盖在工程上很难做到的原因（考试只让你数，不让你穷举）。

### 4.9 McCabe 环路复杂度（必考计算，重点是"怎么数"）

McCabe 环路复杂度衡量程序控制流的复杂程度，**三种等价算法**，任给两样就能算第三样：

**V(G) = 边数 m − 结点数 n + 2 = 判定节点数 + 1 = 封闭区域数 + 1**

**从流程图数起来的三步**：

1. **转结点图**：把流程图化成**有向图**——每个语句块/判定是一个结点，**分支汇合处要补一个新结点**；
2. **数 m 和 n**：m 是**有向弧**的条数（注意方向，一条弧算一条），n 是结点数；
3. **代入 + 互验**：算 m − n + 2，再用"判定节点数 + 1"对一遍。

**用 4.8 那张图走一遍**（同一张图，正好两问一起考）：

| 项 | 数出来 | 备注 |
|---|---|---|
| 结点数 n | **11** | 开始1、读入2、判定3、赋值4/5、**汇合6**、判定7、赋值8/9、**汇合10**、结束11 |
| 有向弧数 m | **12** | 1→2、2→3、3→4、3→5、4→6、5→6、6→7、7→8、7→9、8→10、9→10、10→11 |
| **V(G) = m − n + 2** | **12 − 11 + 2 = 3** | |
| **互验：判定节点数 + 1** | **2 + 1 = 3** | 判定节点只有 ③ 和 ⑦ 两个 ✓ 两法一致 |

**关于"补汇合结点"要不要补**：一定要补，因为**不补图就不合法、m 和 n 都数不清**。补一个汇合点会让 **n 和 m 各 +1**，代入 V(G) = m − n + 2 恰好抵消，所以**补不补不影响最终结果**——它的作用只是让你**数得清、不重不漏**。考试里老实补上再数，最稳。

**V(G) 与"路径条数"不是一回事（别混）**：上面这张图的路径覆盖要 4 条用例，而 V(G) = 3。V(G) 反映的是**判定中枢的个数**（基本路径测试取"独立路径"条数），不等于"所有组合路径的条数"。这两问同时出现时**分开算**，别拿 3 当 4 用。

**反例演示（易错三处）**：
- **"判定节点"只数分支点**（if、while、for、case 的分支），`i = i + 1` 这类顺序语句**不是**判定节点，别把它算进"判定节点数 + 1"里；
- 复合条件 `if (A>0 AND B>0)` 在软考默认按**一个判定节点**算（即这个 if 算 1 个），不要拆成 2 个条件各算一个；
- **一条弧只算一条**，画图时不要因为视觉上"线长"就重复计数。

**应试动作**：① 三种算法任选一种先用、另一种互验（**没互验过不要落笔**，这是本课最容易算错的地方）；② 遇到流程图，先在草稿上标结点号（1、2、3…）再数弧，数弧时按"从一个结点出发有几条箭头出去"逐个结点数，最后加总；③ 记住"语句覆盖 2 个 / 路径覆盖 = 分支数相乘"这个速算结论。

### 4.10 黑盒测试（看功能不看代码）

| 方法 | 做法 |
|---|---|
| **等价类划分** | 把输入分成若干"同类"的**有效等价类**与**无效等价类**，每类取一个代表。**规则：设计用例尽可能多地覆盖有效等价类；而每个无效等价类只用一个用例覆盖** |
| **边界值分析** | 在等价类**边界**处取值：**恰好等于、稍小于、稍大于**边界值。范围 [1, 100] 就取 **0、1、100、101**——错误最爱出现在边界 |
| **错误推测** | 凭经验猜易错点 |
| **因果图** | 输入条件的组合 → 判定表（适合"输入条件互相制约"的场景） |

**为什么"无效等价类只覆盖一个"**（真题原话级考点）：**一个好的无效等价类用例，应该只从一个角度违反规则**。若一个用例同时违反了年龄、学历两个条件，出错时**无法定位到底哪一条规则判错了**；只违反一条，错误才能精确定位。

**等价类 vs 边界值**：等价类是"**在类里随便取一个**"（如 [1,100] 取 50），边界值是"**专挑边的内外侧**"（0、1、100、101）。两者常配合使用。

### 4.11 测试的基本原则（五条，选择题直接考）

1. **尽早、不断地进行测试**（测试不是编码完才开始；对应 V 模型把测试提前）；
2. **程序员应避免测试自己设计的程序**（自己写的东西自己看不出错）；
3. **既要选有效、合理的数据，也要选无效、不合理的数据**（只测正确输入必漏 bug）；
4. **修改后应进行回归测试**（防止改一处坏一片）；
5. **尚未发现的错误数量与该程序已发现的错误数成正比**（已发现的错越多，说明剩下的错也越多——所以"测得越干净"不代表"质量越好"）。

**应试动作**：① 覆盖强弱排序背死（语句最弱、路径最强），并记住"**条件覆盖 ⊉ 判定覆盖**"这个唯一例外；② 流程图两问（最少用例数、McCabe）分开算，McCabe 必须**两种算法互验**；③ 记住三条速算——**语句覆盖 2 个 / 路径覆盖 = 分支数相乘 / V(G) = 判定节点数 + 1**；④ 黑盒题抓"无效等价类只违反一个条件"。

## 第五节 软件维护 ★

### 5.0 为什么维护才是成本大头

维护是软件交付**之后**发生的修改。两条常考的"反直觉"结论：

- **软件维护期通常比开发期长得多，投入也大得多**——所以"如何降低维护成本"其实比"如何提高开发效率"更值钱；
- **可维护性是软件开发阶段（每一个时期）的关键目标**——不是等要维护了才想起来，而是从需求、设计、编码时就要为可维护性做打算。

**动机**：既然 70% 以上的成本在维护，那么代码写得让人看不懂，就等于把成本推给了未来。

### 5.1 四类维护（必须对号入座）

| 类型 | 含义 | 场景识别 | 关键词抓手 |
|---|---|---|---|
| **改正性维护**（更正性） | 针对**真实存在并且已经发生**的错误，做诊断和改正 | "用户报告 bug""统计结果算错了" | **bug** |
| **适应性维护** | 使软件**适应信息技术变化和管理需求变化** | 换操作系统、换数据库、接口规范改版 | **第三方 / 环境变了** |
| **完善性维护** | **扩充功能、改善性能**（增加系统分析设计阶段没规定的功能与性能特征） | "希望增加微信通知功能""查询要更快" | **用户想要新的** |
| **预防性维护** | 针对**真实存在但还未发生**的错误，**主动**为未来的修改与调整奠定更好基础 | 提前重构老代码、为将来的扩展预留结构 | **程序员主动** |

**关键词区分（最省力的记法）**：**bug → 改正；用户（提新需求）→ 完善；第三方/环境 → 适应；程序员主动 → 预防**。

### 5.2 反例演示（最易混的两对）

1. **改正 vs 预防**：判别就一句话——**错误发生了没**。修**已发生**的报错 = 改正性；改**还没发生**的隐患（"这段代码现在没错，但以后会出事，先重写"）= 预防性。**"提前重构"永远不是改正性。**
2. **完善 vs 适应**：判别问一句——**是"自己想要更多"还是"外部逼着改"**。用户主动加功能 = 完善性；因为换了操作系统/数据库、外部接口改版而不得不改 = 适应性。**"升级到新 OS 后要改"是适应性，不是完善性**（完善性不涉及环境变化）。

### 5.3 占比（直接考）

**完善性维护占全部维护工作量的 50%–60%，是最大的一块**；**预防性维护占比最小**。所以"软件维护工作量中占比最大的是"→ 完善性维护。

### 5.4 可维护性的度量与评价指标

**一个公式**：**可维护性 = 1 / (1 + MTTR)**，其中 **MTTR 是平均故障修复时间**。**修复越快（MTTR 越小）→ 指标越大 → 可维护性越好。**

（同族的三个易混公式，别记串：**可靠性 = MTTF/(1+MTTF)**、**可用性 = MTBF/(1+MTBF)**、**可维护性 = 1/(1+MTTR)**。MTTF/MTTR/MTBF 的含义与串联、并联系统可靠性计算详见 [09-计算机系统基础.md](09-计算机系统基础.md) 的可靠性一节，这里只需记住"**可维护性盯的是 MTTR**"。）

**三个定性评价指标（记这三个，别多别少）**：**可理解性、可测试性、可修改性**。考题会用"一致性"来当干扰项——它不是可维护性的评价指标。

**维护工具六类**（认名字即可）：版本控制工具、文档分析工具、开发信息库工具、**逆向工程工具**、**再工程工具**、配置管理支持工具。

**逆向工程 vs 再工程**（各一句）：**逆向工程** = 从代码**反推**出设计甚至需求（由底层往上还原）；**再工程** = 在逆向工程的基础上**重构改造**，得到一个新的改进版本（比逆向工程多"改造"这一步）。

### 5.5 应试动作

背三件事：① 四类维护 + 四个关键词抓手；② **完善性维护占大头（过半）**、预防性维护最小；③ 可维护性盯 **MTTR**，评价指标是**可理解性、可测试性、可修改性**三件套。做题先问"错误发生了没"，再问"自己想要还是环境逼的"。

## 第六节 软件质量特性与软件文档 ★

### 6.1 McCall 模型：三组十一特性（背分组归属）

| 面向 | 包含特性 |
|---|---|
| **运行（产品操作）** | 正确性、可靠性、效率、完整性、可用性 |
| **修正（产品修正）** | 维护性、灵活性、可测试性 |
| **转移（产品转移）** | 可移植性、复用性、互操作性 |

**记忆抓手**：**运行 5、修正 3、转移 3**（共 11）。分组名字本身就是提示——"运行"是软件跑起来时能看出来的，"修正"是改动它时用到的，"转移"是把软件搬到别的环境/别的项目时用到的。

### 6.2 ISO/IEC 9126：六大特性 + 子特性（选择题常问"XX 属于哪个特性"）

| 特性 | 子特性 |
|---|---|
| **功能性** | 适合性、准确性、**互操作性**、安全保密性、依从性 |
| **可靠性** | **成熟性、容错性、易恢复性** |
| **易用性** | 易理解性、易学性、易操作性 |
| **效率** | 时间特性、资源利用性 |
| **维护性** | 易分析性、易改变性、稳定性、易测试性 |
| **可移植性** | 适应性、易安装性、一致性、易替换性 |

**只背两个"最常考的子特性归属"**：**易恢复性 → 可靠性**；**互操作性 → 功能性**。其余的子特性见到能认出来就行（题目一般只问这两处，或用"时间特性属于效率"这类显而易见的送分点）。

**McCall 与 ISO 9126 的区别一句话**：**McCall 是"三组十一特性"（问归类）**，**ISO 9126 是"六大特性 + 各自子特性"（问子特性归属）**。题干出现"成熟性、容错性"这种**子特性名**，一定是在问 ISO 9126。

### 6.3 软件文档三类（按"写给谁看"分）

| 文档类型 | 读者 | 例子 |
|---|---|---|
| **开发文档** | **开发人员** | 需求规格说明书、设计说明书、测试计划 |
| **产品文档** | **用户** | 用户手册、操作指南、安装说明 |
| **管理文档** | **管理人员/负责人** | 项目计划、进度报告、变更记录 |

**记法**：**谁看归谁**——开发看开发文档、用户看产品文档、领导看管理文档。

### 6.4 应试动作

① 背 McCall 的 **5 / 3 / 3** 分组；② 背 ISO 9126 六大特性名 + **易恢复性归可靠性、互操作性归功能性**；③ 文档三类按"读者"对号入座；④ 遇到"XX 属于哪个特性"，先在脑子里定位**它属于六大特性中的哪一个**，再看是不是子特性名。

## 第七节 项目管理基础 ★

项目管理在选择题里考三块：**进度（甘特 / PERT）、成本（COCOMO）、风险（风险暴露）**，外加沟通路径这么一个小公式。

### 7.1 进度管理：甘特图与 PERT 图（优缺点不能互串）

| 图 | 长什么样 | 优点 | 缺点 |
|---|---|---|---|
| **甘特图（Gantt）** | 横轴时间、横条表示每个任务的起止与工期 | 清晰描述各任务**从何时开始到何时结束**、进程情况、以及**任务间的并行关系** | **不能清晰反映各任务之间的依赖关系**，难以确定整个项目的**关键所在** |
| **PERT 图（网络图）** | 结点 + 带权有向弧（结点表示里程碑，弧表示活动与其工期） | 能清晰反映各任务之间的**依赖关系**，从而确定**整个项目的关键所在** | **不能反映任务之间的并行关系** |

**这是一对"互缺"的图**：甘特有"并行"没"依赖"，PERT 有"依赖"没"并行"。**题干问到哪一句，就答缺哪一句**——两个形容词一换就是错项。

**关键路径**：从开始到结束**需要时间最长**的那条路径；**项目工期 = 完成项目的最少时间，由关键路径决定**。

**活动松弛时间（总时差）**：在不延误总工期的前提下该活动的机动时间。它有**两种算法、结果相同**：

```
总时差 = 最迟完成时间 − 最早完成时间
       = 最迟开始时间 − 最早开始时间
```

**总时差为 0 的活动就是关键活动**；把所有松弛时间为 0 的活动连起来，就是关键路径（也就是最长路径）。

**计算方法与第一课完全一样**（顺推取 max 得最早时间、逆推取 min 得最迟时间），此处不重复推导，见 [01-数据结构与算法.md](01-数据结构与算法.md) 第 3.6 节关键路径的四量表演算。**考点在"会算"，不在"知道名词"**。

**两种网络图记法**（认名字即可）：
- **前导图法（PDM）= 单代号网络图**：结点表示活动，每个结点里写 **ES/EF/LS/LF**（最早开始、最早完成、最迟开始、最迟完成）与总时差；**正向找最大（有多条进来的路）、反向找最小（有多条出去的路）**；
- **箭线图法（ADM）= 双代号网络图**：**弧**表示活动、结点表示事件。

**简记**：**单代号看结点（活动在点上）、双代号看弧（活动在线上）**。

### 7.2 沟通路径：两个公式（背公式 + 会代）

n 个人协作时的沟通路径条数：

| 情形 | 公式 | 含义 |
|---|---|---|
| **无主程序员** | **n(n−1) / 2** | 人人都可以直接找别人，两两沟通 |
| **有主程序员** | **n − 1** | 所有人只跟主程序员沟通，由主程序员中转 |

**通用形式与来源**：n 个人各要联系其余 **n−1** 个人，共 n(n−1) 次；但每一次沟通被两端的两个人**各算了一次**，所以要 **÷2**。

**代入算例（n = 5）**：
- 无主：5 × 4 ÷ 2 = **10 条**；
- 有主：5 − 1 = **4 条**。

**反向验算**：n = 5 时，两两配对的组合数就是 C(5,2) = (5×4)/(2×1) = 10 ✓（与公式一致——n(n−1)/2 本身就是组合数公式）。

**口诀**：**无主"两两配对"、有主"一根线串"**。人数一多，无主沟通量按平方增长，这正是"大团队必须有主程序员/接口人"的道理。

### 7.3 成本管理：COCOMO 估算模型

**按代码规模（KLOC，千行）估算工作量**，基本模型：

**E = a × (KLOC)^b**，其中 **E 的单位是人月**。

**a、b 是参数**，按项目类型取不同值：

| 项目类型 | 特征 |
|---|---|
| **组织型** | 规模小、团队熟悉领域、约束少（最"宽松"） |
| **半独立型** | 中等规模、经验与约束都居中 |
| **嵌入型** | 规模大、硬件/接口/法规约束多（最"苛刻"） |

**代入算例**：E = 2.0 × (KLOC)^1.0，规模 30 KLOC → **E = 2.0 × 30 = 60 人月**。
**反向验算**：60 ÷ 2.0 = 30 KLOC ✓ 自洽。

**考法**：**题干一定把公式和 a、b 都给你**，考的是"会不会代"——别去背 a、b 的数值。

（顺带记一句：成本估算模型的规模度量有三种——**对象点、功能点、代码行**。COCOMO 用的是代码行。）

### 7.4 风险管理：四步 + 一个公式

**风险的定义**："**损失或伤害的可能性**"。

**风险的三类**：

| 类别 | 内容 |
|---|---|
| **项目风险** | 预算、进度、人员等项目管理层面的风险 |
| **技术风险** | 技术方案、技术难度、技术选型层面的风险 |
| **商业风险** | 市场、产品定位、销售层面的风险 |

**风险管理四步（背顺序）**：**风险识别 → 风险预测（估计概率与损失）→ 风险评估 → 风险控制**。

**核心公式**：

**风险暴露（风险曝光度） = 风险发生的概率 × 风险可能造成的损失**

**代入算例**：某风险一旦发生会损失 10 万元，发生概率 20% → 风险暴露 = 10 × 20% = **2 万元**。
**反向验算**：2 ÷ 10 = 20% ✓ 概率算回去了。

**应试动作**：看到"概率 × 损失"就是风险暴露；看到"识别→预测→评估→控制"就是风险管理过程。

## 第八节 CMM / CMMI ★

### 8.1 CMM 五级（背顺序 + 抓关键词）

| 级别 | 名称 | 关键词识别 |
|---|---|---|
| 1 | **初始级** | 杂乱无章、甚至混乱；几乎没有明确定义的步骤；项目成功**完全依赖个人努力和英雄式核心人物** |
| 2 | **可重复级** | 建立了**基本的项目管理过程与实践**，用来跟踪**项目费用、进度和功能特性**；有必要的过程准则来**重复**以前在同类项目中的成功 |
| 3 | **已定义级** | 管理和工程两方面的过程已经**文档化、标准化**，并综合成整个开发组织的**标准过程** |
| 4 | **已管理级**（已定量管理级） | 制定了软件过程和产品质量的**详细度量标准**（**定量**） |
| 5 | **优化级** | 加强**定量分析**，通过过程质量反馈与新观念、新技术的反馈，使过程能**不断持续改进** |

**口诀**：**初、重、定、管、优**（初始—可重复—已定义—已管理—优化）。

**考法就是配对**：抓"文档化标准化"→ 3 级；"**定量/量化**"→ 4 级；"**持续改进**"→ 5 级；"**重复**以往成功"→ 2 级；"靠个人英雄"→ 1 级。**3/4/5 三级的区分全在三个词上：标准化、定量、持续改进。**

### 8.2 CMMI 的两种表示法（一阶段式 / 连续式）

**CMMI（能力成熟度模型集成）** 把 CMM 扩成了集成模型，有**两种表示法**：

**① 阶段式（阶段式模型）**——按"组织整体"分五级，与 CMM 五级一一对应：

| 级别 | 名称 |
|---|---|
| 1 | 初始级 |
| 2 | **已管理级**（CMM 的"可重复级"在这里叫已管理级） |
| 3 | 已定义级 |
| 4 | **定量管理级** |
| 5 | 优化级 |

**② 连续式（连续式模型）**——按"单个过程域的能力"分六级 **CL0–CL5**：

| 等级 | 名称 | 一句话 |
|---|---|---|
| CL0 | 未完成的 | 过程域未执行，或未达到 CL1 的全部目标 |
| CL1 | **已执行的** | 过程能把**可标识的输入工作产品转换成可标识的输出工作产品** |
| CL2 | **已管理的** | 重点是把已管理的过程**制度化** |
| CL3 | **已定义级的** | 重点是把已定义的过程**制度化** |
| CL4 | **定量管理的** | 重点是**可定量管理**的过程制度化 |
| CL5 | **优化的** | 用**量化（统计学）手段改变和优化**过程域，满足客户改变与持续改进的需求 |

**阶段式 vs 连续式别混**：**阶段式看"组织整体到了第几级"（5 级）**；**连续式看"某一个过程域自身的能力等级"（CL0–CL5，6 级）**。题干说"**某个过程域**……"→ 连续式；说"**整个组织**……"→ 阶段式。

### 8.3 应试动作

背两串顺序：**CMM/CMMI 阶段式五级 = 初、重定管优**（CMMI 里"可重复"叫"已管理"）；**连续式 = CL0 未完成 → CL1 已执行 → CL2 已管理 → CL3 已定义 → CL4 定量管理 → CL5 优化**。做题先抓三个关键词（标准化=3、定量=4、持续改进=5），再判断问的是"整个组织"还是"某个过程域"。

## 第九节 案例题专攻：数据流图（约 15 分）

案例第一题一般是「文字说明 + 顶层图或 0 层图（缺数据流）」，固定三小问：补数据流、补数据存储或补外部实体、补数据字典。**全部答案都藏在说明文字里**，套路如下。

### 9.0 先认全 DFD 的四种元素（认不出元素就找不到答案）

| 元素 | 常见画法 | 表示什么 | 命名规则 |
|---|---|---|---|
| **外部实体** | 矩形 | 系统之外的**人、组织、外部系统**（顾客、餐厅、银行、支付网关） | 名词（"读者""支付网关"） |
| **加工** | 圆角矩形 / 圆圈 | 对数据做的**变换**（计算、校验、存库） | **动词 + 名词**（"接收订单""校验资格"） |
| **数据存储** | 开口矩形 / 双平行线 | **文件、表、库、清单** | 名词 + 类型（"订单文件""库存表"） |
| **数据流** | 带名字的箭头 | 数据的流动方向 | 名词（"订单""待处理订单"） |

**两条画法铁律（真题的判错依据）**：

1. **数据存储不能直接连外部实体**。外部实体要读文件，必须通过某个加工中转——例如「配送员从配送文件取餐通知」，正确画法是 **配送文件 →(配送任务)→ 加工 →(取餐通知)→ 配送员**，绝不能画成「配送文件 → 配送员」。
2. **DFD 不画控制流**。像"先判断是否逾期，再决定是否拒绝"这种逻辑，DFD 里只体现为**数据**的走向（多了/少了哪条流），不画带条件标注的控制箭头。

### 9.1 套路一：分层与平衡原则（判断"缺什么"的唯一依据）

- **顶层图**：整个系统算**一个**加工，只画外部实体和进出系统的数据流，不画数据存储；
- **0 层图**：把系统拆成几个主要加工，画出外部实体、加工、数据存储、数据流；
- **父子图必须平衡**：子图的输入/输出数据流，必须与父图中对应加工的输入/输出**一一对应**。父子图对不上 = 缺流，这就是补流题的判定依据。

### 9.2 套路二：逐句扫描说明找缺失数据流

说明里**每个动词句都对应一条数据流**（有些句子对应两条，见下）。做法是把它变成对账：

**第一步，把说明拆成"起点 → 终点 → 名字"的三元组**。以"系统按订单文件中的待处理订单，向相应餐厅发送订单信息"这一句为例，它藏着**两个**动作：

```
动作①  读文件：  订单文件  →（待处理订单）→ 加工②      ← 文件流向加工（读）
动作②  发出去：  加工②    →（订单信息）  → 餐厅        ← 加工流向外部实体
```

**一句话对应两条流**，是补流题最容易漏的地方——别以为一句只找一条。

**第二步，把三元组清单和图上已有的箭头逐条对账**，图上找不到的，就是答案。

**第三步，名字用说明原词**。题目通常明确要求"采用说明中的词汇"，说明写"订单信息"就照抄，不要改写成"订单数据"。

### 9.3 套路三：补流三要素与三类最易漏的流

**答案必须写全三要素：起点、终点、数据流名**——只写名字不给起终点，阅卷时按半分处理。

真题里最常漏的就是这三类：

| 类型 | 例子 | 为什么容易漏 |
|---|---|---|
| **加工 → 外部实体的反馈类流** | 订单确认、送达通知、拒绝提示 | 说明里写成"系统向××发送…"，容易被当成一句套话跳过 |
| **加工 ↔ 数据存储的读流** | 订单文件→加工（待处理订单） | 只记得"存文件"是流，忘了**"读文件"也是流** |
| **顶层有而 0 层没有的流** | 顶层图里的"订单信息→餐厅" | 只盯着 0 层图看，没回头和顶层图对照 |

**自查动作（做完必做）**：图上**每个加工都必须既有进入的流、又有出去的流**。发现有"只进不出"或"只出不进"的加工，那里一定缺流（原理见 9.7）。

### 9.4 套路四：补外部实体

**判据一：说明里出现在"向××提交/发送/通知"或"由××提供"位置的、系统以外的人或组织。**

- 是外部实体：**人**（顾客、读者、管理员）、**组织**（餐厅、供应商、银行）、**外部系统**（支付网关、短信平台、身份认证服务）；
- 不是外部实体：说明里的"**系统**""平台"指的是**正在建模的系统自身**，它是加工不是实体；数据库、文件是数据存储也不是实体。

**判据二：数一数说明里出现过的角色**。真题常让你"补出图中的外部实体"，答案个数就等于说明里出现的外部角色个数——漏一个通常是因为某句里角色只当宾语出现一次（如"系统向**顾客**发送送达通知"）。

**反例**：说明写"系统生成配送任务写入配送文件"，若把"系统"填成外部实体即错——它是 0 层图的整体，被拆成了各加工。

### 9.5 套路五：补数据存储（文件名）

**判据：说明里的名词中含"文件 / 表 / 库 / 清单 / 档案 / 日志 / 台账"这类词，且数据需要被保存下来。**

- 例：订单文件、配送文件、图书文件、读者文件、借阅记录表、库存清单；
- **反例（高频错）**：题目让填"数据存储"时，把"订单"填进去——"订单"是**数据流名**，"订单文件"才是存储名。**数据是内容、文件是容器**，别混。
- **方向也要判**：谁写（加工 → 文件）、谁读（文件 → 加工）。**一个文件通常既有入流也有出流**；只画了写没画读，就是漏流。

### 9.6 套路六：补加工名

加工名 = **动词 + 名词**，通常 2–6 个字，且必须与图上箭头吻合。三步定名：

**第一步，看这个加工有哪些输入流、哪些输出流**（箭头就是线索）；
**第二步，回说明里找"用这些输入产生这些输出"的那句话**；
**第三步，用说明里的动词短语命名**（"接收订单""分派订单""跟踪配送""处理还书"）。

**反例**：把加工名写成"处理"（太笼统）、"订单"（纯名词）、"系统"（不是加工名）、"接收订单并分派订单并跟踪配送"（一个加工干了三个加工的活）——四种都是错项。

### 9.7 DFD 的三种错误：黑洞、奇迹、灰洞（平衡的反面，选择题也考）

**黑洞 —— 加工有输入、无输出。** 成因：漏画了该加工的输出流，数据"进去就没了"。

**奇迹 —— 加工有输出、无输入。** 成因：漏画了该加工的输入流，数据"凭空产生"。

**灰洞 —— 加工有输入也有输出，但输入不足以产生该输出。** 成因：漏画了部分输入流，数据"不够用"。

**口诀**：**黑进不出、奇出不进、灰进不够出**。

**灰洞最难认，看例子**：某"处理还书"的加工，只画了「管理员→（还书请求）→加工」和「加工→（还书结果）→管理员」，看起来进和出都有。但"更新图书在馆状态"这件事**必须有图书文件里的在馆数据**才能做——输入不够，输出却凭空生成了，这就是灰洞。改法：补上 图书文件 →（在馆状态）→ 加工 与 加工 →（更新后的在馆状态）→ 图书文件。

**应试动作**：做补流题时，逐个数每个加工的进入流与流出流，三种错误当场就能查出来。

### 9.8 套路七：数据字典写法（五个记号背全）

| 记号 | 含义 | 例子 |
|---|---|---|
| `=` | **定义**为（由…组成） | `登录信息 = 学生 ID + 密码` |
| `+` | **与**（顺序连接） | `订单 = 顾客编号 + 菜品明细 + 送餐地址` |
| `{}` | **重复**（0 次或多次） | `菜品明细 = {菜品名 + 数量}` |
| `[ \| ]` | **或**（择一） | `付款方式 = [现金 \| 微信 \| 银行卡]` |
| `( )` | **可选**（可有可无） | `收货地址 = (省份) + 城市 + 街道` |

**口诀**：**等号组成、加号连接、花括号重复、方括号择一、圆括号可选**。

**反例（两个记号一换就错）**：用 `[]` 表示重复、用 `{}` 表示择一——这是最典型的写法错误。判别窍门：**开花（`{}`）像"一串"，方括号（`[]`）像"岔路"**——重复用花、择一用方。

（说明里给出的字段名要照抄原词，字段间的连接关系按说明的语义判断：能重复多次的加 `{}`，可能没有的加 `()`。）

### 9.9 应试动作

① **先数箭头再读说明**：逐个数每个加工的进入流/流出流，抓出"只进不出、只出不进、进不够出"的位置，那里必缺流；
② **说明逐句拆三元组**（起点、终点、名字），与图上对账，剩者即答案，名字抄原词，一句话可能对应两条流；
③ **补实体看"谁"**（人/组织/外部系统，"系统"自己不算）、**补存储看"文件/表/库"**（别拿数据流名冒充存储名）、**补加工名用"动词+名词"**；
④ 数据字典五个记号会默写，能现场写出 `XX = A + {B} + (C)` 的形式

   A. 黑洞  B. 奇迹  C. 灰洞  D. 黑盒

**二、案例题（数据流图：补外部实体、补数据存储、判断加工错误）**

阅读下列说明，回答问题 1 至问题 3。

【说明】某图书馆管理系统的图书借还与状态维护业务如下：

1. 读者向系统提交借书申请（含读者证号、图书条码）。
2. 系统根据读者证号，从读者文件中读取该读者的借阅资格与已借数量，进行借阅资格校验。
3. 校验通过后，系统从图书文件中读取该图书的在馆状态；将借阅记录写入借阅文件，同时向读者发送借阅成功通知。
4. 图书管理员向系统提交还书请求（含图书条码），系统将图书文件的在馆状态更新为"在馆"，并向管理员返回还书结果。

Top 层图外部实体与 0 层图一致。0 层图已画出四个加工：①处理借书申请、②校验借阅资格、③生成借阅记录、④处理还书；并画出了这些数据流：读者→①（借书申请）、①→②（读者证号）、②→③（校验结果）、①→读者（借阅成功通知）、管理员→④（还书请求）、④→管理员（还书结果）。

**问题 1**：指出该系统的外部实体有哪些。

**问题 2**：该系统需要哪些数据存储（文件）？并指出其中哪些文件被加工④读写。

**问题 3**：图中加工④"处理还书"只有"管理员→④（还书请求）"这条输入流和"④→管理员（还书结果）"这条输出流，没有任何与数据存储相连的流。请指出这属于 DFD 的哪种错误，说明理由，并给出正确的补法。

## 答案与解析

### 课后考题答案

**1. B**
"用户说不清需求 + 先做演示确认"是原型模型的标志特征。瀑布要需求明确；螺旋面向高风险大型项目（核心是风险分析）；V 模型是测试与开发阶段对应的瀑布变体。

**2. B**
螺旋模型 = 瀑布 + 原型 + **风险分析**，风险分析是它的灵魂。文档驱动是瀑布的特征（A 干扰项）。

**3. C**
结对编程、测试驱动开发、持续集成是 XP 的工程实践；每日站会、Sprint、产品负责人是 Scrum 框架角色与仪式。

**4. C**
"功能无关 + 必须同一时间执行" = 时间内聚（初始化是典型）。若按固定次序执行则属过程内聚——本题关键词是"同时执行"。

**5. B**
传"记录/数据结构"= 标记耦合；只传简单变量才是数据耦合。控制耦合传的是控制信号；公共耦合是共用全局数据区而非参数传递。

**6. B**
"同一全局**数据结构**（数组）"→ 公共耦合；若只是同一个全局简单变量则是外部耦合——本题是数组（数据结构），选公共耦合。

**7. C**
排序：语句 < 判定 < 条件 < 判定/条件 < 条件组合 < **路径**。路径覆盖要求走遍所有执行路径，最强。

**8. A**
条件覆盖只管"每个条件取到真、假"，不管"判定的真假分支是否都执行"——用例 (A=1,B=0)、(A=0,B=1) 两个条件真假都取遍，但判定恒为假，真分支没走过。这正是排序中条件覆盖与判定覆盖互不包含、需要"判定/条件覆盖"合并保证的原因。

**9. C**
V(G) = E − N + 2 = 10 − 8 + 2 = **4**。验算：若图有 3 个判定节点，V(G) = 3+1 = 4 ✓。

**10. C**
边界值分析在边界及其外侧邻值取数：0、1、100、101。只取 1 和 100 会漏掉"边界外一点点"的高发错误区。

**11. A**
单元 → 集成 → 确认 → 系统 → 验收。确认测试对照需求规格说明书，验收测试由用户参与。

**12. B**
适应"环境变化"（OS 升级）= 适应性维护。改正性修已发生错误；完善性扩功能；预防性防患未然。

**13. C**
完善性维护占一半以上（约 50%–60%），直接背。

**14. B**
可靠性子特性 = 成熟性、容错性、易恢复性。功能性子特性含适合性、准确性、互操作性、安全性等。

**15. B**
"文档化、标准化、全组织统一采用" = 已定义级（3 级）。可重复级是"能重复以往成功"；已管理级的关键词是"定量"。

### 案例题答案

**问题 1（缺失数据流，共 5 条）**：

逐句扫描说明，每句拆成"起点 → 终点 → 名字"的三元组，注意**一句话可能对应两条流**：

- 句 2「系统**按订单文件中的待处理订单**，向相应餐厅发送订单信息」藏着两条：**订单文件 → 加工②（待处理订单）**（读文件）、**加工② → 餐厅（订单信息）**；
- 句 4「配送员从**配送文件**获取取餐通知」也藏两条：**配送文件 → 加工③（配送任务）**（读文件）、**加工③ → 配送员（取餐通知）**——外部实体不能直接读文件，必须由加工中转；
- 句 5「系统**更新订单状态**」一条：**加工③ → 订单文件（订单状态）**（写文件）。

| 缺失数据流 | 起点 | 终点 | 名称 |
|---|---|---|---|
| 1 | 订单文件 | 加工② 分派订单 | 待处理订单 |
| 2 | 加工② 分派订单 | 餐厅 | 订单信息 |
| 3 | 配送文件 | 加工③ 跟踪配送 | 配送任务 |
| 4 | 加工③ 跟踪配送 | 配送员 | 取餐通知 |
| 5 | 加工③ 跟踪配送 | 订单文件 | 订单状态（更新） |

**三个易漏点**：① **"读文件"也是流**——图中只画了写入文件的流（①→订单文件、②→配送文件），一条读流都没有，而说明里明写"按订单文件中的待处理订单""从配送文件获取"；② **一句话可能对应两条流**（句 2、句 4 都是），一句话只找一条是这道题最常见的丢分原因；③ 反馈类流（确认 / 通知）最容易被当成套话跳过。

**自查**：做完后逐个数每个加工的进出流——加工②若少了"订单文件 → ②"就成了灰洞（进不够出）；加工③若少了"配送文件 → ③"，就凭空发出了取餐通知，变成奇迹。

**问题 2**：

- **读配送文件**：获取配送任务与配送进度，使"送达确认"能与配送文件中的任务对应起来——这就是问题 1 的缺失流 3（配送文件 → 加工③）；
- **写订单文件**：按送达确认把订单状态更新为"已送达"——这就是问题 1 的缺失流 5（加工③ → 订单文件）。

**与问题 1 的关系**：问题 1 问的是"**图上缺哪些箭头**"（画法），本题问的是"加工**为什么要**碰这些文件"（用途），同一件事的两个角度，考场上一问一答都要写。

**多画会被判错**：加工③**不需要读订单文件**——它要的"订单号"可以从配送任务里带过来，说明里也没有"读取订单信息"这句话。补流题只补**说明中写到过**的流，自己推理出来的流不算。

**问题 3**：

```
订单 = 顾客编号 + 菜品明细 + 送餐地址
菜品明细 = {菜品名 + 数量}
```

（`{}` 表示可重复出现；若考试给出字段更细的说明，按说明原词逐项列出。）

### 精华题答案

**1. ① 瀑布模型（需求明确、阶段评审）② 原型模型（需求模糊、先演示确认）③ 螺旋模型（高风险大型项目、每圈风险分析）④ 敏捷（Scrum/XP，短迭代拥抱变化）。**
识别口诀：明确瀑布、模糊原型、高风险螺旋、多变敏捷。

**2. ① 逻辑内聚**（逻辑相似但功能无关，按参数分支执行不同动作）；**② 通信内聚**（统计、排序、打印都是对**同一批成绩数据**的不同操作，彼此没有"输出即输入"的接力关系）；**③ 偶然内聚**（毫无关系硬凑）。
易混点：若题干改成"读数据 → 加工 → 把结果写回文件"这种**前一步输出是后一步输入**的接力链，则是顺序内聚——判别标准是看动作之间有没有数据接力。

**3. ① 控制耦合**（传开关标志 = 控制信号）；**② 数据耦合**（简单变量）；**③ 标记耦合**（整条记录结构）；**④ 公共耦合**（直接修改同一全局数据——注意若是"直接进入对方模块内部改"则是内容耦合，本题是共享全局变量区，属公共耦合）。

**4. V(G) = E − N + 2 = 12 − 9 + 2 = 5**；判定节点数 + 1 = 4 + 1 = **5**。两种算法结果一致 ✓。

**5. 满足条件覆盖**（A、B 两条件的真、假取值都各出现了一次）；**不满足判定覆盖**（两次判定结果都是假，s=1 的真分支从未执行）。这也是"条件覆盖不包含判定覆盖"的实例——想同时保证要用判定/条件覆盖或更强的条件组合覆盖。

**6. ① 改正性**（修已发生的 bug）② **预防性**（为将来的修改提前重构，防患未然）③ **完善性**（扩充新功能）④ **适应性**（适应数据库环境更换）。易混点：② 是"还没发生"→ 预防，不是改正。

**7. 第 4 级（已管理级）**。关键词"定量度量与控制"；若描述为"持续改进、采用新技术"则是第 5 级优化级。

### 补充题答案

**选择题**

**1. C**
"模块规模越小越好"是模块设计原则里**固定的错项**。原则①说的正好相反：模块过大，内部可能揉进不同类型的功能，需要进一步划分；但**过小也不对**——系统复杂度反而增加，**模块之间的调用过于频繁，降低了模块的独立性**。A 是扇入的原话定义；B 是原则④（作用域 ⊆ 控制域）；D 是原则②的原话（深度过大 → 有些模块过于简单 → 考虑合并）。

**2. B**
先数清楚控制流图的**节点**和**边**：

```
节点（7 个）：S1、判定A、S2、判定B、S3、S4、S5
边（8 条）：
  S1 → A        A → S2   A → B
  S2 → S5       B → S3   B → S4
  S3 → S5       S4 → S5
```

算法一（E − N + 2）：V(G) = 8 − 7 + 2 = **3**。
算法二（判定节点数 + 1）：判定只有 A、B 两个 → 2 + 1 = **3** ✓ 两法一致。
干扰项：A = 2 是判定节点数本身（漏了 +1）；D = 8 是把边数直接当复杂度；C = 4 是把三岔汇合点 S5 也误当成判定节点（3 + 1）。

**3. B**
沟通路径 = n(n−1)/2 = 6 × 5 ÷ 2 = **15**。
反向验算：n = 6 的两两配对组合数 C(6,2) = (6×5)/(2×1) = 15 ✓。
干扰项：C = 30 是漏了"每次沟通被两端各算一次"（忘了 ÷2）；D = 36 误用了 n²；A = 6 直接拿人数当路径数（注意**有主程序员**时才是 n − 1 = 5）。

**4. B**
这是一对"互缺"的图：**甘特图有"并行"没"依赖"**（能看清各任务何时起止、哪些在并行），**PERT 图有"依赖"没"并行"**（能看清依赖关系并据此确定关键路径）。A 把依赖关系这个优点挂到了甘特图上；C 正好把两者互换；D 错在 PERT 图能反映依赖关系与关键路径，不只是起止时间。**题干问"缺哪一句"，两个形容词一换就是错项。**

**5. A**
**有输入、无输出 = 黑洞**（黑进不出）。奇迹是"有输出、无输入"；灰洞是"输入输出都有，但**输入不足以产生该输出**"；黑盒是测试方法名，不是 DFD 的错误类型。

**案例题**

**问题 1：外部实体共 2 个——读者、图书管理员。**

判据是"出现在『向××提交 / 向××发送 / 向××返回』位置、且是系统以外的人或组织"：

- 句 1「**读者**向系统提交借书申请」、句 3「向**读者**发送借阅成功通知」→ 读者；
- 句 4「**图书管理员**向系统提交还书请求」→ 图书管理员。

**两个易错点**：① 不要把"**系统**"填成外部实体——它是被拆成四个加工的整体，是被建模的对象；② 不要漏掉"读者"——它在句 1 当主语、句 3 当宾语各出现一次，只看主语就很容易跳过。

**问题 2：数据存储共 3 个——读者文件、图书文件、借阅文件。**

加工④"处理还书"读写的文件：

| 数据流 | 起点 | 终点 | 作用 |
|---|---|---|---|
| 图书在馆状态 | 图书文件 | 加工④ | **读**：确认该图书条码对应的书存在、当前是什么状态（不读就无从"更新"） |
| 更新后的在馆状态 | 加工④ | 图书文件 | **写**：把该图书的状态更新为"在馆" |

另外两个文件的归属：**读者文件**由加工②读（句 2「从读者文件中读取该读者的借阅资格与已借数量」）；**借阅文件**由加工③写（句 3「将借阅记录写入借阅文件」）。

**判据提醒**：数据存储的名一定是"**名词 + 文件 / 表 / 库 / 清单**"。若把"借书申请""还书请求""借阅记录"直接填成数据存储就错了——**这些是数据流名（内容），不是存储名（容器）**。

**问题 3：属于「灰洞」。**

**理由**：先按顺序排除两种更简单的错误——加工④**有输出**（④→管理员：还书结果），所以不是黑洞（有进无出）；它**也有输入**（管理员→④：还书请求），所以也不是奇迹（有出无进）。但它仍不完整：把在馆状态"更新为在馆"这件事，**必须有图书文件中的在馆数据**作为依据，而"还书请求"里只有图书条码，**输入不足以产生"还书结果"这个输出**——这就是**灰洞（进不够出）**。

**正确补法**：补两条与图书文件之间的流——

```
①  图书文件 →（图书在馆状态）→ 加工④        ← 读：拿到当前状态
②  加工④ →（更新后的在馆状态）→ 图书文件    ← 写：把状态改为"在馆"
```

**通用判断顺序**：① 无输出 → 黑洞；② 无输入 → 奇迹；③ 进、出都有，再问"这点输入够不够产生这个输出" → 不够就是灰洞。口诀：**黑进不出、奇出不进、灰进不够出**。
