# 08.2 信息摘要、数字签名与证书 ★★★

**动机**：验证一份大文件"有没有被改过一个字节"，把整个文件倒来倒去比对太笨。办法：用 Hash 函数给文件算出一个短短的"指纹"——**信息摘要**。指纹变了哪怕一点点，文件必然动过。

### 3.1 Hash 函数的四大特性

1. **定长输出**：无论输入多长（1 字节还是 1GB），输出固定长度；
2. **单向性**：从摘要反推出原文，计算上不可行——所以也叫**单向散列函数**；
3. **抗碰撞性**：找两个不同输入对应同一摘要，计算上不可行；
4. **雪崩效应**：原文改动 1 个比特，摘要面目全非。

**代表算法**：**MD5**（摘要 **128** 位）、**SHA-1**（摘要 **160** 位）、SHA-256、国密 SM3。

### 3.2 摘要 ≠ 加密（第二易错点）

**反例演示**：选项「MD5 是一种加密算法」——**错**。摘要有两个"非加密"特征：① **无密钥**（任何人算同一个文件得到的摘要都一样）；② **不可逆**（加密要求能解密还原，摘要不能）。摘要的用途是**完整性验证**，不是保密。

**应试动作**：背"MD5-128、SHA-1-160"两个数字 + 一句"Hash 无密钥、不可逆、管完整性"。考场上问"属于信息摘要算法特性的是"，挑"定长输出/单向/抗碰撞"；问"MD5 摘要长度"，答 128 位。

## 第四节 数字签名 ★★★（永恒考点，必须能默写流程）

**动机**：公钥体系解决了保密，但有个新漏洞——乙收到"甲"发来的消息，怎么确认真是甲发的、而不是别人冒名的？而且甲事后赖账说"我没发过"怎么办？答案：让甲用**只有自己才有的私钥**处理一段消息。全世界只有甲能这么干，这就是**数字签名**——它一举解决**真实性**（确是甲发）和**不可否认性**（甲不能赖账），顺带用摘要比对保证**完整性**。

### 4.1 标准签名与验证流程（四步，背到能默写）

以甲发消息给乙为例：

1. **生成摘要**：甲用**单向 Hash 函数**对正文算出信息摘要；
2. **签名**：甲用**自己的私钥**对摘要加密——这一步就是"签名"；
3. **发送**：甲把**正文 + 已签名的摘要**一起发给乙；
4. **验证**：乙用**同一个 Hash 函数**对收到的正文重新算出新摘要；再用**甲的公钥**解开签名得到原摘要；两者一致 → 消息确实出自甲、且中途未被改。

**为什么只签"摘要"、不签"全文"？**两个原因，背下来回答"为什么不能对全文签名"的题：① **慢**——签名用的是非对称（公钥）运算，天生慢，大文件全文签一遍开销巨大；② **摘要短、够等价**——Hash 摘要定长（如 128 位）且有雪崩效应，正文动一个字节摘要就面目全非，比对这个短摘要**完全等价于**比对整篇全文。所以标准做法永远是"**先算摘要、再签摘要**"——这正是 Hash 在数字签名里不可替代的位置。

### 4.2 方向速查表（考场填空就查这张）

| 动作 | 谁的什么钥 | 为什么 |
|---|---|---|
| 甲**签名** | **甲的私钥** | 私钥唯一，签了就赖不掉 |
| 乙**验证签名** | **甲的公钥** | 公钥配对私钥，能解开才证明是甲签的 |
| 乙**验证数字证书** | **CA 的公钥** | 证书是 CA 签的名（见第五节） |
| 发密文给对方 | **对方的公钥** | 保密方向 |

**反例演示**：真题选项里的三大错误方向——「乙用**乙的公钥**验证」（错，验证必须用**发方**甲的公钥，乙自己的钥匙对是拆"发给乙的密文"用的）；「甲用**甲的公钥**签名」（错，公钥人人有，谁都能"签"，就证明不了身份）；「甲用**乙的私钥**签名」（错，乙的私钥甲根本拿不到）。

### 4.3 签名 + 保密，一步不乱（真题最爱组合）

**动机**：签名流程里"正文 + 签名摘要"是**明文**发的——只解决了身份和完整性，**没解决机密性**。若既要保密又要签名，就在第 3 步外面再套一层数字信封（2.3 节）。完整流程（背诵模板）：

> 甲：Hash 求摘要 → **甲私钥**签名摘要 → （正文+签名）用 **乙公钥** 加密发出
> 乙：**乙私钥**解密 → **甲公钥**验签名 → 同一 Hash 重算摘要比对

记忆口诀："**先签后封，私签公验；封用收方公，拆用收方私**"。

**应试动作**：这是本课最高频考法。把 4.2 的速查表背熟，无论题干怎么换人名（甲乙/AB/发送接收方），第一步先问自己"这个动作是**保密**还是**认证**"——保密走对方公钥，认证走自己私钥。案例题风格题见本课末尾第 16 题。

## 第五节 数字证书与 CA ★★

**动机**：非对称体系还剩最后一个窟窿——**公钥怎么证明是本人的**？乙手里那把"甲的公钥"，万一是攻击者伪造的（攻击者把自己的公钥冒充成甲的发给你），后面整个签名验证都白搭。**数字证书**就是给公钥办的"身份证"：由一个大家信任的权威机构 **CA（证书授权中心）**，把"用户身份 + 用户公钥"捆在一起并盖章。

### 5.1 证书里有什么、怎么验证

- **证书内容**：用户身份信息、**用户的公钥**、证书有效期、序列号，以及最关键的——**CA 用自己的私钥对证书摘要做的数字签名**。
- **验证证书（三步，别只停在"验签名"）**：拿到一张证书，除了用 **CA 的公钥**验 CA 的签名，还要再查两件事才算有效：
  1. **验签名**：用 **CA 的公钥**解开证书上的 CA 签名，比对摘要 → 确认这张证书确实是 CA 签发的、不是伪造的；
  2. **查有效期**：确认证书**当前在有效期内**（未过期、也未被提前撤销）；
  3. **查吊销**：到 CA 或证书库查这张证书**是否已被列入吊销列表（CRL）**——私钥泄露、用户离职都可能让 CA 提前作废证书，正文却仍"未过期"。
  
  三步全过，才证明"**这把公钥确实属于这个人、且当前有效**"。

- **信任链与根证书**：未必每个 CA 都天生被信任。现实里是一串"**信任链**"——顶层有一个大家都信任的**根证书**（内置在操作系统/浏览器里），它给下层 CA 签发证书，下层 CA 再给普通用户签发；验证时逐级向上，直到找到一个你本来就信任的根证书为止。选择题若问"浏览器为什么凭内置根证书就能信某个 CA 签的证书"，本质就是靠这条自下而上的信任链。
- CA 的职责：证书的签发、更新、**撤销（吊销列表 CRL）**、管理。

### 5.2 与第 6 课联动

浏览器地址栏的 **HTTPS**（端口 443，见 [06-计算机网络.md](../06-计算机网络/06-应用层协议.md)）握手时就用到这一套：服务器出示**数字证书**，浏览器用 **CA 的公钥**验证书，确认服务器身份后再协商对称会话密钥加密通信——"证书验身份 + 对称管数据"的组合再现。

**反例演示**：选项「验证数字证书要用证书持有者的公钥」——**错**。证书上的签名是 **CA** 签的，所以要用 **CA 的公钥**验。持有者的公钥是证书**里装的东西**，不是验证工具。

**应试动作**：背两句——"证书 = 身份 + 公钥 + CA 签名"；"验证书用 CA 的公钥，验证普通签名用发送者的公钥"。考场给场景问"浏览器如何确认某网站公钥的真实性"，答"用 CA 公钥验证网站的数字证书"。
