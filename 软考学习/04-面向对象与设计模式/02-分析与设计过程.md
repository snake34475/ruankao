# 04.2 面向对象分析与设计过程 ★★

### 2.1 为什么先要有"过程"

很多人以为"面向对象"就是"写类"。但类从哪来？属性怎么定？关系怎么画？——**不解决这些问题，画出来的类图就是凭感觉摆的**。OOA（面向对象分析）解决"**要什么**"，OOD（面向对象设计）解决"**怎么搭**"，两步各有一套固定动作。考试既考选择题（问"下面哪一步属于 OOA"），更是 UML 案例题的**解题骨架**——案例题让你补类名、补方法名，靠的就是 OOD 的"定义属性/定义服务"这两步。

### 2.2 OOA 四步（背顺序，选择题按顺序出干扰项）★★

| 步骤 | 做什么 | 落在案例题里的动作 |
|---|---|---|
| ① **认定对象** | 从需求描述里挑出**名词**候选 | 说明文字里的名词就是类名候选（读者、图书、借阅记录） |
| ② **组织对象** | 把同类对象**抽象成类**，抽出公共属性 | 学生读者/教师读者 → 抽父类"读者" |
| ③ **描述对象间的相互作用** | 谁和谁有往来、什么关系、多重性 | 读者 1 — 1..\* 借阅记录 |
| ④ **基于对象的操作** | 每个对象要提供哪些操作（服务） | 补**方法名**（checkOut、getForCheckOut） |

**记忆口诀**：**认对象 → 组类 → 拉关系 → 定操作**（"认组拉定"）。

### 2.3 OOD 五步 ★★

| 步骤 | 做什么 |
|---|---|
| ① **识别类及对象** | 在分析结果上补足实现层面的类（控制类、边界类、工具类） |
| ② **定义属性** | 每个类需要存哪些数据（书号、书名、定价） |
| ③ **定义服务** | 每个类要对外提供什么方法（借出、归还、计算应还日期） |
| ④ **识别关系** | 泛化/关联/聚合/组合/依赖，以及多重性 |
| ⑤ **识别包** | 把类按职责分组打包，定义包间依赖 |

**反例演示（易错）**：考题问"下列哪一项属于**面向对象设计**而非分析"——判别标准是"**有没有落到实现细节**"。**"认定对象"是分析**（还在业务层挑名词），**"定义属性/服务"是设计**（已经在写类的成员了）。别把"识别类及对象"错认成分析的"认定对象"：前者是实现视角的补全，后者是需求视角的提取。

### 2.4 OOD 七大原则（送分题，也决定"为什么这么设计"）★★

这七条是判断题与案例题"为什么要用设计模式"的**答题依据**——注意它们的共同指向：**都反对"改一处牵动全身"的紧耦合写法**。

| 原则 | 一句话 | 反对什么写法（反例） |
|---|---|---|
| **单一职责**（SRP） | 一个类只负责一件事 | 一个 `BookManager` 既管借还、又管打印报表、又管发短信 |
| **开放-封闭**（OCP） | **对扩展开放、对修改封闭** | 每加一种支付方式就去改 `PaymentService` 里的 `switch` |
| **里氏替换**（LSP） | 子类**可以替换**父类（不破坏父类的约定） | 子类重写后抛异常/收紧前置条件，父类能用的地方用不了 |
| **依赖倒置**（DIP） | 依赖**抽象**，不依赖具体实现；**针对接口编程** | 高层业务类里直接 `new MySQLDao()` |
| **接口隔离**（ISP） | 多个专门接口优于一个总接口 | 一个 20 个方法的 `IAllService`，实现类被迫空实现一堆方法 |
| **组合重用**（CRP） | 尽量用**组合**而不是继承来重用 | 为了复用几个方法就继承一个不相干的类（继承层级爆炸） |
| **迪米特**（LoD，最少知识） | 一个对象对别的对象**知道得越少越好** | `a.getB().getC().getD().doX()` 层层穿透调用 |

**依赖倒置的经典原话**（真题原句）："**抽象不应该依赖于细节，细节应该依赖于抽象**；高层模块不应该依赖低层模块，两者都应该依赖于抽象。"——这句话只要出现，答案就是**依赖倒置原则**。

**里氏替换与多态的关系**：多态能成立，前提正是里氏替换——"父类的地方放子类不出错"。所以 LSP 是**多态的原则性表述**。

### 2.5 包设计原则（低频，认识就够）

另有六条更细的包（package）级原则，考试偶见，**不要与七大原则混记**：

| 原则 | 一句话 |
|---|---|
| 重用发布等价 | 重用的粒度就是发布的粒度 |
| 共同封闭 | 一个变化应只影响一个包内的类，不波及其他包 |
| 共同重用 | 重用了包中一个类，就得重用包中所有类 |
| 无环依赖 | 包的依赖图中**不允许有环** |
| 稳定依赖 | 朝着**稳定**的方向依赖（不稳定的包依赖稳定的包） |
| 稳定抽象 | 包的**抽象程度应与其稳定程度一致**（越稳定越抽象） |

**真题原题形式**："若重用了一个包中的某个类，就要重用该包中的所有类，这属于（ ）原则" → **共同重用原则**。这句题干里的"某个 → 所有"就是它的唯一识别特征。

**应试动作**：七大原则**必须背名字 + 一句话**（选择题直接考原话）；包原则只背"共同重用""共同封闭"两条题眼，其余见过即可。案例题里问"采用什么设计模式更好、为什么"，答题时**顺手引用原则名**（如"符合开放-封闭原则，新增算法无需修改原有代码"）能显著提分。
