03.12 答案与解析

课后考题答案

1. B "用户说不清需求 + 先做演示确认"是原型模型的标志特征。瀑布要需求明确；螺旋面向高风险大型项目（核心是风险分析）；V 模型是测试与开发阶段对应的瀑布变体。

2. B 螺旋模型 = 瀑布 + 原型 + 风险分析，风险分析是它的灵魂。文档驱动是瀑布的特征（A 干扰项）。

3. C 结对编程、测试驱动开发、持续集成是 XP 的工程实践；每日站会、Sprint、产品负责人是 Scrum 框架角色与仪式。

4. C "功能无关 + 必须同一时间执行" = 时间内聚（初始化是典型）。若按固定次序执行则属过程内聚——本题关键词是"同时执行"。

5. B 传"记录/数据结构"= 标记耦合；只传简单变量才是数据耦合。控制耦合传的是控制信号；公共耦合是共用全局数据区而非参数传递。

6. B "同一全局数据结构（数组）"→ 公共耦合；若只是同一个全局简单变量则是外部耦合——本题是数组（数据结构），选公共耦合。

7. C 排序：语句 < 判定 < 条件 < 判定/条件 < 条件组合 < 路径。路径覆盖要求走遍所有执行路径，最强。

8. A 条件覆盖只管"每个条件取到真、假"，不管"判定的真假分支是否都执行"——用例 (A=1,B=0)、(A=0,B=1) 两个条件真假都取遍，但判定恒为假，真分支没走过。这正是排序中条件覆盖与判定覆盖互不包含、需要"判定/条件覆盖"合并保证的原因。

9. C V(G) = E − N + 2 = 10 − 8 + 2 = 4。验算：若图有 3 个判定节点，V(G) = 3+1 = 4 ✓。

10. C 边界值分析在边界及其外侧邻值取数：0、1、100、101。只取 1 和 100 会漏掉"边界外一点点"的高发错误区。

11. A 单元 → 集成 → 确认 → 系统 → 验收。确认测试对照需求规格说明书，验收测试由用户参与。

12. B 适应"环境变化"（OS 升级）= 适应性维护。改正性修已发生错误；完善性扩功能；预防性防患未然。

13. C 完善性维护占一半以上（约 50%–60%），直接背。

14. B 可靠性子特性 = 成熟性、容错性、易恢复性。功能性子特性含适合性、准确性、互操作性、安全性等。

15. B "文档化、标准化、全组织统一采用" = 已定义级（3 级）。可重复级是"能重复以往成功"；已管理级的关键词是"定量"。

案例题答案

问题 1（缺失数据流，共 5 条）：

逐句扫描说明，每句拆成"起点 → 终点 → 名字"的三元组，注意一句话可能对应两条流：

  • 句 2「系统按订单文件中的待处理订单，向相应餐厅发送订单信息」藏着两条：订单文件 → 加工②（待处理订单）（读文件）、加工② → 餐厅（订单信息）；
  • 句 4「配送员从配送文件获取取餐通知」也藏两条：配送文件 → 加工③（配送任务）（读文件）、加工③ → 配送员（取餐通知）——外部实体不能直接读文件，必须由加工中转；
  • 句 5「系统更新订单状态」一条：加工③ → 订单文件（订单状态）（写文件）。
缺失数据流 起点 终点 名称
1 订单文件 加工② 分派订单 待处理订单
2 加工② 分派订单 餐厅 订单信息
3 配送文件 加工③ 跟踪配送 配送任务
4 加工③ 跟踪配送 配送员 取餐通知
5 加工③ 跟踪配送 订单文件 订单状态（更新）

三个易漏点：① "读文件"也是流——图中只画了写入文件的流（①→订单文件、②→配送文件），一条读流都没有，而说明里明写"按订单文件中的待处理订单""从配送文件获取"；② 一句话可能对应两条流（句 2、句 4 都是），一句话只找一条是这道题最常见的丢分原因；③ 反馈类流（确认 / 通知）最容易被当成套话跳过。

自查：做完后逐个数每个加工的进出流——加工②若少了"订单文件 → ②"就成了灰洞（进不够出）；加工③若少了"配送文件 → ③"，就凭空发出了取餐通知，变成奇迹。

问题 2：

  • 读配送文件：获取配送任务与配送进度，使"送达确认"能与配送文件中的任务对应起来——这就是问题 1 的缺失流 3（配送文件 → 加工③）；
  • 写订单文件：按送达确认把订单状态更新为"已送达"——这就是问题 1 的缺失流 5（加工③ → 订单文件）。

与问题 1 的关系：问题 1 问的是"图上缺哪些箭头"（画法），本题问的是"加工为什么要碰这些文件"（用途），同一件事的两个角度，考场上一问一答都要写。

多画会被判错：加工③不需要读订单文件——它要的"订单号"可以从配送任务里带过来，说明里也没有"读取订单信息"这句话。补流题只补说明中写到过的流，自己推理出来的流不算。

问题 3：

订单 = 顾客编号 + 菜品明细 + 送餐地址
菜品明细 = {菜品名 + 数量}

（{} 表示可重复出现；若考试给出字段更细的说明，按说明原词逐项列出。）

精华题答案

1. ① 瀑布模型（需求明确、阶段评审）② 原型模型（需求模糊、先演示确认）③ 螺旋模型（高风险大型项目、每圈风险分析）④ 敏捷（Scrum/XP，短迭代拥抱变化）。 识别口诀：明确瀑布、模糊原型、高风险螺旋、多变敏捷。

2. ① 逻辑内聚（逻辑相似但功能无关，按参数分支执行不同动作）；② 通信内聚（统计、排序、打印都是对同一批成绩数据的不同操作，彼此没有"输出即输入"的接力关系）；③ 偶然内聚（毫无关系硬凑）。 易混点：若题干改成"读数据 → 加工 → 把结果写回文件"这种前一步输出是后一步输入的接力链，则是顺序内聚——判别标准是看动作之间有没有数据接力。

3. ① 控制耦合（传开关标志 = 控制信号）；② 数据耦合（简单变量）；③ 标记耦合（整条记录结构）；④ 公共耦合（直接修改同一全局数据——注意若是"直接进入对方模块内部改"则是内容耦合，本题是共享全局变量区，属公共耦合）。

4. V(G) = E − N + 2 = 12 − 9 + 2 = 5；判定节点数 + 1 = 4 + 1 = 5。两种算法结果一致 ✓。

5. 满足条件覆盖（A、B 两条件的真、假取值都各出现了一次）；不满足判定覆盖（两次判定结果都是假，s=1 的真分支从未执行）。这也是"条件覆盖不包含判定覆盖"的实例——想同时保证要用判定/条件覆盖或更强的条件组合覆盖。

6. ① 改正性（修已发生的 bug）② 预防性（为将来的修改提前重构，防患未然）③ 完善性（扩充新功能）④ 适应性（适应数据库环境更换）。易混点：② 是"还没发生"→ 预防，不是改正。

7. 第 4 级（已管理级）。关键词"定量度量与控制"；若描述为"持续改进、采用新技术"则是第 5 级优化级。

补充题答案

选择题

1. C "模块规模越小越好"是模块设计原则里固定的错项。原则①说的正好相反：模块过大，内部可能揉进不同类型的功能，需要进一步划分；但过小也不对——系统复杂度反而增加，模块之间的调用过于频繁，降低了模块的独立性。A 是扇入的原话定义；B 是原则④（作用域 ⊆ 控制域）；D 是原则②的原话（深度过大 → 有些模块过于简单 → 考虑合并）。

2. B 先数清楚控制流图的节点和边：

节点（7 个）：S1、判定A、S2、判定B、S3、S4、S5
边（8 条）：
  S1 → A        A → S2   A → B
  S2 → S5       B → S3   B → S4
  S3 → S5       S4 → S5

算法一（E − N + 2）：V(G) = 8 − 7 + 2 = 3。 算法二（判定节点数 + 1）：判定只有 A、B 两个 → 2 + 1 = 3 ✓ 两法一致。 干扰项：A = 2 是判定节点数本身（漏了 +1）；D = 8 是把边数直接当复杂度；C = 4 是把三岔汇合点 S5 也误当成判定节点（3 + 1）。

3. B 沟通路径 = n(n−1)/2 = 6 × 5 ÷ 2 = 15。 反向验算：n = 6 的两两配对组合数 C(6,2) = (6×5)/(2×1) = 15 ✓。 干扰项：C = 30 是漏了"每次沟通被两端各算一次"（忘了 ÷2）；D = 36 误用了 n²；A = 6 直接拿人数当路径数（注意有主程序员时才是 n − 1 = 5）。

4. B 这是一对"互缺"的图：甘特图有"并行"没"依赖"（能看清各任务何时起止、哪些在并行），PERT 图有"依赖"没"并行"（能看清依赖关系并据此确定关键路径）。A 把依赖关系这个优点挂到了甘特图上；C 正好把两者互换；D 错在 PERT 图能反映依赖关系与关键路径，不只是起止时间。题干问"缺哪一句"，两个形容词一换就是错项。

5. A 有输入、无输出 = 黑洞（黑进不出）。奇迹是"有输出、无输入"；灰洞是"输入输出都有，但输入不足以产生该输出"；黑盒是测试方法名，不是 DFD 的错误类型。

案例题

问题 1：外部实体共 2 个——读者、图书管理员。

判据是"出现在『向××提交 / 向××发送 / 向××返回』位置、且是系统以外的人或组织"：

  • 句 1「读者向系统提交借书申请」、句 3「向读者发送借阅成功通知」→ 读者；
  • 句 4「图书管理员向系统提交还书请求」→ 图书管理员。

两个易错点：① 不要把"系统"填成外部实体——它是被拆成四个加工的整体，是被建模的对象；② 不要漏掉"读者"——它在句 1 当主语、句 3 当宾语各出现一次，只看主语就很容易跳过。

问题 2：数据存储共 3 个——读者文件、图书文件、借阅文件。

加工④"处理还书"读写的文件：

数据流 起点 终点 作用
图书在馆状态 图书文件 加工④ 读：确认该图书条码对应的书存在、当前是什么状态（不读就无从"更新"）
更新后的在馆状态 加工④ 图书文件 写：把该图书的状态更新为"在馆"

另外两个文件的归属：读者文件由加工②读（句 2「从读者文件中读取该读者的借阅资格与已借数量」）；借阅文件由加工③写（句 3「将借阅记录写入借阅文件」）。

判据提醒：数据存储的名一定是"名词 + 文件 / 表 / 库 / 清单"。若把"借书申请""还书请求""借阅记录"直接填成数据存储就错了——这些是数据流名（内容），不是存储名（容器）。

问题 3：属于「灰洞」。

理由：先按顺序排除两种更简单的错误——加工④有输出（④→管理员：还书结果），所以不是黑洞（有进无出）；它也有输入（管理员→④：还书请求），所以也不是奇迹（有出无进）。但它仍不完整：把在馆状态"更新为在馆"这件事，必须有图书文件中的在馆数据作为依据，而"还书请求"里只有图书条码，输入不足以产生"还书结果"这个输出——这就是灰洞（进不够出）。

正确补法：补两条与图书文件之间的流——

①  图书文件 →（图书在馆状态）→ 加工④        ← 读：拿到当前状态
②  加工④ →（更新后的在馆状态）→ 图书文件    ← 写：把状态改为"在馆"

通用判断顺序：① 无输出 → 黑洞；② 无输入 → 奇迹；③ 进、出都有，再问"这点输入够不够产生这个输出" → 不够就是灰洞。口诀：黑进不出、奇出不进、灰进不够出。
