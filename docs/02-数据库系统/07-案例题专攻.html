02.7 案例题专攻：数据库设计 ​

案例第 2 题一般是"业务说明 + 不完整 E-R 图 + 关系模式 + SQL 填空"，三小问固定套路：

套路一：E-R 图补全——读句子找联系 ​

题干每个动词都暗示一条联系："学生选修课程""教师讲授课程""部门聘用员工"。补空时：

  1. 先数图中已有几实几联系，句子里的名词 = 实体、动词 = 联系；
  2. 联系类型用业务常识判："一个 X 对应几个 Y"，两边都可多个才是 m:n；
  3. m:n 联系上若有自己的属性（如"成绩"属于选课联系而非学生或课程），标在菱形上。

套路二：关系模式填空——主键外键往哪放 ​

  1. 每个实体一张表，主键 = 实体的码；
  2. 1:n 联系：把 1 端主键放进 n 端表作外键；
  3. m:n 联系：单独建表，主键 = 两端主键组合，联系的属性（成绩）也放这张表；
  4. 小问问"XX 表的主键是什么"：先想清它是实体表还是联系表，联系表的主键几乎总是组合键。

套路三：SQL 填空——按 SELECT 骨架对号入座 ​

  1. 空 FROM：看 SELECT 和 WHERE 里用了哪些列，缺哪张表补哪张，多表加 JOIN ... ON 连接条件；
  2. 空 WHERE：对应题干"查询满足某条件的行"，日期/字符串加引号；
  3. 空在聚合旁："每门课/每个部门的平均/最高/数量"→ GROUP BY 分组列，条件带 AVG/MAX/COUNT 写 HAVING；
  4. 空在 CREATE TABLE：主键 PRIMARY KEY(...)、外键 FOREIGN KEY(...) REFERENCES 表(列)；
  5. 空在 CREATE VIEW：骨架 CREATE VIEW 视图名 AS 查询语句;——视图本身不存数据，只是把一条 SELECT 起名存起来。挖空最常见两种形态：整段定义被挖（照"视图名 + 题目要显示哪些列"倒推 SELECT），或只挖 AS 后的 SELECT（当普通查询题做，用套路 1～3）。视图列名与 SELECT 列一一对应：要显示"运动员编号、姓名、项目名称"就原样投影这三列，跨表取列先补 JOIN；
  6. 填完代入一条具体数据心里跑一遍（同第一课算法填空的自检法）。

反例演示（视图易错）：把 CREATE VIEW 写成 CREATE TABLE、或漏掉 AS 直接接 SELECT，都是 0 分硬伤；后续小问"用视图 vHighScore 查询……"时按 FROM vHighScore 把它当普通表用即可，不要重复写原查询。带答案的视图练习见本课 90 文件案例题问题 3 第 (3) 问。

套路四：题目要求“增加实体”时怎么改 ​

这类小问不是只在图上多画一个矩形，而是要完成“业务句子 → E-R 图 → 关系模式”整条链。

例：在运动会业务中新增规则：“记录教练，教练属性包括教练编号、姓名；每名运动员恰由一名教练指导，一名教练可指导多名运动员。”

  1. 名词“教练”有独立编号和属性 → 新增实体 教练；
  2. 动词“指导”连接教练与运动员；
  3. 一名教练对多名运动员、每名运动员只对一名教练 → 教练:运动员 = 1:n；
  4. 转关系模式：新增 教练(教练编号, 姓名)；把 1 端的教练编号放到 n 端，因此运动员表改为 运动员(运动员编号, 姓名, 团编号, 教练编号)，教练编号是外键。

反例演示（易错）：把“指导”单独建成 指导(教练编号, 运动员编号) 并非一定语法错误，但对没有自身属性的 1:n 联系属于多余拆表；标准答法是把 1 端主键并入 n 端。若题干改成“运动员可由多名教练共同指导”，两边都可多，才应单独建立联系表。

范式小问的答题模板：“候选键为……；非主属性对候选键存在/不存在部分依赖，所以满足/不满足 2NF；存在/不存在传递依赖……，所以最高为……；建议分解为……，公共属性……能决定其中一表，故无损。” 按这条链写，结论和理由都有分。
