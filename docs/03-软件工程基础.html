03 软件工程基础

分值地位：选择题约 6–8 题（第一梯队）+ 案例题「数据流图」一道大题（约 15 分，常是案例第一题）。内聚耦合排序、逻辑覆盖强弱、McCabe 环路复杂度几乎每年必考其一。

学习目标：读完讲义后，你能——① 给一段项目描述选出合适的开发模型；② 背出内聚/耦合七级排序并判断具体场景；③ 排逻辑覆盖强弱、算 McCabe 环路复杂度；④ 区分四种维护和质量特性分类；⑤ 认出 CMM 等级描述；⑥ 按套路补全数据流图（案例题）。

第一节 软件开发模型 ★★

为什么有多种模型

不同项目的需求清晰度和风险高低差别巨大：需求写得一清二楚的项目不需要反复确认，需求说不清的项目硬按部就班走完设计才发现做错了。开发模型的区别就是"怎么安排'想清楚'和'动手做'的顺序"。认模型题的关键是抓题干特征词。

模型 核心特征 适用场景 题干特征词
瀑布模型 线性顺序，每阶段结束有评审，文档驱动 需求明确且稳定的项目 "需求明确""一次通过、阶段评审"
原型模型 先快速做一个可运行的原型给用户确认，再正式开发 需求不明确、用户说不清想要什么 "快速构建演示""用户确认后再开发"
螺旋模型 瀑布 + 原型 + 每圈都做风险分析，多圈迭代 大型、复杂、高风险项目 "风险分析""多轮迭代"
增量模型 分批交付：先做核心功能，再一片片加 可以分期上线的项目 "分批交付""先核心后扩展"
敏捷（Scrum / XP） 短迭代（Scrum 的 Sprint）、拥抱变化、可工作软件优先 需求多变、小团队、快速上线 "每日站会""Sprint""结对编程""测试驱动"

Scrum 与 XP 要能区分：Scrum 是管理框架（产品负责人、Sprint 冲刺、每日站会、回顾会）；XP 极限编程是工程实践（结对编程、测试驱动开发 TDD、持续集成、重构、小型发布）。题干问"结对编程属于"→ XP。

反例演示（易错）：

  • 原型不是最终产品——抛弃型原型确认完需求就扔掉；考题说"原型可作为最终系统交付"即错。
  • 螺旋模型不是"更花哨的瀑布"——它区别于一切传统模型的核心就是每圈迭代都加入风险分析；选项里没有风险分析的螺旋描述都是干扰项。
  • 瀑布模型的"缺点"考法：直到后期才能看到可运行软件，需求变更代价大——不是"没有文档"（瀑布恰恰文档最全）。

应试动作：背四个特征词对应（明确→瀑布 / 不明确→原型 / 高风险→螺旋 / 多变→敏捷），考试就是配对题。

第二节 需求分析 ★

需求工程的四个过程（背顺序）：需求获取 → 需求分析 → 需求规格说明（定义）→ 需求验证（确认）。验证指"检查需求规格说明书是否正确、一致、完整"。

需求分类：功能需求（系统做什么：查询、统计）、非功能需求（做得怎么样：性能、安全性、可靠性）、设计约束（必须用什么平台、遵循什么标准）。考法：给一句描述判断属于哪类——"响应时间不超过 2 秒"→ 非功能需求。

结构化分析的核心工具（与案例题直接挂钩，第九节展开）：

  • 数据流图（DFD）：描述数据在系统中的流动与加工；
  • 数据字典（DD）：给 DFD 中每个数据流、文件下精确定义；
  • 两者配合：只有 DFD 没有 DD，图中的名字就没有精确含义——这是"为什么需要数据字典"的动机。

第三节 模块化设计：内聚与耦合 ★★★（几乎每年考）

为什么要"高内聚、低耦合"

软件要拆成模块，拆法有好坏：一个模块内部干的事越相关（内聚越高），越容易看懂、改起来越不容易牵连别处；模块之间越独立（耦合越低），一个模块改动对别的影响越小。"高内聚、低耦合"就是这两条经验的一句话版。内聚看模块内部，耦合看模块之间——先分清这个方向再背排序。

内聚七级（从低到高，必须背顺序）

级别 名称 含义 一句话识别
1 偶然内聚 动作之间毫无关系，凑在一起（如"为了省事把几个无关函数塞一个模块"） "没什么关系，硬凑"
2 逻辑内聚 逻辑上相似但功能用途无关（如一个模块按参数分别执行打印输入/打印输出） "相似但无关"
3 时间内聚 动作无关，但必须在同一时间执行（如初始化模块） "同一时间"
4 过程内聚 动作关系不大，但必须按特定次序执行 "按次序但无实质关系"
5 通信内聚 各动作对同一数据进行操作（如对同一份数据先读后存再打印） "围绕同一数据"
6 顺序内聚 前一个动作的输出正好是后一个动作的输入 "接力棒"
7 功能内聚 所有部分合起来完成单一功能（如计算利息） "就是一个功能"

耦合七级（从高到低，必须背顺序）

级别 名称 含义 一句话识别
1 内容耦合 一个模块直接访问另一个模块的内部数据或代码 "掀开别人内脏"
2 公共耦合 多个模块通过同一全局数据结构传递信息 "共用一个大仓库"
3 外部耦合 多个模块访问同一全局简单变量（不是数据结构） "共用一个全局变量"
4 控制耦合 传递的信息中含控制信号（如开关标志决定对方走哪个分支） "传的是命令不是数据"
5 标记耦合 通过参数传递记录/数据结构（而非简单变量） "传一整条记录"
6 数据耦合 通过参数传递简单变量 "传一个数"
7 非直接耦合 两模块无直接关系，靠主模块控制和调用 "各干各的"

反例演示（最易混三组）：

  1. 逻辑内聚 vs 偶然内聚：动作之间"有点相似"（都跟打印/输入输出沾边）→ 逻辑内聚；"完全没关系"→ 偶然内聚。判断标准是相似性。
  2. 公共耦合 vs 外部耦合：共用的是数据结构（一整个记录/文件）→ 公共耦合；只是简单变量（一个全局计数器）→ 外部耦合。
  3. 标记耦合 vs 数据耦合：传的是一条记录/结构（学生信息整条）→ 标记耦合；只是一个简单变量（学号这一个数）→ 数据耦合。

应试动作：两个排序要能默写。记法——内聚从"凑（偶然）"到"专（功能）"，耦合从"掀内脏（内容）"到"不认识（非直接）"；做题先抓题干关键词（同一时间/同一数据/接力/命令/记录/变量）对号入座。

第四节 软件测试 ★★★

测试的阶段（背顺序）

单元测试 → 集成测试 → 确认测试 → 系统测试 → 验收测试。确认测试检验软件是否满足需求规格说明书；验收测试由用户参与（常含 α 测试——开发方场所、β 测试——用户实际环境）。

白盒测试与逻辑覆盖（必考排序）

白盒测试把程序看成透明的，按程序内部逻辑设计用例。逻辑覆盖从弱到强：

语句覆盖 < 判定覆盖 < 条件覆盖 < 判定/条件覆盖 < 条件组合覆盖 < 路径覆盖

覆盖 要求
语句覆盖 每条语句至少执行一次（最弱）
判定覆盖 每个判定的真、假分支各至少经历一次
条件覆盖 每个判定中每个条件的真、假取值各至少一次
判定/条件覆盖 判定的真假分支 + 条件的真假取值都满足
条件组合覆盖 每个判定中条件的所有取值组合都出现
路径覆盖 覆盖程序所有可能的执行路径（最强）

反例演示（经典陷阱）：满足条件覆盖不一定满足判定覆盖。例：判定 A>0 AND B>0，两个用例取 (A=1,B=0) 和 (A=0,B=1)——两个条件的真假都取遍了（条件覆盖满足），但判定结果都是假，真分支一次没走过（判定覆盖不满足）。这就是为什么排序里条件覆盖只保证条件、不保证分支，要两者都保必须上"判定/条件覆盖"。

McCabe 环路复杂度（必考计算）

衡量程序控制流的复杂程度，三种等价算法：

V(G) = 控制流图的边数 E − 节点数 N + 2 = 判定节点数 + 1 = 封闭区域数 + 1

代入算例：某程序流程图有 9 条边、7 个节点 → V(G) = 9 − 7 + 2 = 4。验算（第三种算法）：若该图恰有 3 个判定节点（如 2 个 if + 1 个 while），V(G) = 3 + 1 = 4 ✓ 两种算法一致。

反例演示（易错）：

  • "判定节点"只数分支点（if、while、for、case 的分支），i = i + 1 这类顺序语句不是判定节点；
  • 复合条件 if (A>0 AND B>0) 在某些教材拆成多个条件的组合时算法不同——软考默认按判定节点数+1（即这个 if 算 1 个判定节点）。

黑盒测试（看功能不看代码）

方法 做法
等价类划分 把输入分成若干"同类"等价类，每类取一个代表（有效等价类 + 无效等价类都要测）
边界值分析 在等价类边界处取值（如范围 [1,100] 取 0、1、100、101）——错误最爱出现在边界
错误推测 凭经验猜易错点
因果图 输入条件组合 → 判定表

应试动作：① 覆盖强弱排序背死（语句最弱、路径最强）；② McCabe 三公式等价、任给两样算第三样；③ 测试五阶段顺序；④ "条件覆盖 ⊉ 判定覆盖"这个陷阱认得出。

第五节 软件维护 ★

维护是软件交付之后的修改，四类（必须会对号入座）：

类型 含义 场景识别
改正性维护 修已经发生的错误 "用户报告 bug"
适应性维护 适应环境变化（新 OS、新硬件、新接口规范） "系统升级到新操作系统后要改"
完善性维护 扩充功能、改善性能（用户的新需求） "希望增加报表导出功能"
预防性维护 为将来可能的修改预先重做（防患未然） "提前把老代码重构以便日后维护"

反例演示（易错）：改正 vs 预防——修已发生的 bug 是改正性；改还没发生的隐患是预防性（易混淆知识点里专门强调这对）。占比：完善性维护占全部维护工作量的一半以上（约 50%–60%），选择题直接考。

应试动作：背四类 + "完善性占大头"；判断时先问"错误发生了没（改正/预防）→ 没发生是预防；再问是改自己还是改环境（完善/适应）"。

第六节 软件质量特性 ★

McCall 模型把质量特性分三组（背分组归属即可）：

面向 包含特性
运行（操作） 正确性、可靠性、效率、完整性、可用性
修正（修改） 维护性、灵活性、可测试性
转移（迁移） 可移植性、复用性、互操作性

ISO/IEC 9126 六大特性：功能性、可靠性、易用性、效率、维护性、可移植性（各含子特性，如可靠性含成熟性/容错性/易恢复性）。

应试动作：考法是"XX 属于哪个特性/哪一组"——背 ISO 六大特性名 + McCall 三组归属；易混点："易恢复性"属于可靠性子特性，"互操作性"属于功能性子特性。

第七节 项目管理基础 ★

  • 甘特图（Gantt）：横轴时间、条形表示任务工期，直观；缺点：不能显式反映任务之间的依赖关系（经典考点）。
  • PERT 图 / 关键路径：任务网络图求关键路径——计算方法与第一课 3.6 AOE 网完全相同（顺推取 max、逆推取 min、余量为 0 即关键活动），不重复讲，见 01-数据结构与算法.html 第 3.6 节。
  • COCOMO 估算模型：按代码规模（KLOC）估算工作量，基本模型 E = a × (KLOC)^b（E 单位人月），按项目类型（组织型 / 半独立 / 嵌入型）取不同参数 a、b。考法是题干给公式和参数，代入算即可——例：E = 2.0×(KLOC)^1.0，规模 30KLOC → E = 2.0×30 = 60 人月。
  • 风险管理：过程 = 风险识别 → 风险预测（估计概率与损失）→ 风险评估 → 风险控制。风险暴露 = 风险损失 × 风险发生概率（代入算例：损失 10 万、概率 20% → 风险暴露 2 万）。风险分类：项目风险（预算进度）、技术风险（技术方案）、商业风险（市场）。

第八节 CMM / CMMI ★

CMM 把软件过程成熟度分五级（背顺序和关键词）：

级别 名称 关键词识别
1 初始级 混乱，成功靠个人英雄
2 可重复级 基本项目管理制度，能重复以往成功
3 已定义级 过程文档化、标准化，全组织采用标准过程
4 已管理级 过程和产品量化测量与控制
5 优化级 持续改进，新技术、防患未然

CMMI（能力成熟度模型集成）阶段式表示同样五级：初始、已管理、已定义、量化管理、优化。考法就是配对：抓"文档化标准化"→ 3 级，"量化"→ 4 级，"持续改进"→ 5 级，"重复以往成功"→ 2 级。

第九节 案例题专攻：数据流图（约 15 分）

案例第一题一般是"文字说明 + 顶层图/0 层图（缺数据流）"，三小问：补数据流（起点、终点、名字）、指出加工用到的文件、补数据字典。全部答案都藏在说明文字里，套路如下：

套路一：分层与平衡原则（判断"缺什么"的依据）

  • 顶层图：整个系统算一个加工，只画外部实体和进出系统的数据流；
  • 0 层图：把系统拆成几个主要加工；
  • 父图与子图必须平衡：子图的输入/输出数据流必须与父图中对应加工的输入/输出一一对应——父子图数据流对不上 = 缺流，这是补流题的判定依据。

套路二：逐句扫描说明找缺失数据流

说明中每个动词句都对应一条数据流："顾客提交订单"（订单 → 系统）、"向顾客发送确认"（确认 → 顾客）、"通知房主"（通知 → 房主）。把说明句子列成清单，逐条在图上勾掉，剩下没画的句子就是答案。数据流名要用说明中的原词（题目明确要求"采用说明中的词汇"）。

套路三：补流三要素与常见去向

答案必须写全：起点、终点、数据流名。常见易漏位置：

  • 加工 → 外部实体的反馈类流（确认、通知类，最容易漏）；
  • 加工 ↔ 文件的读写（"保存订单"= 写订单文件，"查询余额"= 读账户文件）；
  • 顶层图与 0 层图对照：顶层有而 0 层没有的流，必缺。

套路四：数据字典写法

用"="（由…组成）、"+"（与）、"{}"（重复）、"|"（或）描述。例：

登录信息 = 学生 ID + 密码
订单 = 顾客编号 + {菜品名 + 数量} + 送餐地址

（{} 内是可以重复出现的项。）

  13. 软件维护工作中占比最大的是（ ）。 A. 改正性维护 B. 适应性维护 C. 完善性维护 D. 预防性维护

  14. ISO/IEC 9126 质量模型中，"成熟性、容错性、易恢复性"属于（ ）的子特性。 A. 功能性 B. 可靠性 C. 易用性 D. 维护性

  15. 某组织已将其软件过程文档化、标准化，所有项目均采用经批准的标准过程进行开发。按 CMM 该组织处于（ ）。 A. 可重复级 B. 已定义级 C. 已管理级 D. 优化级

二、案例题（数据流图，模拟真题风格）

阅读下列说明和图，回答问题 1 至问题 3。

【说明】某订餐系统接收顾客订单并跟踪配送，业务如下：

  1. 顾客向系统提交订单（含顾客编号、菜品明细、送餐地址），系统将订单存入订单文件，并向顾客发送订单确认。
  2. 系统按订单文件中的待处理订单，向相应餐厅发送订单信息；同时生成配送任务写入配送文件。
  3. 餐厅备餐完成后向系统发送备餐完成通知。
  4. 配送员从配送文件获取取餐通知。
  5. 配送员送达后向系统发送送达确认，系统更新订单状态，并向顾客发送送达通知。

顶层图（0 层图的外部实体与之一致）：外部实体为顾客、餐厅、配送员。

0 层图中画出三个加工：①接收订单、②分派订单、③跟踪配送；两个文件：订单文件、配送文件。 已画出的数据流有：顾客→①（订单）、①→订单文件（订单）、①→顾客（订单确认）、②→配送文件（配送任务）、③→顾客（送达通知）、配送员→③（送达确认）、餐厅→③（备餐完成通知）。

问题 1：对照说明，指出 0 层图中还缺少的数据流（给出起点、终点和数据流名）。

问题 2：加工③"跟踪配送"除收到外部输入外，还需要读写哪些文件？各起什么作用？

问题 3：补齐数据字典条目：订单 = ______；菜品明细 = ______。

精华题（历年必考风格，考前必刷）

  1. 【模型识别】为下列项目选模型：① 需求明确的银行核心系统改造；② 需求模糊的管理信息系统；③ 高风险的大型航天控制软件；④ 需求多变的互联网创业产品。

  2. 【内聚耦合】写出下列模块的内聚类型：① 一个模块按参数值分别执行存文件或打印操作（功能无关、逻辑相似）；② 一个模块对同一批学生成绩数据先统计平均分、再排序、再打印报表；③ 一个模块把三个互不相关的函数凑在一起，只因为写代码时顺手。

  3. 【内聚耦合】区分耦合类型：① 模块间传递一个开关量标志决定对方执行哪个分支；② 模块间传递一个整数；③ 模块间传递整个"职工记录"结构；④ 两个模块都直接修改同一全局变量 count。

  4. 【McCabe】某程序流程图包含 4 个判定节点，其控制流图有 12 条边、9 个节点。用两种方法求 V(G) 并互相验证。

  5. 【逻辑覆盖】对语句 if (A>0 AND B>0) s=1; else s=0;：用例 T1(A=1,B=0)、T2(A=0,B=1) 满足了哪种覆盖？没满足哪种覆盖？

  6. 【维护分类】指出维护类型：① 修改程序中一处导致统计错误的计算 bug；② 为两年后的系统改造提前重构核心模块；③ 用户要求增加微信通知功能；④ 数据库从 Oracle 迁移到 PostgreSQL。

  7. 【CMM】"组织对软件过程和产品质量建立了定量的度量与控制"→ 第几级？

答案与解析

课后考题答案

1. B "用户说不清需求 + 先做演示确认"是原型模型的标志特征。瀑布要需求明确；螺旋面向高风险大型项目（核心是风险分析）；V 模型是测试与开发阶段对应的瀑布变体。

2. B 螺旋模型 = 瀑布 + 原型 + 风险分析，风险分析是它的灵魂。文档驱动是瀑布的特征（A 干扰项）。

3. C 结对编程、测试驱动开发、持续集成是 XP 的工程实践；每日站会、Sprint、产品负责人是 Scrum 框架角色与仪式。

4. C "功能无关 + 必须同一时间执行" = 时间内聚（初始化是典型）。若按固定次序执行则属过程内聚——本题关键词是"同时执行"。

5. B 传"记录/数据结构"= 标记耦合；只传简单变量才是数据耦合。控制耦合传的是控制信号；公共耦合是共用全局数据区而非参数传递。

6. B "同一全局数据结构（数组）"→ 公共耦合；若只是同一个全局简单变量则是外部耦合——本题是数组（数据结构），选公共耦合。

7. C 排序：语句 < 判定 < 条件 < 判定/条件 < 条件组合 < 路径。路径覆盖要求走遍所有执行路径，最强。

8. A 条件覆盖只管"每个条件取到真、假"，不管"判定的真假分支是否都执行"——用例 (A=1,B=0)、(A=0,B=1) 两个条件真假都取遍，但判定恒为假，真分支没走过。这正是排序中条件覆盖与判定覆盖互不包含、需要"判定/条件覆盖"合并保证的原因。

9. C V(G) = E − N + 2 = 10 − 8 + 2 = 4。验算：若图有 3 个判定节点，V(G) = 3+1 = 4 ✓。

10. C 边界值分析在边界及其外侧邻值取数：0、1、100、101。只取 1 和 100 会漏掉"边界外一点点"的高发错误区。

11. A 单元 → 集成 → 确认 → 系统 → 验收。确认测试对照需求规格说明书，验收测试由用户参与。

12. B 适应"环境变化"（OS 升级）= 适应性维护。改正性修已发生错误；完善性扩功能；预防性防患未然。

13. C 完善性维护占一半以上（约 50%–60%），直接背。

14. B 可靠性子特性 = 成熟性、容错性、易恢复性。功能性子特性含适合性、准确性、互操作性、安全性等。

15. B "文档化、标准化、全组织统一采用" = 已定义级（3 级）。可重复级是"能重复以往成功"；已管理级的关键词是"定量"。

案例题答案

问题 1（缺失数据流，共 3 条）： 逐句扫描：句 2 中"向相应餐厅发送订单信息"没有画出；句 4 中"配送员获取取餐通知"没有画出（取餐通知由加工③读取配送文件后发给配送员）；句 5 中"系统更新订单状态"没有画出。

缺失数据流 起点 终点 名称
1 加工② 分派订单 餐厅 订单信息
2 加工③ 跟踪配送 配送员 取餐通知
3 加工③ 跟踪配送 订单文件 订单状态（更新）

易漏点：第 3 条是"加工 → 文件"的写流，反馈类（确认/通知）和文件读写流最容易漏。

问题 2：

  • 读配送文件：获取配送任务与当前配送进度（配送员送达确认要与配送文件中的任务对应）；
  • 读写订单文件：根据送达确认更新订单状态（写），并按订单信息确定通知对象（读）。

问题 3：

订单 = 顾客编号 + 菜品明细 + 送餐地址
菜品明细 = {菜品名 + 数量}

（{} 表示可重复出现；若考试给出字段更细的说明，按说明原词逐项列出。）

精华题答案

1. ① 瀑布模型（需求明确、阶段评审）② 原型模型（需求模糊、先演示确认）③ 螺旋模型（高风险大型项目、每圈风险分析）④ 敏捷（Scrum/XP，短迭代拥抱变化）。 识别口诀：明确瀑布、模糊原型、高风险螺旋、多变敏捷。

2. ① 逻辑内聚（逻辑相似但功能无关，按参数分支执行不同动作）；② 通信内聚（统计、排序、打印都是对同一批成绩数据的不同操作，彼此没有"输出即输入"的接力关系）；③ 偶然内聚（毫无关系硬凑）。 易混点：若题干改成"读数据 → 加工 → 把结果写回文件"这种前一步输出是后一步输入的接力链，则是顺序内聚——判别标准是看动作之间有没有数据接力。

3. ① 控制耦合（传开关标志 = 控制信号）；② 数据耦合（简单变量）；③ 标记耦合（整条记录结构）；④ 公共耦合（直接修改同一全局数据——注意若是"直接进入对方模块内部改"则是内容耦合，本题是共享全局变量区，属公共耦合）。

4. V(G) = E − N + 2 = 12 − 9 + 2 = 5；判定节点数 + 1 = 4 + 1 = 5。两种算法结果一致 ✓。

5. 满足条件覆盖（A、B 两条件的真、假取值都各出现了一次）；不满足判定覆盖（两次判定结果都是假，s=1 的真分支从未执行）。这也是"条件覆盖不包含判定覆盖"的实例——想同时保证要用判定/条件覆盖或更强的条件组合覆盖。

6. ① 改正性（修已发生的 bug）② 预防性（为将来的修改提前重构，防患未然）③ 完善性（扩充新功能）④ 适应性（适应数据库环境更换）。易混点：② 是"还没发生"→ 预防，不是改正。

7. 第 4 级（已管理级）。关键词"定量度量与控制"；若描述为"持续改进、采用新技术"则是第 5 级优化级。
