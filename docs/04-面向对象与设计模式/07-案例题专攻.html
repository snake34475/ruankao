04.7 案例题专攻：UML 建模

案例题的形态固定为「文字说明 + 挖空的图（用例图/类图/顺序图/通信图/活动图/状态图之一）」，常配 3 个小问。三个固定套路如下。

套路一：补用例图——参与者、用例、include/extend

  1. 参与者：名词且"谁在使用系统/系统服务谁"（读者、管理员、外部系统如支付网关）；
  2. 用例：系统为参与者完成的一件完整的事（动词短语：借书、还书、缴费）；
  3. 挖空补关系：句子里"必须先/一定要"→ include；"如果…就/可选"→ extend；两种"某类参与者…"→ 用例泛化。

从"用例详细描述"里挖答案（近真题的新形态）：题目给的往往是一段标准格式的描述——参与者 / 典型事件流（1、2、3…）/ 备选事件流（2a、4a…）。读法三条：

  • 参与者直接抄（原文写了"参与者：读者"）；
  • 典型事件流的每一步对应顺序图/通信图里的一条消息，步骤序号 = 消息顺序；
  • 备选事件流 → extend 的来源（如"4a 读者要借的书无法外借 → 告知本书无法借阅"就是"告知无法借阅"这个扩展用例）。

套路二：补类图——名词变类、关系按语义套，方法按事件流找

  1. 类名：说明中的核心名词（读者、图书、借阅记录）——注意填空题要求"用图中给出的英文词汇"，所以要把中文名词与英文类名对应上（读者 = Patron、图书 = Book、目录 = Catalog）；
  2. 属性：说明里"要记录的信息"（书号、书名、定价）；
  3. 方法（补 M1、M2…）：从事件流的动词里找，且要匹配调用者与接收者——如"根据图书目录中的图书ID确认该书可以借阅"这一步，主语是目录对象 → 方法就是目录提供的 find(bookID)／getForCheckOut(id)；"判断读者身份"→ 读者对象的 isFaculty()；
  4. 多重性：按 3.1 的"逐端问"法填写；
  5. 关联类：多对多时中间挂关联类（学生—课程之间挂"选课记录"——与第 2 课 m:n 转关系模式同构）。

判"哪个方法属于哪个类"的通用办法：看动作的宾语归谁管——"查书"问的是图书/目录 → 方法落在这两个类上；"生成借阅记录"要落到借阅记录或会话控制类上；"通知读者应还日期"落到读者或通知类上。

套路三：补顺序图/通信图/状态图/活动图——按说明的顺序与事件照搬

  1. 顺序图挖消息：按说明句子的先后顺序填消息名（从上到下 = 时间先后），注意返回消息（虚线箭头）也要填；
  2. 通信图挖序号：序号体现调用层次（1、1.1、1.1.2），先定第一个调用，再补嵌套；
  3. 状态图挖状态/事件：状态 = 名词（空闲/占线），转换线上标事件（题干会说"当…时进入…"）；起点实心圆、终点带圈圆；
  4. 活动图挖动作/条件：动作 = 动词短语，菱形出口标监护表达式（题干会说"如果…则…否则…"）。

套路四：设计模式小问（"可以采用何种设计模式？简要说明原因"）

这是 3 分题，答题必须两段：模式名 + 原因（只写名字通常拿不满）。原因要用题目原话 + 原则名，模板如下：

可以采用策略（Strategy）模式。理由：题库中的规则（制度）会不断扩充和调整，属于一族可互相替换的算法；采用策略模式把每种规则封装成独立的策略类，由上下文按需注入，新增规则时只需增加新的策略类，不必修改原有代码，符合开放-封闭原则。

识别抓手（题干 → 模式）：

题干出现 答案模式
"可灵活扩充/调整的一系列规则、算法，可互相替换" 策略
"状态改变时通知所有相关对象/订阅者" 观察者
"创建过程复杂、分步骤，且表示可不同" 构建器
"系统只能有一个××（如全局配置、唯一编号生成器）" 单例
"要接入已有接口不兼容的第三方/旧系统" 适配器
"需要在不修改类的前提下增加新操作" 访问者
"对象行为随自身状态变化而变化" 状态
"需要支持撤销/重做、操作排队" 命令
"多步骤处理，每个处理者只处理自己管的部分，其余往下传" 职责链

应试动作：这一问先写模式名再写理由，理由必含「新增/变化时只需加新类、不必改原有代码」这类功能点，并点名原则（开放-封闭 / 依赖倒置 / 单一职责）。给分点是关键词，不是文采。
