06.5 TCP、UDP 与三次握手 ★★★ ​

为什么要分 TCP 和 UDP 两种 ​

传输层负责"程序到程序"的交付（用端口号区分同一台主机上的不同应用）。有的应用宁可慢也要一条都不能丢（网页、文件、邮件），有的应用宁可丢也要快（直播、语音、域名查询）。于是传输层提供两种选择：

对比项TCPUDP
连接面向连接（先握手再传数据）无连接（拿到地址直接发）
可靠性可靠（确认、重传、按序交付）不可靠（尽力而为，丢了不补）
有序性保证按序到达不保证顺序
流量控制/拥塞控制有（滑动窗口）没有
开销与速度头部大、开销大、较慢头部小（8 字节）、开销小、快
数据单位字节流用户数据报
典型应用HTTP/HTTPS、FTP、SMTP、TELNETDNS、DHCP、TFTP、SNMP、音视频流

共同点（考过原型的知识点）：TCP 和 UDP 都用端口号标识上层应用（端口寻址）；都基于 IP 之上、属于传输层。但 UDP 没有连接管理、没有重传、没有流量控制。

反例演示：

  1. "UDP 是不可靠协议，所以 UDP 报文没有端口"——错。可靠不可靠是传输质量，端口寻址是编址方式，UDP 同样用端口（如 DNS 用 53）。
  2. "TCP 因为可靠，所以比 UDP 一定更快"——反了。确认重传换可靠，代价就是速度；要快用 UDP。
  3. "DNS 是传输层协议"——错。DNS 是应用层协议，只是它使用 UDP（端口 53）来传输，别把"用谁传输"和"属于哪层"混为一谈。

TCP 三次握手（背报文 + 背状态） ​

动机：TCP 要在传数据前确认"双方都具备收发能力"。为什么三次而不是两次？——两次握手下，服务器无法确认"客户端能收到我发的数据"；且历史上一个早已失效的连接请求若突然到达服务器，两次握手会让服务器白白建起一条没人用的连接。第三次握手让客户端把"我收到了你的确认"再告诉服务器，双方的收发能力才都被双向确认。

三次握手过程（客户端 A，服务器 B）：

步骤谁发什么报文标志本步的状态变化（谁变了、变成什么）
1A → B：请求建立连接SYN=1（seq=x）A：CLOSED → SYN-SENT；B 仍停在 LISTEN
2B → A：同意并确认SYN=1, ACK=1（seq=y, ack=x+1）B：LISTEN → SYN-RCVD；A 仍停在 SYN-SENT
3A → B：确认ACK=1（seq=x+1, ack=y+1）A：SYN-SENT → ESTABLISHED；B：SYN-RCVD → ESTABLISHED

这张表的"谁"会随着步骤换人：第 1、3 步的发送方是 A，第 2 步的发送方是 B。所以读表时要盯"这一步是谁在发"，别把 B 的状态变化记到 A 头上。

把数字代进去，状态就再也不会记乱（设 A 的初始序号 x=100、B 的 y=200）：

步骤报文这一步在说什么
1A→B：SYN=1，seq=100A 说"我把起始编号定为 100"
2B→A：SYN=1，ACK=1，seq=200，ack=101B 确认"100 我收到了，下一个请给我 101"；同时报出自己的起始号 200
3A→B：ACK=1，seq=101，ack=201A 确认"200 我收到了，下一个请给我 201"

数字规律（背这一条就够）：ack = 对方的 seq + 1——因为 SYN（和之后的 FIN）本身要占掉一个序号位，所以要 +1；而自己的 seq 一旦定下就固定不变，之后每传一段数据才按字节数往前推。

记忆抓手："一请、二请二应、三应"——第一次只带 SYN；第二次 SYN 和 ACK 一起带（SYN+ACK 报文）；第三次只带 ACK。四个关键状态按顺序：CLOSED / LISTEN → SYN-SENT → SYN-RCVD → ESTABLISHED。

断开连接（四次挥手，了解过程即可）：FIN → ACK → FIN → ACK，双方各发一次、各回一次；主动方最后进入 TIME-WAIT 等待一段时间（确保最后的 ACK 送达、旧报文消亡）再 CLOSED。考点级别低于握手，记住"挥手四次、比握手多一次"即可。

滑动窗口（流量控制） ​

动机：逐段“发一段、等一次确认”太慢；一口气无限发送又可能压垮接收方或网络。滑动窗口让发送方在一个许可范围内连续发送，既利用线路，又给速度设上限。

TCP 同时受两扇“窗口”约束：

  • 接收窗口 rwnd：接收方通告自己还有多少缓存，防止发送方压垮接收主机，属于流量控制。
  • 拥塞窗口 cwnd：发送方根据丢包、确认等网络反馈估计可发送量，防止压垮网络路径，属于拥塞控制。

因此，发送方实际可用的发送窗口上限是：

发送窗口 = min(rwnd, cwnd)

不跳步算例：接收方通告 rwnd = 12 KB，发送方当前 cwnd = 8 KB，则发送窗口为 min(12, 8) = 8 KB。即使接收方还有 12 KB 空间，网络当前只允许谨慎发送 8 KB。若下一时刻 rwnd = 4 KB、cwnd = 10 KB，则窗口变为 4 KB，瓶颈改成接收方。

窗口怎样“滑动” ​

为便于手算，先把数据想成编号为 1、2、3……的等长小段，窗口大小设为 4：

时刻已确认当前允许连续发送发生了什么
t0无1、2、3、4左边界在 1，可连续发 4 段
t11、23、4、5、6收到累计确认，左边界滑到 3，新放进 5、6
t21～45、6、7、83、4 也确认，窗口继续右移

这里“确认到 2”可理解为接收方下一段期望 3；已确认的数据移出窗口，右侧才腾出同样数量的新位置。窗口没有把旧数据整体搬家，只是可发送编号范围的左右边界改变了。

反例演示：若只收到对第 1、2 段的累计确认，却把窗口从 [1,4] 滑成 [5,8]，就等于错误地假设 3、4 也已确认；正确窗口是 [3,6]。

慢启动在做什么 ​

新连接不知道网络能承受多大流量，因此拥塞窗口不会一开始就开到最大。慢启动让 cwnd 从较小值开始，正常收到确认时在每个往返时间内大致成倍增长；到达慢启动门限后转入拥塞避免，增长趋于线性。发生超时等明显拥塞信号时，会显著减小窗口，再谨慎增大。

“慢启动”名字里的“慢”指起点小、先试探，并不表示增长速度一直慢；它的早期增长反而近似指数型。考试通常只要求识别“由小到大探测网络容量”和“cwnd 管网络拥塞”。

应试动作：① TCP/UDP 对比表整表背下，特别是“谁用 TCP、谁用 UDP”的典型应用清单；② 三次握手按 SYN → SYN+ACK → ACK 默写；③ 看到“接收方缓存”选 rwnd/流量控制，看到“网络拥塞”选 cwnd/拥塞控制，计算实际窗口就取二者较小值；④ 窗口移动题只让“已经确认”的编号移出左边界。
