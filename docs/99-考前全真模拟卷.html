99 考前全真模拟卷

用途：覆盖 12 课核心考点的一套完整模拟卷。上午卷 75 道单项选择题，每题 1 分；下午卷 5 道案例题，每题 15 分。两科均以 45 分为训练合格线。

作答建议：严格模拟连考。先完成上午卷，再完成下午卷；不要边做边翻讲义。计算题保留草稿，案例题尽量使用题干原词作答。考试日期、合格标准及机考安排以官方通知为准。

使用方法

  1. 上午卷限时不超过 120 分钟，建议 70–90 分钟完成并检查；
  2. 下午卷按剩余时间训练，先做数据流图、数据库和 UML，再做算法与程序题；
  3. 全部交卷后再翻到文件末尾看答案；
  4. 错题按题号记录对应章节，回到相应讲义补漏；
  5. 上午或下午任一科低于 45 分，都应视为本次模拟未通过。

第二科 应用技术（75 分）

案例一 数据流图（15 分）

某社区维修平台的业务如下：

  1. 居民提交报修请求，内容包括居民编号、设备类型、故障描述和上门地址。系统读取居民文件核验居民状态，生成维修订单并写入订单文件，同时向居民返回受理结果。
  2. 系统读取待分派订单和维修人员文件，根据技能与可用状态选择维修人员，向维修人员发送工单，并把分派结果写回订单文件。
  3. 维修人员完成服务后提交完工报告。系统更新订单状态，并向第三方支付平台发送支付请求。
  4. 支付平台返回支付结果。支付成功后，系统把结算结果写入订单文件，并向居民发送电子回执。

顶层图中已有外部实体：居民、维修人员、支付平台；已有数据流包括“居民→系统：报修请求”“系统→居民：受理结果/电子回执”“系统→维修人员：工单”“维修人员→系统：完工报告”“系统→支付平台：支付请求”“支付平台→系统：支付结果”。

分层图包含：加工 1“受理报修”、加工 2“匹配派单”、加工 3“结算归档”；数据存储 D1“居民文件”、D2“订单文件”、D3“维修人员文件”。图中已经画出以下数据流：

  • 居民→加工1：报修请求；加工1→居民：受理结果；
  • D1→加工1：居民信息；加工1→D2：新订单；

第一科逐题解析

计算机系统基础

1. A　负数补码求绝对值：10010110 按位取反为 01101001，加 1 得 01101010=106，所以原数为 −106。反向验证：+106=01101010，取反加 1 正好回到 10010110。D 是误按无符号数解释。

2. A　阶码位数决定可表示指数范围，尾数位数决定有效精度。甲阶码长、尾数短，因此范围更大、精度更低。口诀“阶范尾精”。

3. B　IR 保存当前指令；PC 保存下一条指令地址；MAR 保存要访问的主存地址；PSW 保存状态标志。“当前指令”是 IR 的识别词。

4. B　题目明确 100 ns 是未命中的完整时间，使用加权平均：0.95×10+0.05×100=9.5+5=14.5 ns。结果位于 10～100 ns 之间，合理。C 对应“先查 Cache，未命中再追加 100 ns”的另一种题意，本题不适用。

5. C　6000 RPM 一圈需要 60000/6000=10 ms，平均旋转等待为半圈 5 ms；平均存取约为 8+5=13 ms。D 错在加了整圈等待。

6. A　直接映射中每个主存块只能放到固定 Cache 行，最容易冲突但电路简单；全相联最自由、冲突最低、硬件最复杂；组相联折中。

7. C　冗余模块可靠度=1−(1−0.8)^2=1−0.04=0.96；再与 A 串联：0.9×0.96=0.864。反向检查：并联后高于 0.8，与 A 串联后低于 0.9，符合直觉。

8. B　r=3 时 2^3=8<8+3+1=12，不够；r=4 时 16≥8+4+1=13，所以至少 4 位。等号或大于均满足。

9. C　RISC 的典型特征是指令少而规整、寻址方式少、多寄存器、Load/Store 访存、常用硬布线并利于流水线。A、B、D 都更符合 CISC。

10. B　流水线周期为最长段 4 ns，第一条建立时间=2+3+4=9 ns，20 条总时间=9+(20−1)×4=85 ns。非流水时间为 20×9=180 ns，85 ns 小于它，合理。

程序设计语言基础

11. A　词法分析把字符流切分并识别为 token；语法分析再检查 token 序列能否按文法组成表达式和语句。

12. B　括号匹配和表达式结构属于语法结构检查，由语法分析完成。词法分析只识别单词级记号。

13. B　正规式要求字符串由 a、b 构成并以 abb 结尾。baabb 满足；A 以 bba 结尾，C 以 bab 结尾，D 长度虽可但以 bbb 结尾。

14. B　传值时形参得到实参值的副本，修改形参一般不改变调用者变量本身。若值本身是对象引用，可能通过引用修改对象内容，但“把形参重新赋值”仍不等于改变调用者的引用变量；应服从题面语言语义。

15. C　解释执行通常边翻译边执行，不要求先生成完整目标程序；编译通常先把源程序整体转换为目标代码，再运行目标程序。A、D 把两者说反，B 把编译期和运行期错误混为一谈。

操作系统

16. B　I/O 完成只表示等待条件消失，进程进入就绪队列；是否立即运行还取决于调度器，不能直接写运行态。

17. B　进入临界区前执行 P 申请互斥资源，退出后执行 V 释放资源。若顺序倒置，就不能阻止多个进程同时进入。

18. C　死锁四个必要条件是互斥、请求并保持、不可剥夺、循环等待。选项 C“可剥夺”恰好是否定了必要条件。

19. B　最不利时每个进程都占有 4−1=3 个资源，再多 1 个即可让某进程完成：3×(4−1)+1=10。用 9 个时可能三个进程各占 3 个并互等第 4 个；10 个时至少有一个能取得第 4 个，完成并释放。

20. B　4 KiB=2^12 B，低 12 位即后三个十六进制数 ABCH 为页内偏移；页号 5 换为物理块号 9，拼成 9ABCH。页内偏移在转换中不变。

21. C　前三次装入 1、2、3；再次访问 1 命中，但 FIFO 不改变进入先后；访问 4 时淘汰最早进入的 1，最终集合为 {2,3,4}。若是 LRU，命中 1 会更新近期性并淘汰 2。

数据结构与算法

22. C　按栈计算：读到 6、2 后弹出二者做 6/2=3，再压入 3；读到下一个 3 后执行加法，得到 3+3=6。后缀表达式必须按“先弹出的是右操作数”计算。

23. B　元素数=(rear−front+10)%10=(7−2+10)%10=5。

24. C　二叉树边数既可写为 n−1，又可写为 n1+2n2；代入 n=n0+n1+n2 得 n0=n2+1。即叶子比双分支结点多 1。

25. A　前序首项 A 是根；中序把树分为左 DB、右 EC。左子树前序 BD，为 B 的左孩子 D；右子树前序 CE，为 C 的左孩子 E。后序是左 DB、右 EC、根 A，即 DBECA。

26. C　依次合并最小权：2+3=5，5+7=12，8+12=20。哈夫曼 WPL 等于所有非叶结点权值之和：5+12+20=37。按叶深复核：2、3 深 3，7 深 2，8 深 1，2×3+3×3+7×2+8×1=37。

27. A　无向边 {i,j} 同时使 A[i][j] 与 A[j][i] 有边，因此矩阵关于主对角线对称。无自环时对角线为 0，并非总为 1。

28. B　Dijkstra 用“已确定最短距离不会再被更小值推翻”的贪心性质，要求边权非负。含负权边时应考虑 Bellman-Ford 等算法。

29. C　拓扑排序不断删除入度为 0 的顶点；能包含所有顶点当且仅当图没有有向环，即图为 DAG。

30. B　100 个元素最坏比较次数为 ⌈log2(100+1)⌉=7。也可按判定树容量反查：6 次最多区分 2^6−1=63 个元素，不够；7 次最多 127 个，足够。

31. D　归并排序在相等关键字时先取左序列元素即可保持原相对次序，属于稳定排序。快速、堆、希尔通常不稳定。

32. D　当每次枢轴都造成极不平衡划分时，比较量为 (n−1)+(n−2)+…+1=n(n−1)/2，故最坏为 O(n^2)；平均通常为 O(n log n)。

软件工程基础

33. B　原型模型用可运行原型帮助用户看到系统并反馈，适合需求不清。需求明确、变更少才更适合瀑布。

34. B　螺旋模型每一圈包含计划、风险分析、实施和客户评估，最突出的识别词是“风险分析”。

35. D　模块内所有成分为一个明确功能服务且不可或缺，是最强的功能内聚。顺序内聚要求前一步输出成为后一步输入，题干没有这种接力链。

36. D　直接进入另一个模块内部访问其数据或代码是最强、最差的内容耦合。共享全局数据区才是公共耦合。

37. C　V(G)=E−N+2=12−9+2=5。若画出的流程图有 4 个独立判定结点，也可用“判定结点数+1=5”交叉验证。

38. B　边界值分析关注合法边界及紧邻边界外的值，0、1、100、101 正好覆盖两个端点内外。A 缺少边界外值。

39. B　因外部运行环境（操作系统）变化而修改是适应性维护。修复已发生错误是改正性；扩功能是完善性；为防未来隐患是预防性。

40. C　第 4 级定量管理级以度量、统计和定量控制为关键词；第 5 级优化级强调持续过程改进与新技术反馈。

面向对象与设计模式

41. A　封装把数据与操作组合并隐藏内部实现，通过公开接口使用。继承是复用父类特征，多态是同一消息产生不同响应。

42. B　同类中方法名相同、参数列表不同是重载，编译期按参数匹配；子类用相同签名替换父类实现才是重写。

43. B　顺序图以生命线和消息箭头表现对象交互，纵向体现时间先后。类图看静态结构，部署图看物理结点。

44. C　部署图描述软件制品/构件部署在哪些物理或执行环境结点上。构件图主要表现软件构件及依赖，不强调物理落点。

45. A　身份校验是每次提交订单都执行的必经行为，使用 <<include>>；箭头从基用例“提交订单”指向被包含用例“身份校验”。

46. B　“一族可互换算法、运行时选择”是策略模式。观察者处理一对多通知；适配器转换接口；单例保证唯一实例。

47. C　适配器把不兼容接口转换为客户期望接口。装饰器增加职责，代理控制访问，备忘录保存和恢复状态。

数据库系统

48. B　内模式/物理存储变化不影响概念模式和应用，称为物理数据独立性；概念模式变化不影响外模式和应用才是逻辑数据独立性。

49. B　投影 π 选列，选择 σ 选行。口诀“σ 像筛子筛行，π 两条竖线切列”。

50. B　候选键 A 为单属性，不可能存在对键的部分依赖，所以满足 2NF；但 A→B→C 形成非主属性 C 对键 A 的传递依赖，不满足 3NF，最高为 2NF。逐级判断不能因看到冗余就退回 1NF。

51. B　AVG 在分组后计算，聚合结果的筛选必须用 HAVING。WHERE 在分组前筛选原始行，此时平均值尚未形成。

52. D　持久性要求已提交结果经受系统故障仍保留。原子性是全做或全不做，隔离性处理并发影响。

53. A　两段锁要求先处于加锁增长阶段，再处于解锁收缩阶段，可保证冲突可串行化；事务仍可能互持对方需要的锁而死锁。

54. C　故障恢复口诀：已提交事务 REDO，保证持久性；未提交事务 UNDO，保证原子性。

计算机网络

55. B　传统交换机依据 MAC 地址转发帧，工作在数据链路层。路由器依据 IP 地址工作在网络层。

56. B　/27 留 5 位主机位，共 2^5=32 个地址；传统 IPv4 子网扣除网络地址和广播地址，可分配 32−2=30 个。

57. C　/26 每块 64 个地址，末字节网段起点为 0、64、128、192。130 落在 128～191，网络地址为 192.168.1.128。按位与掩码 255.255.255.192 也得 128。

58. C　DNS 默认端口 53；FTP 控制 21，SMTP 25，HTTP 80。DNS 常用 UDP，区域传送或较大响应等场景可用 TCP。

59. B　TCP 面向连接，提供可靠、有序、无重复的字节流，并具有确认、重传、流量与拥塞控制；UDP 无连接、尽力而为。

信息安全

60. A　签名用发送者自己的私钥，验证用发送者公钥。口诀“私签公验”；接收者的密钥用于保密方向，不用于代表甲签名。

61. A　数字信封取长补短：用快速的对称密钥加密大数据，再用接收者公钥加密那把对称密钥，接收者用自己的私钥取出密钥。

62. B　Hash 摘要对修改敏感，主要用于完整性校验；它通常无密钥且不隐藏原文，不能单独提供机密性。

63. B　参数化查询把 SQL 结构与数据参数分离，配合输入校验可阻止恶意输入被解释成 SQL 代码。单纯改端口、加长密码不能修复字符串拼接漏洞。

标准化与知识产权

64. B　GB 是国家标准代号，/T 表示推荐性，因此 GB/T 为推荐性国家标准。具体标准是否适用仍以现行正式文本为准。

65. A　合法持有人为防止原件损坏制作必要备份，并按法定范围使用、在失去合法持有资格时妥善处理，通常属于允许情形；不得借备份之名复制传播。具体争议以现行法律和授权协议为准。

66. C　软件著作权保护程序及有关文档的具体表达，不垄断思想、处理过程、操作方法或数学概念本身。独立创作相同功能也不当然侵权。

67. B　不区分职位，用组合：C(8,2)=8×7/(2×1)=28。若两个职位不同才用 A(8,2)=56。

71. A — coupling　良好模块设计是 high cohesion and low coupling（高内聚、低耦合）。其他词分别是递归、带宽、继承。

案例一答案：数据流图（15 分）

问题 1（6 分）

缺失的 3 条数据流如下：

起点 终点 数据流名称 依据
加工 2“匹配派单” 维修人员 工单 说明第 2 条“向维修人员发送工单”
加工 2“匹配派单” D2“订单文件” 分派结果（维修人员编号/已分派状态） 说明第 2 条“把分派结果写回订单文件”

每条必须同时写对起点、终点和名称。名称可使用含义相同且来自题意的表述，如“订单更新信息”。

问题 2（4 分）

  • 读取 D2：取得待分派订单的设备类型、地址和当前状态；
  • 读取 D3：取得维修人员的技能、可用状态等信息；
  • 二者要匹配，才能选出能处理该故障且当前可接单的维修人员；
  • 分派完成后修改 D2 订单文件，写入维修人员编号和“已分派”等订单状态。

易错点：D3 提供人员候选信息，但业务说明没有说加工 2 改变人员档案，所以不能凭空添加“加工 2→D3”。

问题 3（3 分）

（1）设备类型；（2）故障描述。二者顺序互换不扣分。

完整定义可写为：

维修订单 = 订单编号 + 居民编号 + 设备类型 + 故障描述 + 上门地址 + 订单状态 + [维修人员编号]

维修人员编号在订单刚受理、尚未派单时可能不存在，因此用 [ ] 表示可选。

问题 4（2 分）

违反父图与子图的数据流平衡原则：分层图边界上新增了顶层图不存在的“系统→居民：广告信息”。处理方式有两种：若广告确属需求，则在顶层图补上对应数据流并同步需求说明；若不属需求，则从分层图删除该数据流。不能只改一层而保持不平衡。

案例二答案：数据库设计与 SQL（15 分）

问题 1（4 分）

  • 教师—课程：1:n。一名教师可负责多门课程，每门课程恰由一名教师负责；
  • 学员—课程：m:n。一个学员可选多门课程，一门课程可被多名学员选；
  • m:n 的“选课”联系应单独转换为关系“选课”，选课时间、成绩是该联系的属性，放在选课表中。

问题 2（4 分）

  • 学员（学员号，姓名，所属部门），主键：学员号；
  • 教师（教师号，姓名），主键：教师号；
  • 课程（课程号，课程名，学分，教师号），主键：课程号；外键：教师号→教师（教师号）；
  • 选课（学员号，课程号，选课时间，成绩），组合主键：（学员号，课程号）；两个外键分别引用学员和课程。

组合主键的原因：同一学员可选多门课，同一课程有多个学员，任何单独一列都不能唯一标识一条选课记录；题面说明同一学员对同一课程最多一条有效记录，因此二者组合恰好唯一。

问题 3（3 分）

CREATE TABLE 选课 (
    学员号    CHAR(10) NOT NULL,
    课程号    CHAR(10) NOT NULL,
    选课时间  DATE,
    成绩      DECIMAL(5,2),
    PRIMARY KEY (学员号, 课程号),
    FOREIGN KEY (学员号) REFERENCES 学员(学员号),
    FOREIGN KEY (课程号) REFERENCES 课程(课程号)
);

字段类型允许合理变化；得分点是组合主键与两个正确的外键方向。

问题 4（4 分）

SELECT s.学员号, s.姓名, AVG(e.成绩) AS 平均成绩
FROM 学员 AS s
JOIN 选课 AS e ON s.学员号 = e.学员号
GROUP BY s.学员号, s.姓名
HAVING COUNT(*) >= 3
   AND AVG(e.成绩) >= 80;

解析：先连接学员与选课，再按学员分组；“至少 3 门”和“平均成绩不低于 80”都是聚合后的组条件，必须放在 HAVING。把 AVG(e.成绩)>=80 放进 WHERE 是典型错误。

案例三答案：UML 与设计模式（15 分）

问题 1（4 分）

  • “查看课程” <<include>> “身份登录”，箭头从“查看课程”指向“身份登录”；
  • “提交作业” <<include>> “身份登录”，箭头从“提交作业”指向“身份登录”；
  • “申请结业证书” <<extend>> “完成课程”，箭头从扩展用例“申请结业证书”指向基用例“完成课程”。

识别依据：必经行为用 include；满足条件且主动申请才发生的可选行为用 extend。口诀“include 从基用例指出去，extend 从扩展用例指回来”。

问题 2（5 分）

  • 课程—课时是**组合（composition）**关系；
  • 实心菱形画在整体“课程”一端；
  • 一门课程包含 1..* 个课时，每个课时属于 1 门课程；若允许空课程，课程到课时一端也可按业务规则标 0..*，但本题“由若干课时组成”应取 1..*；
  • 学员和课程的 m:n 联系拆成两个 1:n：学员 1—0..* 选课记录，课程 1—0..* 选课记录；
  • 每条选课记录恰好关联 1 名学员和 1 门课程，并保存选课时间、学习进度。

课时不能脱离课程独立存在是组合而非聚合的直接判据。

问题 3（4 分）

采用策略（Strategy）模式。

  • Context：课程内容播放器/展示上下文；它持有一个展示策略并委托其展示；
  • Strategy：统一的“内容展示策略”接口，如 display()；
  • ConcreteStrategy：视频展示、图文展示、直播展示三种具体实现。

原因：三种方式是一族可互换算法/行为，运行时按配置选择。新增一种展示方式只需增加具体策略，调用方不必增加大段条件分支，符合开闭原则。

问题 4（2 分）

使用 UML 顺序图（sequence diagram）。它沿时间轴展示学员、系统、校验服务、存储等对象之间的消息先后。

案例四答案：算法设计（15 分）

问题 1（8 分）

（1）1
（2）a[j] < a[i]
（3）dp[j] + 1
（4）dp[i] > dp[best]
（5）prev[k]

补全后的核心代码：

for (int i = 0; i < n; i++) {
    dp[i] = 1;
    prev[i] = -1;
    for (int j = 0; j < i; j++) {
        if (a[j] < a[i] && dp[j] + 1 > dp[i]) {
            dp[i] = dp[j] + 1;
            prev[i] = j;
        }
    }
}

int best = 0;
for (int i = 1; i < n; i++) {
    if (dp[i] > dp[best]) best = i;
}

int k = best;
while (k != -1) {
    output_reverse(a[k]);
    k = prev[k];
}

问题 2（3 分）

j<i 保证只从 a[i] 前面已经计算完的状态转移；a[j]<a[i] 保证把 a[i] 接到以 a[j] 结尾的子序列后仍然严格递增。满足两项后，候选长度为 dp[j]+1，只有它严格大于当前 dp[i] 才更新长度和前驱。

问题 3（2 分）

  • 时间复杂度：两层循环检查所有 j<i，比较次数为 0+1+…+(n−1)=n(n−1)/2，故为 O(n²)；
  • 额外空间复杂度：dp、prev 及输出链共线性规模，故为 O(n)。

问题 4（2 分）

对 [3,1,2,5,4,7]，计算结果如下：

i a[i] dp[i] prev[i]
0 3 1 −1
1 1 1 −1
2 2 2 1
3 5 3 2
4 4 3 2
5 7 4 3

LIS 长度为 4。从 best=5 沿前驱得到反向下标 5→3→2→1，反向输出值为 7,5,2,1；再逆序得到一条正向 LIS：[1,2,5,7]。

交叉验证：[1,2,4,7] 也是长度 4 的 LIS，但题目规定同长度不更新前驱，因此代码保留较早遇到的 a[3]=5，输出 [1,2,5,7]。枚举所有可接关系后不存在长度 5 的严格递增序列。

案例五答案：Java 程序设计与设计模式（15 分）

问题 1（8 分）

（1）observers.add(observer)
（2）this.stock = stock
（3）notifyObservers()
（4）observer.update(stock)
（5）implements StockObserver

完整关键实现：

public void attach(StockObserver observer) {
    observers.add(observer);
}

public void setStock(int stock) {
    this.stock = stock;
    notifyObservers();
}

private void notifyObservers() {
    for (StockObserver observer : observers) {
        observer.update(stock);
    }
}

class EmailAlert implements StockObserver {
    @Override
    public void update(int stock) {
        if (stock < 10) {
            System.out.println("Low stock: " + stock);
        }
    }
}

问题 2（4 分）

使用观察者（Observer）模式：

  • Inventory：Subject/ConcreteSubject（被观察者/具体主题），保存观察者集合并在状态变化时通知；
  • StockObserver：Observer（抽象观察者）接口，定义统一更新方法；
  • EmailAlert：ConcreteObserver（具体观察者），收到库存变化后执行邮件告警相关行为。

问题 3（3 分）

主要优点：

  1. Inventory 只负责库存状态和发布通知，不依赖具体邮件实现，降低耦合；
  2. 可在运行时添加多个订阅者；
  3. 新增短信、消息队列等通知方式时，只需实现 StockObserver 并注册，通常无需修改 Inventory，符合开闭原则。

反例：若把邮件、短信、日志全部硬编码进 setStock，每增加一种通知都要修改核心库存类，条件分支不断膨胀，也难以独立测试。
