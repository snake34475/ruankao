页面内存诊断：Chrome 打开讲义页为何占 215 MB

软考软件设计师资料库 · docs/ 阅读版 · 2026-09-17 · 全部数字为实测值

结论：215 MB 里约七成与页面无关。

在一台全新、无扩展的 Chrome 上，打开一个完全空白的标签页就要 562.7 MB（10 个进程）；打开体积最大、DOM 节点最多的 01 课讲义页，总计 668.9 MB。两者相差 106 MB。

单看承载页面的那个渲染进程：空白页 84.1 MB → 讲义页 114.9 MB，页面内容只贡献约 30 MB。其余是 Blink 排版引擎、V8、ICU 字符库、GPU 合成器、网络栈的固定开销。

实施记录（同日追加）：方案 2「去掉顶栏毛玻璃」与方案 4「字重归并」已实施并通过三档宽度验收； 方案 3「content-visibility」在实施后经实测收益为零、且造成首屏滚动条失真 26%，已回退；方案 5「表格改列表」在 01 课试点后一次实渲即被判定"展示异常"，已整批回退——详见下文方案 3、方案 5。

一、实测环境与方法

为了排除扩展、缓存、其他标签的干扰，每次测量都用独立的临时 profile 启动 Chrome，并在加载完成后通过 CDP（Chrome DevTools 协议）读取指标，同时用系统 API 读取各进程的内存。

四、另外验证的两件事

1. file:// 下学习状态是共享的（好消息）

曾担心双击打开时每个文件是独立源、导致「学习状态」跨页不互通。实测从 index.html 写入 localStorage，再导航到 01 课读取——能读到。Chrome 把所有 file:// 页面视为同一个源，状态记录功能正常工作。

2. 同源标签页并不会复用渲染进程

曾设想"改用本地 HTTP 服务让同源页面共享进程、从而省内存"。实测：无论 file:// 还是 http://，每新开一个标签页就新增一个独立渲染进程（两次新开，渲染进程都 +2）。这条设想不成立，改用 HTTP 服务并不能省内存，因此不作为优化建议。

五、优化方案（按收益排序）

  1. 1 · 单标签阅读，开启「内存节省程序」省 80–115 MB / 个标签 这是唯一有数量级效果的杠杆。既然每个标签页都是独立渲染进程、且同源也不复用，同时开 5 个讲义页就是 5 × 80–115 MB 的纯渲染开销，再叠加每个页面的内容成本。

    做法：Chrome 设置 → 性能 → 打开「内存节省程序」，让闲置标签自动休眠。也可以访问 chrome://discards 手动丢弃暂时不看的标签。

    阅读习惯上：用 docs/index.html 作为唯一入口页跳转，而不是把十几课都开着。

  2. 2 · 去掉顶栏的毛玻璃效果样式重算 −64%滚动 CPU −30% tools/style.css 第 129–130 行给吸顶栏加了 backdrop-filter: blur(12px) saturate(1.3)。它会让顶栏成为独立合成层，还必须保留其背后像素的副本，滚动时持续重新采样。

    实测（软件合成）：滚动一屏时样式重算从 190 次降到 68 次，滚动 CPU 从 501 ms 降到 352 ms。你的机器是 i7-8565U 核显，软件合成占比比独显机器高，这条对你尤其有效。GPU 合成模式下 CPU 差异会变小，但合成层纹理（占 GPU 进程内存）依然会省下来。

    /* tools/style.css 第 129-130 行 */
.topbar {
  background: color-mix(in srgb, var(--bg) 84%, transparent);
  backdrop-filter: blur(12px) saturate(1.3);   /* ← 删掉这一行 */
  border-bottom: 1px solid var(--line);
}

    背景本来就是 84% 不透明的页面底色，改成不透明后视觉上几乎看不出差别，底部细线保留。改完必须重跑 npm run build 并同步 docs/style.css。

  3. 3 · 长文档：让屏幕外内容不参与排版已实施 → 实测否决 → 已回退 做法：改 tools/build_html.mjs 按 h2 把正文包成 <section class="sec">（原正文在 <main> 下是扁平的，没有分节容器），再对 .sec 加 content-visibility: auto 与 contain-intrinsic-size: auto 720px，让屏幕外的小节跳过排版与绘制。

    实测结果：收益为零，代价明显，已回退。

    实测项未分节分节后结论
    加载时 Layout 耗时1735 ms1854 ms未改善
    滚动阶段 Task 耗时570 ms573 ms无差别
    首屏文档总高73,113 px54,117 px短 26%，滚动条失真
    慢速浏览一遍后73,113 px73,509 px会收敛，但过程中位置漂移
    前 5 个标题的位置逐像素完全一致分节未改变布局（间距修正有效）

    原因：这份文档各小节高度差异极大（约 500 px 到 2 万 px），contain-intrinsic-size 取任何固定估算值都会让文档总高严重偏离实际。虽然滚过一遍后浏览器会记住真实尺寸并收敛，但首次浏览期间滚动条长度会从 54,117 变到 73,509，产生"内容在往下移"的漂移感——对精读场景是明显劣化。而布局成本的大头是 CJK 字体就绪后的全文重排，跳过屏幕外小节并不省它。

  4. 4 · 字重归并到标准两档零视觉损失 tools/style.css 中出现了 font-weight: 750（第 413 行）、780（第 893 行）、650（第 978 行）以及多处 600。这类非标准字重，在命中可变字体（Windows 11 自带的 Segoe UI Variable、或系统里装了思源黑体可变版）时，每个不同数值都会实例化一套字形实例。中文页面的字形缓存是隐形大头。

    建议统一到 700 与 600 两档。改动无副作用，风险为零。

  5. 5 · 步骤流水账表格改「一行一条」列表已试点 → 已整批回退 表格在 Blink 中是最重的布局对象（走独立的表格布局算法），而且每一列都必须服从同一套列宽——内容长短差异一大，短列就被压扁、长列疯狂折行。01 课原有 41 张表、267 行、1,004 个单元格。

    先说一条被实测推翻的旧判据：此前写的"首列 ≤3 字、其他列含长句 → 必然竖排"不成立。列宽是整张表所有列共同博弈的结果，且首列是纯数字或拉丁词时根本不会折行（拉丁词不折行，最小宽度就是整个词）。用无头 Chrome 逐格实测（"单行所需宽度 vs 可用宽度" + 实际行数）后：01 课 41 张表里只有 2 张真的被挤压（八大排序一览的"不稳定"列 43.2/44.4 px、快排演算的"起始"18.2/29.6 px）；全仓库 13 课 230 张表也只有 3 张（另两张在 04 / 06）。

    做法（已试过，结论是不要这么做）：把 10 张「步骤流水账」表——每行代表"第几步做了什么"、各列语义互不相同（DFS/BFS 演算、Kruskal/Prim/Dijkstra 逐轮、拓扑排序、绕树记录、八大排序一览、快排挖坑、线性探测算例）——换成「一行图例 + 每条一行、字段用全角 ｜ 分隔」的列表：

    **每行依次是：步 ｜ 动作 ｜ 栈（顶在右） ｜ 已访问（输出序）**

- **1** ｜ A 无路可退，先访问 A、压栈 ｜ `A` ｜ A
- **2** ｜ A 的第一个未访问邻居 B → 访问 B、压栈 ｜ `A B` ｜ A B

    结构指标确实全部向好：表格 41 → 31 张、行 267 → 192、单元格 1,004 → 640（−36%）；DOM 节点 10,971 → 10,208；页面总高 73,113 → 72,159 px；"逐字竖排"从 2 处降到 0 处；三档宽度与深色主题截图也无溢出。

    但一次实渲就被否掉，已整批回退：① ｜ 是行内文本，比例字体下每一行分隔符的横坐标各不相同——列对齐在数学上不可能，眼睛会反复试图按列扫读而失败，看上去就像一张"坏掉的表格"；② 因此原表里那些靠成列才好用的关键信息被拆散到行中段、还会折行——例如八大排序一览的"稳定性"一列（考试就考哪个不稳定）、Kruskal 的"判断"一列（✓选中 / ✗跳过），散进长句后完全丧失可扫性。回退方式：git checkout HEAD -- 软考学习/01-数据结构与算法.md，再重跑两类标记缺陷修复（回退会把 ~→～ 的修复一起带回旧状态，必须补跑）。

    这条的教训：结构指标好 ≠ 读者读起来好。横向对齐的比较信息留在表格里；真正竖排的那 3 张，优先改措辞 / 缩格内文字，其次改分组列表（每条一段、术语加粗引导），绝不要用 ｜ 把字段拼回一行。任何新格式在推广到多课之前，必须先在一页上实渲并逐格核对。

不建议做的

做法为什么不建议
关闭硬件加速省下 GPU 进程的 105–132 MB，但光栅化会转移到渲染进程，总量通常不降反升，滚动还会明显变卡
拆分讲义页破坏「一考点一文件」结构，且实测页面内容只占约 30 MB，拆了也省不下来
给整页小节加 content-visibility已实测：收益为零、首屏滚动条失真 26%，见方案 3（实施后已回退）
换用更轻的字体栈页面零外部请求、用的是系统字体，没有可省的下载体积；pdf/text/ 与 docs/ 无关
用 ｜ 拼列的"伪表格"替换表格省 DOM 节点是真的，但比例字体下列不可能对齐，关键列信息被打散、还会折行——读者第一眼就判定"展示异常"，见方案 5（已整批回退）

六、自己动手看内存

想确认某个标签页到底吃多少，不要看 Windows 任务管理器（chrome.exe 十几行分不清谁是谁），用 Chrome 内置的：

  1. 在 Chrome 里按 Shift + Esc 打开 Chrome 任务管理器；
  2. 看「内存占用」列，并注意每行左侧的类型（标签页 / GPU 进程 / 浏览器 / 实用程序）；
  3. 同一个页面刷新后内存会明显回落，说明是"正常的高水位"而非泄漏；
  4. 要判断页面自身是否过重，看 DOM 节点数（本仓库最大页 10,971，健康）和 JS 堆（0.57 MB，极健康）比看总内存更有意义。
附录：本次诊断用的探针脚本（可复现）

脚本用无头/带界面 Chrome + CDP 读取指标，并与系统进程内存做关联。保存在 .refs/mem-probe.mjs（该目录已 gitignore，不随仓库提交）。

用法：
  node .refs/mem-probe.mjs <文件路径或URL> [normal|noblur|ui|ui-noblur] [标签]
示例：
  node .refs/mem-probe.mjs "docs/01-数据结构与算法.html" ui "01课"
  node .refs/mem-probe.mjs "about:blank" normal "空白页基线"

mode 含义：normal 无头模式；ui 带界面（最贴近真实）；noblur / ui-noblur 注入覆盖样式禁用 backdrop-filter 作为对照。

import { spawn, execSync } from 'node:child_process';
import { mkdtempSync, rmSync } from 'node:fs';
import { tmpdir } from 'node:os';
import { join, resolve } from 'node:path';
import { pathToFileURL } from 'node:url';

const CHROME = 'C:/Program Files/Google/Chrome/Application/chrome.exe';
const PORT = 9411 + (process.pid % 200);
const rawTarget = process.argv[2];
const MODE = process.argv[3] || 'normal';
const url = /^https?:|^file:|^about:/.test(rawTarget)
  ? rawTarget : pathToFileURL(resolve(rawTarget)).href;

const sleep = ms => new Promise(r => setTimeout(r, ms));

function chromeProcs() {
  const map = new Map();
  try {
    const out = execSync('tasklist /FI "IMAGENAME eq chrome.exe" /FO CSV /NH',
      { encoding: 'utf8', windowsHide: true });
    for (const line of out.split(/\r?\n/)) {
      const m = line.match(/^"chrome\.exe","(\d+)","[^"]*","\d+","([\d,]+) K"/);
      if (m) map.set(+m[1], +m[2].replace(/,/g, ''));
    }
  } catch {}
  return map;
}

class CDP {
  constructor(ws) {
    this.ws = ws; this.seq = 0; this.pending = new Map(); this.handlers = new Map();
    ws.addEventListener('message', ev => {
      const m = JSON.parse(ev.data);
      if (m.id && this.pending.has(m.id)) {
        const { res, rej } = this.pending.get(m.id); this.pending.delete(m.id);
        m.error ? rej(new Error(JSON.stringify(m.error))) : res(m.result);
      } else if (m.method && this.handlers.has(m.method)) {
        this.handlers.get(m.method)(m.params); this.handlers.delete(m.method);
      }
    });
  }
  send(method, params = {}) {
    const id = ++this.seq;
    return new Promise((res, rej) => {
      this.pending.set(id, { res, rej });
      this.ws.send(JSON.stringify({ id, method, params }));
    });
  }
  once(m) { return new Promise(res => this.handlers.set(m, res)); }
  async evalJS(expression) {
    const r = await this.send('Runtime.evaluate', { expression, returnByValue: true, awaitPromise: true });
    return r.result && r.result.value;
  }
}

async function typedMemory(cdpBrowser, snapshot) {
  const res = {};
  const info = await cdpBrowser.send('SystemInfo.getProcessInfo');
  for (const p of info.processInfo || []) {
    const kb = snapshot.get(p.id), type = p.type || 'unknown';
    const s = res[type] || (res[type] = { count: 0, totalMB: 0, maxMB: 0 });
    s.count++;
    if (kb) {
      s.totalMB = +(s.totalMB + kb / 1024).toFixed(1);
      s.maxMB = Math.max(s.maxMB, +(kb / 1024).toFixed(1));
    }
  }
  return res;
}

  mine.sort((a, b) => b.memKB - a.memKB);
